# dev-research 技能实现计划

## 一、这个技能做什么（职责定性）

按蓝图 §10.1/§10.2：**技术调研 → 带来源引用的报告（后台代理执行；只信一手来源、每条结论带引用）**。它把"X 和 Y 该选哪个""某平台 API 支不支持 Z"这类技术未知，变成落盘 `docs/research/NNNN-slug.md` 的一手来源调研报告，供 need 的 FR、spec 的实现决策、决策卡引用。实盘先例 docs/research/0001（tracker 三平台调研）已示范了报告形态，本次将其形式化进模板。

定位要点：research 是**无状态纯参考资料**（§6.1，frontmatter 只有 `id`，check.sh validate 只做轻校验、无必填节）；**不进 sdlc next-mode 自动串联链**（路由表无此行，用户手动或 dev-clarify 调研驱动方法联动触发），出口只指路不代拍板——调研给事实与对比，方向取舍仍归决策卡/spec。

## 二、怎么做（SKILL.md 运行时设计，~100 行，§12 范文文风）

1. **前置**：仓库根须有 `.sdlc/check.sh`，否则停、指路 /setup-workspace。
2. **入口**：
   - **值得做亮牌（可拒绝）**：问题一句话、单来源、5 分钟能查证 → 亮牌"这是内联查证不是系统调研"（对应 dev-clarify 三层分工），用户坚持才立项。
   - **研究问题三要素规整**：模糊的"帮我调研 X"必须规整成 `要回答什么 / 为什么重要（堵着哪个决策）/ 影响哪个 FR 或假设`，要素不全先问齐；多个问题同主题可并一张报告。
3. **决策点①（开工前必问）**：念问题清单请用户确认，防答非所问——调研最大的浪费是跑偏。
4. **调研纪律（核心）**：
   - **后台代理并行**：研究问题派后台子代理并行检索（Agent 工具），主会话不被长检索阻塞；平台无后台能力则前台顺序执行并告知。
   - **只信一手来源**：官方文档、官方 API 参考、代码本身、标准 RFC；二手内容（博客/教程/AI 生成）只能作线索，结论必须回溯到一手来源；查不到一手来源就如实写"未找到一手来源，以下为二手线索"。
   - **每条结论带引用 + 检索日期**（平台 API 随版本演进，0001 先例教训："实现时请复核"）。
   - **事实与判断分离**：有出处的标事实；推断的标"判断"并写依据。
   - **防编造**：子代理带回的结论，支撑关键决策（影响 FR/决策卡）的逐条回原文核验，一般结论抽验；禁止拿模型训练记忆冒充检索结果——凭记忆的内容要么检索验证要么明确标注；检索工具不可用 → 停手如实相告。
5. **出口门禁**：落盘前装载 ref-writing（§7.2）；按固定模板落盘 `docs/research/NNNN-slug.md`（id = 目录内最大号+1）→ `check.sh validate`（research 轻校验）→ `publish` → 提交留痕 `[trivial]`。
6. **出口（指路，不自动串联）**：给用户念"结论速览"；抛决策问题："报告 NNNN 已落盘，结论可作 spec 实现决策依据 / 回 dev-clarify 决策卡拍板"——否掉的方案建议进「范围与非目标」。
7. **中断语义**：research 无状态字段，未落盘即未发生——问题确认前被打断直接重开，确认后重跑检索（幂等），报告只有落盘才存在。
8. **禁止事项**：无来源下结论、拿记忆冒充检索、替用户拍板选型、报告里写实现方案、动 need/spec 等其他产物（只指路）、把过期报告当活文档改（过期 = 重新调研出新报告）。

**报告模板**（内嵌 SKILL.md，按 0001 先例形式化）：frontmatter（id、created）+ `## 调研问题与用途`（三要素清单）+ `## 结论速览`（表/要点，每条带来源与日期）+ 分主体小节（逐条结论带"来源：URL（检索日期）"）+ `## 对本项目的映射要点`（回答了哪个 FR/假设/决策卡、否掉了什么）+ `## 来源清单`。
