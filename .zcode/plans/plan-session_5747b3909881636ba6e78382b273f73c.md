# 实现 dev-accept 技能（蓝图 §11.9 按图施工）

## 背景与依据

dev-accept 是批 1 唯一剩余技能（§10.2 第 11 项未标注）。规格来源：
- **§11.9**：触发 = spec 全部工单 done 后自动（dev-ship 链）或手动；做什么 = 逐条运行集成级验收场景、逐 FR 核销、跑 `check.sh all`、写验收报告；出口 = passed → spec → done（末轮且成功标准核销、无未接受风险 → need → fulfilled），rejected → 缺陷归 dev-fix、范围问题进下一轮建议；决策点 = 开不开下一轮；落盘前加载 ref-writing。
- **§6.5**：验收报告正文固定四节 `## 场景结果`（逐条：场景/FR/证据/结论）、`## 假设验证`、`## 残余风险`、`## 下一轮建议`；frontmatter `id` `spec` `round` `status`。
- **check.sh 已就绪**：`validate` 对 acceptance 校验四必填节 + `spec`（须存在）+ `round`；`phase` 输出 spec 行带 `need=`/`round=`、acceptance 行带 `spec=`，可作入口定位依据。
- **同构模板**：与 dev-review / dev-ship / dev-plan / dev-spec 完全同构（定性三行 → §0 前置 → §1 入口门禁 → §2 装载上下文 → §3 纪律 → 内嵌模板 → §4 出口门禁 → §5 中断与交接 → 禁止事项），全文约 95 行（现役 82–98）。

## 改动一：新建 `skills/dev-accept/SKILL.md`

**Frontmatter**（仅 name + description，description 写宽承接直连请求 + 说明拒绝/衔接）：
> 对工单已全部交付（done）的 spec 做集成验收——在集成后的代码上逐条运行 spec 的集成级验收场景、逐 FR 核销、跑全量检查，写 docs/acceptance/ 验收报告（场景结果/假设验证/残余风险/下一轮建议），通过则 spec 置 done（末轮且成功标准核销、无未接受风险则 need 置 fulfilled），不通过则指路 dev-fix。当用户要求验收、核销需求、检查 spec 是否交付、跑验收场景时使用——工单未全部 done 或没有 approved spec 时会在入口被拒绝并指路 dev-ship。

**章节骨架与关键设计**（按图施工的落地决策）：

- **§0 前置**：`.sdlc/check.sh` 存在校验（同款）。
- **§1 入口门禁**：
  1. **重入判定先行**：docs/acceptance/ 已有 `spec: NNNN` 指向本 spec 且 `status: draft` 的报告 → 续接，已核销的场景/FR 不重跑；已有 `passed` → 说明已验收、停；已有 `rejected` → 终态，指路 dev-fix 或下一轮，停。
  2. **确定 spec**：用户给了编号 → 用它；没给 → `check.sh phase` 找 `approved` 且名下工单全部 `done` 的 spec；恰一张直接用；多张列候选（编号、标题、round）请用户点名，禁止代挑（沿 dev-plan 惯例）；零张 → 停止转述缺什么（有 implemented 工单 → 先 /dev-ship）。
  3. **集成环境校验**：当前分支应为 BASE_REF（集成后的代码）；不在 → 请用户先切回并同步，验收不跑在未合并的分支上。
- **§2 装载上下文**：spec 全文（重点 ## 验收场景）→ need 全文（若有；重点成功标准、## 假设与风险）→ 该 spec 名下工单 done 清单；三五句复述：验收哪几条集成场景、覆盖哪些 FR、怎么算通过。
- **§3 验收纪律**：
  - 只跑 `[FR-N | 集成级]` 场景（工单级场景已由 dev-implement 在票内核销，不重跑）；逐条 Given/When/Then 运行，**证据 = 运行输出/观察结果，读代码不算**。
  - 逐 FR 核销：FR 核销 = 覆盖它的场景全部过；说不出证据不许判过。
  - 跑 `check.sh all` 必须全绿；仓库没定义检查命令 → 本身是发现，写进报告，不静默跳过。
  - 假设验证：逐条对照 need `## 假设与风险` 写验证结果。
  - 场景失败只记录证据，不在验收中现场修；全部跑完再定级。
- **§4 出口门禁**：
  1. **落盘前用 Skill 工具装载 ref-writing**（§7.2 引用矩阵）。
  2. 写报告 `docs/acceptance/NNNN-slug.md`（id = 目录内最大号 +1，目录懒创建；`round` = spec 的 round；status 先 draft），四节固定模板内嵌，`check.sh validate` 必过 + `publish`。
  3. **判定（机械，不问人）**：集成场景全过 + all 绿 → `status: passed`；有场景没过 → `status: rejected`，缺陷与范围问题如实写报告。报告状态变更的提交用 `[trivial]`（沿 dev-ship §4.3 同理由：流程状态落盘，不是绕门禁）。
  4. **passed 出口**：spec frontmatter `status` 改 `done` + 追加 `done: <今日>`，跑 validate + publish，`[trivial]` 提交。然后 need 处理：成功标准逐条核销、且残余风险为空（或逐条经用户显式接受）→ need `status` 改 `fulfilled` + 追加 `fulfilled: <今日>`；有未核销标准或未接受风险 → 抛决策问题"开不开下一轮"（带默认建议，按残余风险性质给：默认建议开 → 下一轮从 /dev-spec 起步、round 递增、范围 = 残余风险），用户不显式确认不开轮、need 不动。
  5. **rejected 出口**：缺陷指路 dev-fix 开 fix 工单（dev-fix 未实现 → 断链说明，沿 dev-ship 断链话术风格），范围问题确认已写进 `## 下一轮建议`，停。
- **§5 中断与交接**：停前报告以 `status: draft` 落盘（已跑场景的结果与证据全部写入），重入从 §1.1 续接；状态在盘上，不在对话里。
- **禁止事项**（约 6 条）：改工单状态或 spec 正文（spec → done 归本技能、工单状态归 dev-ship，验收场景与实现不符是 rejected 证据不是现场改场景的理由）；没跑场景凭读代码写"通过"；验收中现场修缺陷；跳过 `check.sh all` 或红灯写"全绿"；为通过而弱化结论、删失败场景；未满足末轮条件就把 need 置 fulfilled（沉默或"都行"不算接受风险）。

4. **提交**：`[trivial] 入库 dev-accept 流程技能（蓝图 §11.9 按图施工，§10.2 标注完成）`，正文含：技能行数与设计要点、symlink 安装说明、§13.2 五项自测结果、trivial 豁免理由（纯文档新增，dev-retro 审计留痕）。提交经 `.sdlc/check.sh` 门禁，不用 --no-verify。

## §13.2 自测方案（写入提交正文）

- **产物校验（实测）**：在 /tmp 建 sandbox（拷贝 .sdlc/，构造 need/spec/ticket 产物），写 acceptance 报告正例过 `check.sh validate`，再测缺节 / 缺 spec / 缺 round 三类反例被拦——check.sh 是纯脚本，可直接行为实测。
- **拒绝路径（实测 + 静态）**：sandbox 中工单未全 done 时 `phase` 输出无"approved 且全 done"候选，技能入口拒绝逻辑以此为准——实测 phase 输出，静态核验拒绝话术与指路（dev-ship）。
- **触发 / 衔接（静态核验）**：3 句话术（含 1 句"这功能做完了吗"式直连请求）对照 description；出口三形态（passed 自动推进 + 决策点问人 / rejected 拦停指路）对照 §8 契约。重入为静态核验（draft 续接路径）。
- 完整行为验证（真实会话中触发衔接链）待新会话补跑——本会话技能列表固定，沿既有技能惯例在提交与 §10.2 中注明。

## 执行顺序

1. 写 `skills/dev-accept/SKILL.md` → 2. sandbox 自测（validate 正反例 + phase 拒绝依据）→ 3. symlink 安装 → 4. 蓝图 §10.2 标注 + README 更新 → 5. `[trivial]` 提交（走 check.sh 门禁）。
