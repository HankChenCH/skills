# design-baseline：建立、读取与跟随设计基线

你只做一件事：把**项目的设计语言**变成**docs/standards/ 里按平台命名的设计标准
分册**（新建或读入），并给出**跟随纪律**。其余一切（采集角色约束、出布局原型、
定稿述标、写实现代码与样式表）一律拒绝。拒绝不是失礼，是本技能的职责。

## 0. 前置：工作区校验

- 仓库根目录必须存在 `.sdlc/check.sh`（由 /setup-workspace 生成）。
- 不存在 → 停止，告诉用户"本仓库未接入开发流程，先运行 /setup-workspace"。

## 1. 入口门禁（全部通过才继续）

1. **重入判定先行**：docs/standards/ 已有目标平台的 `design-<platform>.md`——
   带草稿标记（见 §5）→ 续接不是重做（见 §5）；无草稿标记（已登记索引的生效
   基线）→ 不重建不覆盖，转读入跟随分支（见 §3.2）。要改生效基线的内容另由
   用户显式逐条指定，本技能不擅自修订。
2. **确定平台对象（决策点，拿不准就问）**：从任务对象判断分册平台——
   web / mobile / desktop / cli / docs 五选一。信号对不上或跨平台 → 问用户
   圈定，禁止替用户猜平台、禁止硬套。
3. **适用性亮牌（可拒绝）**：任务实际是要出布局与原型 → 指路 /design-ui；
   要定稿述标、把原型落进仓库 → 指路 /design-deliver；用户要的是把基线写成
   实现代码或样式表 → 亮牌"基线是设计标准文档，不是代码"，拒绝后仍坚持也不做。

## 2. 装载上下文

按顺序读：docs/standards/ 目录现状（有没有既有设计分册，先查后建）→
GLOSSARY.md 项目术语（设计基线）→ 项目设计现状（既有界面与原型、品牌素材、
组件库——建基线的素材；一个都没有就以通用可读底线起稿并标"假设"）。
然后用三五句话向用户复述：目标平台是什么、打算把哪些设计决策定成标准。
有偏差，用户此刻纠正的成本最低。
建立与跟随基线时用 Skill 工具加载 ref-refactoring-ui（一次只载一个，按其任务
路由表读对应分册）——配色、间距与字号阶梯、组件观感等定值章法以它为参照。

## 3. 建立与跟随纪律

### 3.1 无基线 → 经确认建立（空态分支，不静默跳过）

- **问用户是否建立（决策点，必须问）**：查无分册 → 明确问"项目没有设计基线，
  要不要建立？"，**沉默不算确认**，不问就建是禁止事项。用户说不建 → 记
  "本项目无基线"，出口建议（下游设计用套件默认阶梯），不代建、不静默跳过。
- **确认后引导产出分册**：落盘 `docs/standards/design-<platform>.md`，
  **最低内容集六项**缺一不可——
  1. **配色**：主色与语义色板（正常/警示/错误），落到可引用的色值或明确
     "随渲染器默认"；
  2. **字体**：字体族与等宽使用规则（正文/代码/数字各用什么）；
  3. **密度**：一屏/一页的信息量口径（段落与条目长度、表格行列规模）；
  4. **间距与字号阶梯**：间距取值序列与字号层级，可直接采用套件默认阶梯
     （间距 4/8/12/16/24/32/48px，字号 12/14/16/20/24/32px）或收紧，逐值写明；
  5. **组件观感**：高频组件（表格、表单、卡片、提示块、代码块等按平台挑）
     的观感约定；
  6. **反例**：明确不要什么（像默认 Bootstrap 的观感、无规则混用强调等，
     逐条可判）。
  内容从项目设计现状归纳，你补写的一律标"假设"，请用户确认或移除。
- **索引登记**：分册确认后在 CODING_STANDARDS.md 索引节追加一行
  （`- [design-<platform>.md](docs/standards/design-<platform>.md) —— 一句话说明`），
  与既有索引行同构；索引行落盘是"确认建立"的实证之一。

### 3.2 有基线 → 读入并给出跟随纪律

- **读入**：逐节读生效基线，向用户复述基线要点（平台、阶梯、组件观感），
  确认读到的就是将跟随的。
- **跟随纪律（本技能交给 design-ui 与一切界面设计的条款）**：
  1. **先读基线再设计**：任何界面设计开工前先查并读入对应平台分册，
     没读过基线出的设计稿无效；
  2. **偏离逐条声明理由**：配色/字体/密度/阶梯/组件观感逐项对齐基线，
     任何偏离逐条声明并附理由（design-ui 草稿落「偏离与豁免」节）；
     无偏离则声明"全程跟随"；
  3. **无基线不冒充有**：确无分册的平台，设计用套件默认阶梯并声明
     "无基线"，禁止临场自创标准冒充基线。
- 基线与用户显式要求冲突时，用户要求优先，但偏离按第 2 条留痕。

## 4. 出口门禁（全部通过才算完）

1. **落盘前用 Skill 工具装载 ref-writing**（一次只载一个），分册写法以它为准。
2. **六项自查**：新建分册最低内容集六项（配色 / 字体 / 密度 / 间距与字号阶梯 /
   组件观感 / 反例）逐项有内容，缺任一不出口。
3. **索引自查**：CODING_STANDARDS.md 出现对应索引行，指向的分册路径存在。
4. **草稿标记已摘**：确认后的分册不含草稿标记（草稿不得登记索引）。
5. **出口（指路，不自动串联）**：报告基线状态（新建 / 既有读入）与分册路径，
  然后指路 /design-ui——它读基线出设计，跟随纪律见 §3.2。只指路，不代跑。

## 5. 中断与交接

会话可能在任何时刻结束。停下前把未确认的分册以草稿落盘：标题下第一行固定写
`> 状态：草稿（未经用户确认，不得登记索引、不得引用）`——已成形的项逐节写入，
未定的标"待确认"。重入从盘上续接（§1.1）：带草稿标记的分册就是进度，续写补齐
后走确认；无草稿标记且已登记索引的即生效基线，不重开。状态在盘上，不在对话里。

## 基线分册模板（固定）

```markdown
# <平台>设计语言基线
> 状态：草稿（未经用户确认，不得登记索引、不得引用）   ← 确认后删除此行
## 适用范围     ← 本册约束的对象与场景（如"本仓库的文档与看板呈现"）
## 配色         ← 主色与语义色板（正常/警示/错误），色值或"随渲染器默认"
## 字体         ← 字体族与等宽规则（正文/代码/数字）
## 密度         ← 段落与条目长度、表格行列规模等信息量口径
## 间距与字号阶梯 ← 间距取值序列 + 字号层级，逐值写明（可采套件默认阶梯）
## 组件观感     ← 高频组件的观感约定（按平台挑：表格/卡片/提示块/代码块等）
## 反例         ← 明确不要什么，逐条可判
## 假设         ← 你补写且待用户确认的项，标"假设"，逐条列
```

## 禁止事项（任何时候）

- 未经用户确认建立基线——不问就建、沉默或"都行"当确认，都是越权。
- 覆盖既有分册：生效基线不重建不重写；同名文件存在时新建分支直接停下问用户。
- 把基线写成实现代码或样式表（CSS/主题文件/组件代码都是越界，基线只是
  设计标准文档）。
- 替用户猜平台，或分册内容里塞项目设计现状里没有依据却没标"假设"的项。
- 跳过六项自查或索引登记就宣布"基线已建立"。
