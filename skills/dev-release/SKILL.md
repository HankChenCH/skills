# dev-release：版本发布与 CHANGELOG

你只做一件事：把**一段已合入主干的历史**变成**一个有版本号、有 CHANGELOG、过了检查单的发布**。
其余一切（顺手修缺陷、改已发布条目、未经确认打 tag）一律拒绝。
拒绝不是失礼，是本技能的职责。

## 0. 前置：工作区校验

- 仓库根目录必须存在 `.sdlc/check.sh`（由 /setup-workspace 生成）。
- 不存在 → 停止："本仓库未接入开发流程，先运行 /setup-workspace"，不做任何发布。

## 1. 入口门禁（全部通过才继续）

1. **重入判定先行**：CHANGELOG.md 存在，且顶部最新版本节没有对应的 git tag →
   发布做了一半，跳到 §4 从断点续接（断点清单见 §5）；顶部版本节已有 tag 且已推送 →
   报告"v<版本> 已发布"，收工，不重复发版。
2. 读 `.sdlc/config.sh` 的 BASE_REF。当前必须在该分支上、工作树干净
   （`git status --porcelain` 为空）、与远端同步（ahead/behind 皆零）。
   任一不满足 → 停止并转述差在哪：发布只从主干打。
3. **确定发布区间**：`git tag -l 'v*'` 取最新版本 tag 为起点（无任何 tag →
   自首次提交），终点 HEAD。区间内 `git log` 为空 → 停止："无可发布内容"，不空发版本。
4. 区间内有 ready/in-progress 的工单 → 如实列出（它们在分支上，不影响主干内容），
   问用户是否照常发布；不答不继续。

## 2. 装载上下文

按顺序读：区间 `git log --oneline` 与 diff 摘要 → 区间内 done 工单及其 spec
（docs/tickets/、docs/specs/，变更分类的盘上依据）→ 既有 CHANGELOG.md
（不存在则本次懒创建）。

然后用三五句话向用户复述：发布区间覆盖哪些提交与工单、大致是什么性质的变更。
有偏差，用户此刻纠正的成本最低。

## 3. 决策点①：版本号确认（开工前必问）

- 分类映射（依据盘上产物与提交，不凭感觉）：破坏性变更（接口/schema/行为不兼容，
  spec 实现决策或提交明示）→ **major**（0.x 期按 semver 惯例 → minor）；
  新用户可见能力（新 FR）→ **minor**；缺陷修复 → **patch**。
- 完整念一遍区间变更清单（逐条带工单/spec/提交来源）+ 建议版本号与理由，
  请求确认。**沉默不算确认**，要改回本节。

## 4. 发布检查单（顺序执行，逐项留证）

1. `.sdlc/check.sh all`（全量 lint / typecheck / test），必须全绿。仓库没定义
   任何检查命令 → 这本身就是发现：如实报告，不静默跳过。
2. CHANGELOG 条目落盘：落盘前用 Skill 工具装载 ref-writing。按下方模板懒创建
   骨架 + 新版本节（分类逐条，每条指得回工单/spec/提交，无变化的分类不写）。
   项目清单带版本字段（package.json / pyproject 等）→ 一并同步。
3. 发布记账提交：`[trivial]` 并写明豁免理由（版本记账，无逻辑变更）——同
   dev-ship 合并后逻辑，这是发布状态落盘，不是绕门禁（dev-retro 可审计）。
4. **决策点②：tag 与推送（单向门，必须问人）**：建 annotated tag `v<版本>`
   （message = 本版一句话摘要），push BASE_REF 与 tag。TRACKER=github 且 gh
   可用 → 附带问是否 `gh release create`（正文取 CHANGELOG 该版本节）。
   **用户显式确认才执行；沉默或"都行"不算确认。**
5. **部署验证**：问清部署方式与验证判据（一条可判定的检查，如冒烟命令/健康检查）。
   有部署 → 部署后按判据验证并报告结果；库类产物（无部署面）→ 记"不适用"；
   验证执行不了 → 如实报告，不装绿。结果只在会话中报告，不回写 CHANGELOG。
6. **出口（指路，不自动串联）**：报告四件——版本号、tag、CHANGELOG 位置、
   部署验证结果——然后指路："要沉淀这一周期，/dev-retro。"
   发布给版本与证据，复盘归 dev-retro，不做完沉默等指令。

## 5. 中断与交接

状态在盘上，断点四处，重入从对应步骤续接：CHANGELOG 新版本节已写未提交 →
重跑 §4.2；已提交未打 tag → 从 §4.4 续接；已打 tag 未推送 → 从推送续接；
未部署验证 → 从 §4.5 续接。tag 一旦推送即发布完成，不可回撤。
状态在盘上，不在对话里。

## CHANGELOG 模板（懒创建时用）

```markdown
# Changelog

本项目的所有显著变更记录于此。
格式遵循 Keep a Changelog（https://keepachangelog.com），版本遵循语义化版本。

## [v<版本>] - <YYYY-MM-DD>

### Added
### Changed
### Fixed
```

分类按需取舍：Added / Changed / Deprecated / Removed / Fixed / Security；
无变化的分类整节不写。已发布的旧节只读不改。

## 禁止事项（任何时候）

- 未经用户显式确认打 tag 或推送——发布是单向门，沉默不是确认。
- 检查有红灯仍发布，或把部署验证写成"应该没问题"。
- CHANGELOG 条目编造——每条必须指得回提交/工单/spec。
- 替用户定版本号。
- 顺手修缺陷或动源码——回 /dev-fix 开票。
- 改写已发布版本的条目——已发布不可变，纠错走下一个版本。
