# ref-git-commit：什么是好的提交与合并信息

总标准只有一条：**半年后顺着提交历史读，每个提交能独立说清"做了什么、为什么"，
且每个提交都能追溯到工单。** 以下每条都是它的分解，提交与评审共用同一份标准。

## 提交（commit）

1. **一次提交只做一件事**：对应工单的一个验收标准或一次红绿循环。"顺手改的"混进来，
   评审与回滚的成本放大数倍——想顺手，另开提交；超出工单范围，另开工单。
2. **首行结构固定**：`[#NNNN] 行为摘要`；多工单 `[#0007][#0008]`（按四位编号写）；
   纯文档与 typo 走 `[trivial]` 豁免。摘要说行为（"修复工单校验漏读 frontmatter"），
   不报文件清单——改了哪些文件是 diff 自己会说的。
3. **首行祈使语气、尽量短**："修复 X"而不是"修复了 X"；它是历史里的索引，详情往下放。
4. **正文写 diff 看不出来的事**：为什么这么改（取舍、被否掉的方案）、影响面与证据
   （哪个测试、什么输出）。首行与正文空一行；三行能说清就不写十行。
5. **禁止**：`--no-verify` 或任何绕过 `.sdlc/check.sh` 的提交；一个提交混多张不相关
   工单；`update`、`fix bug`、`WIP` 这类零信息摘要。

## 合并（merge）

6. **合并方式跟仓库约定，message 跟合并方式**：
   - merge commit：首行讲清合入什么（分支叙事），正文列覆盖的工单编号。
   - squash：多个提交收敛为一个时，message 按第 2–4 条重写（`[#NNNN]` + 行为摘要 +
     为什么），不把中间态的 WIP 带进历史。
   - fast-forward：没有合并信息，历史就是提交本身——提交写干净，历史才干净。
7. **PR/MR 描述里的工单引用语法随平台**：GitHub `#N`（issue 与 PR 同一编号空间）、
   GitLab issue `#N` / MR `!N`、云效 Codeup 无等价短语法。平台编号 ≠ 盘上工单编号：
   `Closes #N` 吃的是平台编号，把盘上 NNNN 直接写进去不会联动任何东西。

## 范例（好 / 差对照）

差：`update`——零信息，门禁也过不了（无 [#NNNN]）。

差：`[#0007] 修改了一些文件并修复bug`——有编号但无行为；"一些文件"迫使读 diff 才知改了什么。

好：

```
[#0007] 修复 publish 在 config 缺 TRACKER 时的静默退出

缺省值 `: "${TRACKER:=local}"` 原本写在读取 config 之后，变量未定义直接退码 1。
证据：bash run-tests.sh 62/62。
```

## 自查口令（每次提交前过一遍）

只做了一件事吗？首行带 `[#NNNN]` 且说的是行为吗？正文说了 diff 看不出来的为什么吗？
半年后顺着历史读到它，还需要翻代码才能懂吗？
