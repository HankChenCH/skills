# 混沌测试（验证依赖故障下的韧性：降级/重试/熔断前加载）

混沌测试向系统注入故障，验证"坏了依赖也仍在稳态内"。
顺序不可倒：先定义稳态，再注入故障——没有稳态定义的注入只是制造事故。

## 好用例的标准

1. **先有稳态假设**：一句可度量的话加"用什么指标证明它成立"（如"下单成功率 ≥ 99.9%，
   以订单表增长与错误率为证"）；注入期间盯这些指标，不盯"感觉还在跑"。
2. **一次只注入一个变量**：注入支付网关超时就不同时加网络丢包——两个变量叠加出的现象
   归因不了，韧性结论必须是单变量下得出的。
3. **只在 seam 上注入**：故障打在预定的依赖边界（外部服务、队列、磁盘、时钟），
   与"测试只在 seam 上测"同源；不往内部实现里塞故障。
4. **验证回弹，不只验证不崩**：故障移除后指标要回到稳态（重试耗尽、熔断恢复、积压消化）；
   "当场没崩但永不恢复"是失败。
5. **可一键终止**：任何注入都有 abort 开关与自动终止条件（稳态指标破阈值即停）；
   先在最小爆炸半径（单实例、预发）演练，再扩大。
6. **输出是结论不是记录**：发现了哪个未预期行为、开了什么 fix 工单、稳态假设要不要修订。

## 范例（好 / 差对照）

差（无稳态定义、叠加注入）：

```text
把支付服务停了，顺便再限流 50%，系统没挂，混沌测试通过。
```

"没挂"不是稳态判据；两个变量叠加，就算失败也归因不了；"通过"没有任何指标支撑。

好（稳态先行、单变量、验证回弹）：

```text
稳态假设：下单成功率 ≥ 99.9%（指标：订单表增长、支付错误率）。
注入：支付网关响应延迟 +10s（toxiproxy 打在网关 seam 上，仅此一个变量），预发环境。
观察：熔断 2s 内打开，下单走降级渠道，成功率 99.97%——稳态保持；
移除延迟后 30s 熔断半开恢复，积压清零。
结论：降级路径符合设计；未预期行为：恢复初期重试风暴抬高网关 p99（已开 fix 工单）。
```

有判据、有单变量、有回弹验证、有产出。

## 反模式

- **在生产无 abort 裸奔注入**：演练变事故，损失没有上限。
- **只注入方便注入的故障**（重启容器），跳过设计真正担心的（慢响应、半开连接、时钟漂移）。

## 自查口令（注入前过一遍）

稳态用什么指标证明？这次只动了一个变量吗？abort 开关与自动终止条件就位了吗？
验证的是"移除故障后回到稳态"吗？结论变成了 fix 工单或假设修订吗？
