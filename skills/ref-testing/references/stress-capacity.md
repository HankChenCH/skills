# 压力/容量测试（有容量或性能目标要验证、或要防性能回归时加载）

压测回答"这个系统在目标负载下是否仍达标、在哪开始劣化"。
先有独立的目标数字，才谈得上通过——没有目标的"压一下看看"不产生知识。

## 好用例的标准

1. **目标来自 spec/SLA，先于脚本存在**："导入 5000 行 ≤ 2s（FR-3）"这样的独立来源——
   期望值独立原则在性能上同样成立，没有目标数字就没有"通过"。
2. **测曲线不只测点**：梯度加压找到吞吐与延迟的拐点（何时开始劣化、劣化形状），
   单压一个峰值说明不了容量上限。
3. **数字可比较**：固定环境与规格、固定数据规模、预热后计量、看分位数（p95/p99，
   平均值会藏住尾部）；跨环境只比相对退化，不比绝对值。
4. **给瓶颈归因**：劣化时看资源水位（CPU、内存、连接池、队列深度），结论带着"卡在哪个资源"。
5. **CI 只留阈值守门**：常规流水线跑小规模基准、断言阈值（超阈即红）；全量压测按需手动跑——
   把小时级压测塞进每次 CI，门禁会被降级成摆设。
6. **结果落盘**：环境、数据规模、数字、日期写成记录，下一轮回归有得对比、可复现。

## 范例（好 / 差对照）

差（无目标、单点、只看平均）：

```text
压了 1000 并发，平均响应 180ms，看起来没问题。
```

"没问题"是相对什么标准？1000 并发是谁定的？平均 180ms 掩盖着 p99 已经 4s 的事实。

好（目标独立、梯度加压、分位数、归因落盘）：

```text
目标：导入 5000 行 ≤ 2s（spec FR-3，即吞吐 ≥ 2500 行每秒）。
实测（4C8M 容器、10 万行种子、预热 5 分钟后计量，各档 10 分钟）：
  1500 / 2500 / 3500 行每秒梯度下 p95 = 0.5 / 0.9 / 1.8s，拐点约 3200 行每秒；
  拐点时 DB 连接池打满（20/20），CPU 与内存 < 60%。
结论：容量满足 FR-3（拐点 3200 > 所需 2500，余量约三成）；瓶颈在连接池，扩池前上限约 3200 行每秒。
```

有目标、有环境、有分布、有归因——下一轮回归有对比基线，超阈即红。

## 反模式

- **拿开发机数字当容量结论**：环境不同，绝对值没有意义。
- **压出峰值就收工**：没有拐点与 p99，容量上限仍是猜的。

## 自查口令（压测前过一遍）

目标数字来自实现外吗？环境、数据、预热固定了吗？看了 p95/p99 而不只是平均吗？
劣化归因到资源了吗？结果落盘可对比了吗？
