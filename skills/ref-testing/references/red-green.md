# 红绿循环（实现一个新行为前加载）

每个行为走一轮 red → green：先写一个会失败的测试，看它红，再写刚好让它通过的实现。
失败测试是"行为尚不存在"的证据；先实现后补测试，测试只是实现的回声。

## 好用例的标准

1. **Red 先行，且看它红**：跑一次失败测试，确认失败原因是"行为缺失"（断言失败、函数不存在），
   不是语法错或环境错——红错了的循环整轮作废。
2. **一循环一行为**：这轮只让一个新测试变绿；发现别的问题，记录、开票，不顺手修。
3. **Green 刚好**：写让测试通过的最小实现，不做"反正以后要"的推广（ref-implementation 的
   无投机泛化）——多余的行为没有红测试护着，写了就是未经验证的代码。
4. **重构在绿的前提下做**：先绿再改结构，测试一行不动；测试红了说明重构改了行为，回退。
5. **禁止为变绿做任何事**：删测试、改弱断言、加条件跳过、放宽名字里的行为——都是把红灯拆掉，
   不是把缺陷修掉（dev-implement 禁止事项）。

## 范例（好 / 差对照）

差（先写实现再补测试，期望值镜像实现）：

```ts
test("parseLedger 汇总 total", () => {
  const rows = [{ amount: 3 }, { amount: 4 }];
  expect(parseLedger(rows).total).toBe(rows.reduce((s, r) => s + r.amount, 0));
});
```

实现刚用 `reduce` 汇总，测试就用 `reduce` 算期望——同义反复，实现写错测试也绿；
"超限报错"这个行为则根本没有测试护着。

好（红先行的失败测试，期望是 spec 来的字面量）：

```ts
test("超限时报错并列出行数", () => {
  const raw = Array.from({ length: 5001 }, () => "a,b");
  expect(() => importCsv(raw.join("\n"))).toThrow(/5000.*5001/);
});
```

名字即规格；5000/5001 来自 spec 上限，不是算出来的；当前实现还没有这个行为，红得其所——
这就是本轮要实现的东西。

## 反模式

- **先绿后红**：实现写完才"补"测试，红从未被观察——你不知道它到底会不会红。
- **一轮多行为**：绿不了就放宽断言凑数，两个行为都没被真正验证。

## 自查口令（每轮绿后过一遍）

这轮的红被看见过吗？当时的失败原因是"行为缺失"吗？实现是否只做了让测试变绿的事？
测试文件在这一轮里被改动过吗？
