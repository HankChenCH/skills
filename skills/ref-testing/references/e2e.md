# e2e 测试（验证关键用户旅程全链路前加载）

e2e 用真实系统（UI → API → 落库）走用户走的路，回答"这条旅程通不通"。
它是数量最少、最慢、最贵的一层——穷举留给底层，e2e 只守关键旅程。

## 好用例的标准

1. **只覆盖关键旅程**：注册 → 下单 → 收确认这个量级的主干（合并前必绿的那几条）；
   给每个行为分支都配 e2e 是把底层的穷举搬到了最慢的一层。
2. **断言用户可观察的结果**：页面呈现、返回给用户的确认、落库的数据；不断言组件树、
   内部状态或网络调用的实现细节。
3. **语义化定位**：选择器用角色、文案、`data-testid`（面向可访问性），不用实现衍生的
   CSS 链——改样式不该红一条旅程。
4. **受控环境与固定种子**：跑在与生产同形貌的环境上，种子数据固定；时间相关逻辑冻结时钟。
5. **失败留证据**：失败自动附截图与 trace，看证据就能复述"哪一步、看到什么、期望什么"。
6. **接受慢，限制数量，不许熬绿**：用自动重试把失败"熬绿"是在掩盖真问题——链路级
   flaky 要当场查，不是重跑三次装没看见。

## 范例（好 / 差对照）

差（断言实现细节，选择器脆弱）：

```ts
test("下单", async () => {
  await page.click("div.checkout-panel > form > button.btn-primary--lg");
  await expect(page).toHaveURL(/\/order\/\d{8,}/);
});
```

改版即红；URL 位数是实现细节；用户到底成功没有（看到了什么）反而没有断言。

好（语义定位，断言用户可见结果与落库事实）：

```ts
test("买家下单后看到确认页且订单可查", async () => {
  await seedCatalog({ "SKU-1": { price: 100, stock: 5 } });   // 固定种子
  await loginAs(buyer);
  await page.getByRole("button", { name: "加入购物车" }).click();
  await page.getByRole("button", { name: "结算" }).click();
  await expect(page.getByText("订单已提交")).toBeVisible();

  expect(await db.orders.latestOf(buyer.id))
    .toMatchObject({ status: "open", total: 100 });
});
```

断言的是用户看到的确认与落下的订单；改样式不红，改行为才红。

## 反模式

- **用 e2e 穷举表单校验**：慢十倍地做底层一行断言能做的事——收回去。
- **断言截图或 DOM 全等**：任何无关改动都红，维护税很快吞掉全部收益。

## 自查口令（加一条 e2e 前过一遍）

这条旅程挂了，用户真的受影响吗？断言里有没有实现细节？选择器语义化了吗？
失败会自动留下能复述问题的证据吗？它能不能降级到更低一层去测？
