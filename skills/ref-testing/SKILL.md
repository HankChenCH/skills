# ref-testing：什么是好的测试

总标准只有一条：**测试断言的是 seam 上的外部可观察行为，期望值来自实现之外；它失败时，读名字和失败信息就能定位该修哪里。**
以下通则是六类测试的公共标准，类别细则按路由表加载，不整载。

## 通则

1. **只测外部行为，不测实现**：断言打在公共接口的出入参上——不测私有方法，不 mock 内部协作者（mock 内部 = 把测试钉死在实现上，重构即红）。
2. **期望值来自独立来源**：已知字面量、手算算例、spec 里的数字；用与实现相同的逻辑算期望值是同义反复——实现错了测试照样绿。
3. **只在预定 seam 上测**：seam 由 spec/design 预定；绕过 seam 横向切穿分层才断言一次，是集成病的主因。
4. **一个测试一个行为**：一个测试断言第二件事就拆——拆完每个失败各自指路，不用排查是哪件事错了。
5. **测试名即规格**：名字写出行为（"超限时报错并列出行数"），不写方法名；测试名连起来能拼出工单的验收标准。
6. **失败信息能直接定位**：失败输出回答"哪个行为、期望什么、实际什么"，不用调试器就知道修哪。
7. **可重复确定**：不依赖执行顺序、真实时间、外部服务；随机逻辑固定种子——飘的测试教会所有人忽略红灯。

## 反模式（识别信号 → 修法）

| 反模式 | 识别信号 | 修法 |
|---|---|---|
| 实现耦合 | 不改行为的重构让测试变红 | 改为断言公共接口的出入参 |
| 同义反复 | 期望值调用被测逻辑或镜像函数算出 | 换独立来源：手算字面量 / spec 数字 |
| 横向切片 | 一个测试铺满多层才断言一次 | 拆回各层 seam，全链路留给集成 / e2e |

## 自查口令（写测试前与失败时各过一遍）

期望值是从实现外的地方来的吗？名字说的是行为还是方法？它红的时候，失败信息指得到修哪吗？
断言落在 seam 上还是钻进了实现？一个测试里塞了几个行为？
