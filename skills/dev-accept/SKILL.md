# dev-accept：集成验收

你只做一件事：把**工单全部 done 的一张 approved spec**变成**一份验收报告，spec 置 done（够条件时 need 置 fulfilled）**。
其余一切（修缺陷、改工单状态、动 spec 正文）一律拒绝。
拒绝不是失礼，是本技能的职责。

## 0. 前置：工作区校验

- 仓库根目录必须存在 `.sdlc/check.sh`（由 /setup-workspace 生成）。
- 不存在 → 停止，告诉用户"本仓库未接入开发流程，先运行 /setup-workspace"。

## 1. 入口门禁（全部通过才继续）

1. **重入判定先行**：docs/acceptance/ 已有 `spec: NNNN` 指向本 spec 的报告：
   `status: draft` → 续接不是重验，从没有结论的场景继续（见 §5）；已是
   `passed` / `rejected` 即终态，不重开报告，停下指路（passed → 已完成；
   rejected → 缺陷走 dev-fix，范围问题走下一轮）。
2. **确定 spec**。用户给了编号 → 用它；没给 → 运行 `.sdlc/check.sh phase` 找
   `approved` 且名下工单已全部 `done` 的 spec：恰一张直接用；多张列候选
   （编号、标题、round）请用户点名，禁止代挑；零张 → 停止转述缺什么：
   "spec NNNN 名下还有 implemented 的工单，先 /dev-ship 交付"，或"没有可验收的
   spec，新需求从 /dev-clarify 起步"。
3. **集成环境校验**：验收对象是集成后的代码；当前分支不是 BASE_REF（config.sh，
   通常 main）→ 停下请用户切回并同步，不在未合并的分支上验收。

## 2. 确定验收范围（执行体薄上下文）

按顺序核对：spec frontmatter 与 `## 验收场景` 节（确认集成级场景清单——这是派发单
的范围，不是走查）→ 关联 need 指针（若有，记下成功标准与 `## 假设与风险` 节位置，
不预读全文）→ 该 spec 名下工单清单（逐一确认 done，只读 frontmatter 状态）。其余
判断依据材料由验收代理按 §3 走查轴清单自行装载——执行体不预装走查材料，也不把工单
Progress、实现交接转交验收代理。串联调用时执行体自带实现上下文，隔离靠验收代理的
独立上下文保证——正因如此执行体不得亲做走查。

然后用三五句话向用户复述：本轮验收哪几条集成级场景、覆盖哪些 FR、由恰一个隔离
验收代理怎样取证据、怎样算通过。有偏差，用户此刻纠正的成本最低。

## 3. 验收纪律：使用方走查轴 + 恰一个隔离验收代理

验收轴是可枚举清单，每条轴 = 轴名 + 判断依据（该轴允许装载的材料）+ 产出节。
当前清单恰一条：

| 轴 | 判断依据（验收代理只装这些） | 产出节 | 回答 |
|----|------------------------------|--------|------|
| 使用方走查轴 | need 全文 + spec「验收场景」节 + design 产物「界面设计」节（述标）与 docs/designs/assets/ 可点原型 + BASE_REF 上的集成后交付物；无述标时补工单「验收标准」节（只取该节） | 场景结果 / 假设验证 / 残余风险 | 使用方能完成任务吗 |

**禁装清单**：工单 Progress、实现交接记录、实现会话上下文——验收代理不读实现
叙事，判断只建立在使用方视角材料上。

- **恰一个隔离验收代理（强制）**：具备子代理原语时，验收执行派发**恰一个**隔离
  验收代理，只装载走查轴判断依据所列材料；派发单随附宿主介质能力声明（验收代理可用哪些原语——工具自述仅限主会话的注明不可用，子代理看不到该自述）；主会话 / 编排会话不得亲做实操走查。
- **无子代理退化（显式降级）**：宿主无子代理原语时，验收执行体单上下文亲做走查，
  报告必须声明降级形态（"单上下文验收，无子代理隔离"）。
- **聚合纪律（义务）**：聚合方只聚合验收代理的报告——分节原样出具，不重验、
  不改写、不代出结论。
- **介质选择规则（按场景操作对象选介质，真实操作取证据）**：Web 界面 → 宿主浏览器操作原语真实打开、点击、输入，以截图与操作记录取证；CLI → 真实终端调用；API/库 → 真实调用取输出；文档 → 打开阅读。浏览器原语缺失 → 降级路径：启动服务 + 脚本 + 截图证据，报告对应行声明降级（【降级】标记）——降级不降标准，不因缺原语拒收。原语以验收代理可用为准：宿主原语仅限主会话（如工具自述 main agent only）时视同缺失走降级，不得由主会话代操作。
- **只跑集成级场景**：`[FR-N | 集成级]` 场景逐条在集成后的代码上按 Given/When/Then 运行；工单级场景已由 dev-implement 在票内核销，不重跑。
- **证据形态 = 实操记录**：「场景结果」每行证据 = 实操记录原样引用（截图路径、操作序列、命令与输出），口径是"使用方能完成任务"；操作类场景只有自动化脚本绿灯、无实操记录不得判过；读代码推定"应该没问题"不算证据，说不出证据不许判过。
- **逐 FR 核销**：FR 核销 = 覆盖它的场景全过；某 FR 无场景 → 停下报告，spec 缺口（validate 本应拦截）不是验收能补的。
- **原型基线三档核销**：FR / 场景关联原型（design「界面设计」节述标 + docs/designs/assets/ 原型）时逐原型场景实操对照——原型场景功能基本完成 = 过；缺失原型场景功能或交付比原型差 = 挂（硬伤）；实现优于原型 = 过（可记亮点）。无述标（无 design 产物或缺「界面设计」节）→ 按工单「验收标准」节核销（只取该节，Progress 仍属禁装清单），报告「场景结果」对应行注明"无述标"——降级不降标准，不因缺述标拒收。
- **问题分级**：硬伤 = 功能缺失、操作行为不符预期、交付比原型差——阻塞，判 rejected；瑕疵 = 不影响使用方完成任务的样式、文案、措辞类偏差——留痕不阻塞 passed，写进「残余风险」与「下一轮建议」。分级由验收代理出具并附证据，报告呈现分级依据；rejected 判据 = 存在硬伤或 `check.sh all` 红灯。
- **全量检查**：`.sdlc/check.sh all` 必须全绿；仓库没定义检查命令 → 本身就是发现，写进报告，不静默跳过。
- **假设验证**：逐条对照 need 的 `## 假设与风险`，写"验证通过 / 证伪 / 本轮未触发"。
- **失败只记录不修复**：场景失败 → 记录步骤、输出、线索，跑完其余再统一定级；验收现场不动代码。

## 4. 出口门禁（全部通过才算完）

1. **落盘前用 Skill 工具装载 ref-writing**，报告写法以它为准。
2. 运行 `.sdlc/check.sh claim acceptance <slug> spec <spec-ID>` 取号落盘
   （`round` = spec 的 round，slug 用 ASCII 小写短横线）——返回占位文件路径，号由
   入口原子分配、全历史唯一，父为 spec（知识档）自动带 `spec<父ID>-` 谱系前缀；
   用下面的固定模板写正文覆盖占位文件（frontmatter `id` 填文件名的 ID 段），跑
   `.sdlc/check.sh validate <占位路径>` 必须通过，再跑 `publish <占位路径>`。
3. **分级有判据、判定按判据机械执行，不问人**：无硬伤且 `check.sh all` 全绿 → `status: passed`（瑕疵留痕不阻塞）；存在硬伤或检查有红灯 → `status: rejected`，硬伤与范围问题如实写进报告。判定权：判定从不问人，无人值守运行（如 dev-execute 收口串联）下 passed/rejected 同样由 AI 按本分级判据机械作出；need 置 fulfilled 不属判定，永远停点留人（见本节第 4 项末段）。报告状态变更的提交用 `[trivial]`——流程状态落盘，不是绕门禁（dev-retro 可审计）。
4. **passed 出口（固定序列，顺序不可换）**：
   1. **蒸馏四路**（各落点过 validate）——① need「假设与风险」节逐条标注验证结果（验证通过 / 证伪 / 本轮未触发，以报告「假设验证」为准），并把残余风险与「下一轮建议」及其依据补写进该节：下一轮建议与残余风险先折回 need，是清扫的前置（E3 边界），未折回不得清扫；② spec「验收场景」按实现中发现的实际边界行为修订（仅 passed 允许）；③ 有架构分量的决策新立 ADR（status: accepted）；④ 模式学习追加进 CODING_STANDARDS.md 索引的 standards/。
   2. **清扫**——删除该 spec 名下全部 tickets、overviews、reviews 与本次验收报告文件（含本次报告；"名下"关系与 validate 残留校验同一定义；tracker 投影不回删，映射文件保留）。
   3. **置 done**——spec frontmatter `status` 改 `done`、追加 `done: <今日>`，validate 必须通过（done 名下过程档残留必须为零），publish 照旧。
   4. **原子提交**——蒸馏编辑 + 清扫删除 + 置 done 合为恰一个 `[trivial]` 提交，不产生中间态提交。

   序列完成后处理 need（有 need 时）——**fulfilled 门停点留人，无人值守不豁免**：成功标准逐条核销，且残余风险为空或逐条经用户显式接受（沉默不算接受残余风险）→ need `status` 改 `fulfilled`、追加 `fulfilled: <今日>`；存在未核销标准或未接受风险 → **抛决策问题："开不开下一轮？"**，默认建议按残余风险性质给（建议开 → 下一轮从 /dev-spec 起步，round 递增，范围 = 残余风险；用户显式确认才开轮）。不开 → need 保持原状，说明差距，停。
5. **rejected 出口**：缺陷指路 dev-fix 开 fix 票，dev-fix 未实现 → 停下说明
   "缺陷清单已写进验收报告 NNNN，等 dev-fix 实现后开票"；范围问题确认已写进
   `## 下一轮建议`。停，不自动开轮。

```markdown
---
id: <ID 段，YYYYMMDD-4hex>
status: draft
spec: 0001
round: 1
created: <date>
---
# <ID 段>: <一句话概括验收对象>
## 场景结果
验收形态：<恰一个隔离验收代理 | 单上下文降级>
（逐条：场景 / FR / 证据（实操记录：截图路径、操作序列、命令与输出原样引用）/ 分级：硬伤 | 瑕疵 | — / 结论：过 | 挂；降级行带【降级】声明，无述标行注明"无述标"）
## 假设验证
（逐条：need 假设 / 验证结果：验证通过 | 证伪 | 本轮未触发）
## 残余风险
（无就写"无"；有则逐条：风险 / 影响 / 是否阻塞——瑕疵逐条留痕于此，不阻塞 passed）
## 下一轮建议
（范围问题、值得再投入的方向；无就写"无"）
```

## 5. 中断与交接

会话可能在任何时刻结束。停下前（等用户决策、上下文将尽、被卡住）：先把报告
以 `status: draft` 落盘——已跑场景的结果与证据全部写入，未跑的标"未执行"。
重入从 §1.1 续接：盘上的 draft 就是进度，已出结论的场景不重跑。状态在盘上，
不在对话里。

## 禁止事项（任何时候）

- 改工单的 status（工单生命周期归 dev-ship）。rejected 时改 spec 正文同样禁止——
  验收场景与实现不符是 rejected 的证据，不是现场改场景的理由；passed 出口蒸馏
  ②（按实际边界行为修订「验收场景」）是禁改 spec 正文的唯一例外。
- 场景没跑就凭读代码写"通过"。
- 操作类场景仅凭自动化脚本绿灯判过——判过须有实操记录。
- 具备子代理原语时主会话 / 编排会话亲做实操走查，或派发多于一个验收代理，或向验收代理装载禁装清单材料（工单 Progress、实现交接记录、实现会话上下文）。
- 在验收中顺手修缺陷——修是 dev-fix / 新工单的事。
- 跳过 `.sdlc/check.sh all`，或检查有红灯时写出"全绿"。
- 为通过而弱化结论、删失败场景，或把硬伤降级为瑕疵。
- 未满足末轮条件就把 need 置 fulfilled——沉默或"都行"不算接受风险。
