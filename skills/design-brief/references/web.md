# Web 对象：角色画像与场景要点

design-brief 对象路由选中本分册后加载。适用：浏览器访问的界面——后台、控制台、
官网、SaaS 工作台。核心动作：按角色画像定三要素口径，约束落在"屏内要求"上，
不落版面稿。

## 角色画像（约束以角色为单位逐个落）

- **后台操作员**：高频数据处理者——查得快、录得快、批量快。约束重心：
  高密度一屏多看数据、键盘流、常用操作少跳转。
- **管理者 / 审阅者**：看趋势、做决定、批内容。约束重心：总览与明细分离
  （先全局后下钻）、异常突出、审批动作一步可达。
- **外部访客**：低频获取者——看懂、找到、走完单条路径。约束重心：
  单页单任务、引导线性、术语少。

## 场景要点

- 列表 + 详情：数据角色的高频主场，约束写清列表列的主次与详情唤起方式的要求。
- 表单录入 / 审批流：写清必填信息优先级与提交流的步数要求。
- 仪表盘总览：写清先看什么（健康度/趋势）再看什么（明细）的优先级顺序。
- 多标签并行：操作员常开多个单据——约束可要求"状态在外层可见"。

## 三要素落法（Web 口径）

- 信息优先级：落成屏内分区要求——主区放什么、侧区放什么、什么可折叠；
  禁止写成"左栏 240px"。
- 密度要求：落成可核口径——数据表一屏可见行数量级、单屏并排信息块数、
  分栏意图（高密度多列 / 低密度大块）。
- 关键操作路径：落成任务步数与页面顺序——高频任务几步内完成、
  路径上必现的信息与动作。
- 触屏线索：若 Web 要兼顾移动访问，把"谁在什么场景用手机访问"写成约束
  （供 design-ui 做移动适配决策）；断点与适配方案本身不写。

## 好 / 坏对照

- 好："操作员一屏可见 ≥20 行设备数据，异常行优先于正常行被看见。"
- 坏："用表格展示，左边放筛选器。"——这是版面稿，归 design-ui。

## 自查口令

每个角色的三要素都指得回其使用场景吗？密度落成了可核口径吗？
路径写的是任务步数还是页面草图？
