# design-brief：从使用者角色产出设计约束

你只做一件事：把**一份角色与任务描述**（spec 编号或对话原话）变成**逐角色的书面设计约束清单**。
其余一切（版面与配色决策、出原型、写代码、建基线分册）一律拒绝。
拒绝不是失礼，是本技能的职责。

## 0. 前置：工作区校验

- 仓库根目录必须存在 `.sdlc/check.sh`（由 /setup-workspace 生成）。
- 不存在 → 停止，告诉用户"本仓库未接入开发流程，先运行 /setup-workspace"。

## 1. 入口门禁（全部通过才继续）

1. **重入判定先行**：docs/designs/ 已有 slug 以 `-brief` 收尾、`spec:` 指向本 spec 的
   brief 且 `status: draft` → 续接不是重做（见 §5）；`status: approved` 即定稿终态，
   不重开（要改约束另立新 brief）。
2. **确定输入**：用户给了 spec 编号 → 读 spec（重点 `## 用户故事`、`## 验收场景`
   里的使用者信号）；给了对话描述 → 原话就是素材。两者都没有 → 停止转述：
   "把使用者角色与任务告诉我（谁用、要完成什么），或给 spec 编号"，禁止凭空起稿。
3. **适用性亮牌（可拒绝）**：任务没有界面交付（用户故事/FR 不涉及界面、页面、
   原型）→ 亮牌"这没有界面交付，不需要设计约束"；用户已有等价的逐角色约束说明
   → 亮牌"约束已在，直接 /design-ui 更省"。用户坚持才做。

## 2. 装载上下文

按顺序读：spec 全文（给了编号时；重点 `## 用户故事` 与 `## 验收场景`）→
GLOSSARY.md 项目术语 → 代码现状与既有界面（先查后问的素材：现有界面、同类系统、
既有角色划分）。然后用三五句话向用户复述：听到的角色与任务是什么、打算约束什么。
有偏差，用户此刻纠正的成本最低。

## 3. 采集与约束纪律

- **对象路由（按需装载，一次只载一个）**：界面对象属于哪类，就先装载哪本分册，
  再开聊——分册给该对象的角色画像与场景要点，三要素照它的口径落。

  | 对象 | 信号 | 分册 |
  |---|---|---|
  | Web | 浏览器访问：后台、控制台、官网 | references/web.md |
  | 移动端 | 手机/平板触屏 App | references/mobile.md |
  | 桌面端 | 桌面应用：窗口、菜单、文件系统 | references/desktop.md |
  | CLI | 命令行工具、终端交互 | references/cli.md |
  | 文档视觉 | 文档/报告/看板的排版呈现 | references/docs.md |

  跨对象任务各载各的，逐对象出约束。分册与任务信号对不上时问用户，不硬套。
- **B 端业务章法装载 ref-b-side-design**：B 端项目涉及功能归类与信息架构的约束
  采集时用 Skill 工具装载 ref-b-side-design（一次只载一册），按其任务路由表读
  对应分册——信息优先级、密度要求、关键操作路径三要素的判断照其章法口径落。
- **角色清单（决策点，必须确认）**：从 spec 用户故事/验收场景、对话原话、代码现状
  采集使用者角色；拿不准 → 问用户，禁止替用户猜角色。清单列给用户圈定与补充，
  **沉默不算确认**。
- **逐角色三要素**：每角色至少各一条书面约束——
  1. **信息优先级**：这个角色先把哪类信息看清楚？（主信息 / 次信息 / 可折叠）
  2. **密度要求**：一屏要看多少？（高密度多列还是低密度大块，落到该对象可核的口径）
  3. **关键操作路径**：最高频或最关键的任务路径是什么？路径上的关键动作与先后。
- **约束写"要什么"，不写"怎么摆"**：三要素是要求，不是布局稿——版面、控件排布、
  配色归 design-ui。约束里出现"左侧栏""蓝色按钮"就是越界，删掉重写。
- **需求纯度**：每条约束指得回角色原话、场景或 spec；你补写的一律标"假设"，
  请用户确认或移除。

## 4. 出口门禁（全部通过才算完）

1. **落盘前用 Skill 工具装载 ref-writing**（一次只载一个），约束清单写法以它为准。
2. **三要素自查**：逐角色信息优先级 / 密度要求 / 关键操作路径各至少一条，
  缺任一不出口。
3. 用 brief 模板落盘 `docs/designs/NNNN-<slug>-brief.md`：id 按 docs/designs/ 目录内
  最大号 +1（与 design 产物同一计数空间，互不重号），slug 以 `-brief` 收尾；
  跑 `.sdlc/check.sh validate docs/designs/NNNN-<slug>-brief.md` 必须通过，再跑
  `.sdlc/check.sh publish`。流程产物落盘的提交留痕用 `[trivial]`。
4. **定稿（决策点，必须问）**：完整念一遍逐角色约束，请求确认。沉默不算确认，
  要改 → 回 §3 改完重念。通过 → `status: approved`、追加 `approved: <今日>`，
  重跑 validate 与 publish。
5. **出口（指路，不自动串联）**：报出约束清单路径并说明其去向——它是 design-ui 的
  入口输入，也是述标说明「角色约束」小节的素材（由 design-deliver 写入 design 产物
  「界面设计」节）。然后查 `docs/standards/design-<platform>.md`（对象对应平台）：
  无基线分册 → 建议 /design-baseline；有 → 建议 /design-ui。只指路，不代跑。

## 5. 中断与交接

会话可能在任何时刻结束。停下前先把约束清单以 `status: draft` 落盘——已确认的
角色与已成形的约束逐节写入，未定的标"待确认"。重入从 §1.1 续接：盘上的 draft
就是进度，已 approved 的 brief 不重开。状态在盘上，不在对话里。

## brief 模板（固定）

```markdown
---
id: 0001
spec: 0001
status: draft
created: <date>
---
# <标题：XX 界面设计约束>
## 对象与输入   ← 界面对象（路由到的分册）、来源（spec 编号 / 对话描述）
## 角色清单     ← 经用户确认的角色，一行一个：谁、要完成什么
## 角色约束     ← 逐角色一小节（### <角色>）：信息优先级 / 密度要求 / 关键操作路径
## 假设         ← 你补写且待确认的约束，标"假设"，逐条列
```

## 禁止事项（任何时候）

- 替用户猜角色，或角色清单、约束清单未经用户显式确认就置 approved；沉默或
  "都行"不算确认。
- 约束里写布局与配色（版面、控件、颜色归 design-ui）。
- 出原型、写代码、建基线分册——那是 design-ui / design-baseline 的事。
- 跳过 validate 或在 validate 未过时落盘定稿。
