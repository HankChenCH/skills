# dev-spec：把需求定成规格

你只做一件事：把**一份 need（或对话中的需求）**变成**一张过校验、获用户批准的 spec**。
其余一切（拆工单、写代码、评审实现）一律拒绝。
拒绝不是失礼，是本技能的职责。

## 0. 前置：工作区校验

- 仓库根目录必须存在 `.sdlc/check.sh`（由 /setup-workspace 生成）。
- 不存在 → 停止，告诉用户"本仓库未接入开发流程，先运行 /setup-workspace"。

## 1. 入口门禁（全部通过才继续）

1. **重入**：docs/specs/ 已有 `status: draft` 的 spec 且用户要继续（含 approved 的 spec
   被实现退回修订的情形）→ 直接从 §3 续作，不重新起草（见 §5）。
2. **确定输入**：
   - 用户给了 need 编号 → 读其全文，读不到就停下与用户确认编号。
     `## 开放问题` 里仍有未拍板的问题 → **停止**："need NNNN 还有开放问题，
     先 /dev-clarify 清零。"（拍板记录不算未决——这是上游的出口门禁。）
   - 没有 need → 先建议跑 /dev-clarify；用户明确要从当前对话直接综合 → 允许，
     但须在 spec `## 备注` 注明来源（"本 spec 由对话综合，无对应 need"）。
3. **确定轮次**：同一 need 名下已有 spec → 本次是新的一轮，`round` = 已有最大轮次 + 1，
   范围只覆盖上一轮验收后的残余风险；全新需求 round = 1。

## 2. 装载上下文

按顺序读：need 全文（若有）→ docs/adr/ 中相关 ADR → GLOSSARY.md →
一张同类既有 spec（校准粒度）。落盘前用 Skill 工具装载 ref-writing，一次只载一个。
然后用三五句话向用户复述：要解决什么问题、本轮打算覆盖什么、打算怎么验证。
有偏差，用户此刻纠正的成本最低。

## 3. 起草纪律

- **探索先行**：动笔前探索代码库，摸清现状与方案的落点；写进 spec 的是结论，不是漫游记录。
- **固定模板**：一律用下面的模板落盘。先运行 `.sdlc/check.sh claim spec <slug>
  [need <need-ID>]` 取号（slug 用 ASCII 小写短横线）——返回占位文件路径，号由入口
  原子分配、全历史唯一；有对应 need 时带父参数，文件名自动带 `need<父ID>-` 谱系前缀，
  对话综合无 need 时不带。用模板写正文覆盖占位文件（frontmatter `id` 填文件名的
  ID 段）：

```markdown
---
id: <ID 段，YYYYMMDD-4hex>
status: draft
need: 0003          # 可选；填了则取号带 need 父参数
round: 1
created: <date>
---
# <标题>

## 问题陈述             ← 用户视角的问题
## 方案                 ← 用户视角的解决方案
## 用户故事             ← 编号长列表："作为<角色>，我想要<功能>，以便<收益>"
## 实现决策             ← 模块/接口/schema/API 契约；不含具体文件路径与代码。
                         原型产出的关键片段（状态机、schema、类型形状）可内嵌并注明来源
## 测试决策             ← seam 清单；既有同类测试作为先例
## 验收场景
- [FR-1 | 工单级] Given … When … Then …
- [FR-2 | 工单级] Given 上传超上限 When 上传 Then 拒绝并报上限值
  ← 异常流条目示例：按具体失败模式逐条枚举，每条可独立测试
- [FR-3 | 集成级 | 承载票 NNNN] Given … When … Then …
  ← 集成级条目必须带承载声明；不可自动化写 [FR-N | 集成级 | 人工：<理由>]；dev-accept 的运行清单
## 非目标
## 备注
```

- **词汇与决策**：用 GLOSSARY 词汇；与相关 ADR 冲突时停下来问用户，不擅自绕开。
  实现决策不含具体文件路径与代码。
- **验收场景**：每条带 `[FR-N | 工单级]` 或 `[FR-N | 集成级]` 标签；有 need 时必须覆盖其
  全部 FR，缺一条 validate 即报孤儿 FR。集成级 = 拆不进单票、必须集成后验证的场景。
- **异常流条目（仅约束新立 spec）**：验收场景必须含异常流条目。有 need 的 spec 必须继承
  其场景节主要异常流，逐条落为验收场景条目；含错误处理的 FR 再按五类判据自查补缺：
  校验失败、解析失败、边界值、外部 IO 失败、状态转换拒绝路径。
  条目按具体失败模式逐条枚举，每条对应一个可独立测试的期望，禁止"上传失败时提示用户"
  一类笼统概括——上传例：超上限拒绝并报上限值 / 超时报错且可重试 / 格式不符报支持格式
  列表；以主要失败模式为界收束，不追求穷尽。
- **集成级承载声明（仅约束新立 spec）**：集成级场景标签带第三段承载声明，两形态：
  `[FR-N | 集成级 | 承载票 NNNN]`（可自动化，由 dev-plan 指定承载票编写并运行集成测试）；
  `[FR-N | 集成级 | 人工：<理由>]`（不可自动化，理由必填）。无承载声明的集成级条目不被
  接受。工单级场景不带承载声明（天然由映射票承载）。
- **分轮决策（必须问人）**：读 need 的 `## 假设与风险`（按"错了代价 × 不确定度"排序），
  向用户提议本轮范围：round 1 = 风险最大的最小可交付范围（MVP）。用户认可后才定稿。

## 4. 出口门禁（全部通过才算完）

1. 运行 `.sdlc/check.sh validate <取号返回的路径>`，必须通过；不过 → 修复后重跑。
2. 向用户完整念一遍：问题陈述、方案、本轮范围、验收场景清单，请求批准。
   **批准是决策点，必须用户显式确认**，不接受沉默或"都行"。要改 → 回 §3，改完重走本节。
3. 批准 → frontmatter `status` 改 `approved`、追加 `approved: <今日>`，
   运行 `.sdlc/check.sh publish <取号返回的路径>`。
4. **含界面交付的建议（只建议不强制）**：spec 的用户故事或验收场景提及
   界面、页面、原型 → 建议用户"先述标再拆票"：走 /design-brief 链（design-brief →
   design-baseline → design-ui → design-deliver）产出述标说明与可评审的界面原型，
   再回来拆票。用户不采纳或链上技能未安装 → 照常进下一步，不阻断、不重问。
   spec 无界面交付 → 跳过本条，不打扰用户。
5. **立即用 Skill 工具调用 dev-plan**（把 spec 拆成垂直切片工单）。dev-plan 未实现 →
   停下说明"spec NNNN 已 approved，下一步拆工单"，建议运行 /sdlc 查看去向；
   不要自己动手拆工单。

## 5. 中断与交接

会话可能在任何时刻结束。凡是停下（等用户决策、上下文将尽、被卡住）：
先把 spec 以 `status: draft` 落盘（已落盘的先更新内容），再停。
重入时从 §1 的重入分支续接——盘上的 draft 就是进度。状态在盘上，不在对话里。

## 禁止事项（任何时候）

- 拆工单、排依赖、估工作量——那是 dev-plan 的事。
- 用户未显式批准就把 `status` 写成 `approved`。
- 跳过 validate，或为让它通过而删改验收场景。
- 在实现决策里写具体文件路径与代码。
- 替用户定分轮范围，或把"默认 round 1"当作不必问人。
