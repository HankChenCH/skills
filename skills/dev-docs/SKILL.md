# dev-docs：面向人的文档维护

你只做一件事：让**面向人的文档**与**仓库实际行为**一致。
其余一切（改流程产物、顺手修代码、无核验地写"应该如此"）一律拒绝。
拒绝不是失礼，是本技能的职责。

## 0. 前置：工作区校验

- 仓库根目录必须存在 `.sdlc/check.sh`（由 /setup-workspace 生成）。
- 不存在 → 停止："本仓库未接入开发流程，先运行 /setup-workspace"，不改任何文档。

## 1. 入口门禁（全部通过才继续）

1. **重入判定先行**：git status 有未提交的文档改动 → 上轮做了一半：
   列出改动文件，问用户"续接还是放弃"，续接则从对应文档继续。
   与本任务无关的改动如实列出，不碰。
2. **范围判定**：请求命中的文件必须是面向人的文档（README、用户文档、
   API 文档等给人读的文档）。以下不在范围内，只指路不代写：
   流程产物（need/spec/design/ticket/review/acceptance/research/retro/adr）
   转对应技能，写需求转 /dev-clarify 或 /dev-spec；METHOD.md 归 /setup-workspace；
   CHANGELOG 归 /dev-release；源码内注释与 docstring 属源码文件，改动走工单。
3. **变更范围可枚举**：说不出要改哪些文件就不动笔——先读仓库把范围找出来；
   找不出来，把候选文件列给用户问。

## 2. 装载上下文与决策点①：变更清单确认（动笔前必问）

读：请求涉及的现有文档全文 → 文档所描述行为对应的实现与测试。
然后完整念一遍变更清单——改哪些文件、每处改什么、依据是什么
（哪条命令实测 / 哪个实现文件 / 哪个测试），请求确认。
沉默不算确认，要改回本节。

## 3. 一致性纪律（先核验后落笔）

- **行为断言逐条核验**：写进文档的每条命令、参数、输出、路径、限制，
  按三档核验并在变更清单里留档——实跑（跑了，结果如何）/
  读实现（哪个文件哪段）/ 测试为证（哪个测试名）。
  三档都够不着 → 不写"应该如此"，如实标注"未核验"，问用户写不写。
- **文档与实现冲突**：以实际行为为准改文档是默认建议，但改哪边必须问人。
  用户认定是代码错了 → 不改文档，转 /dev-fix 开票，修完再回头对齐——
  文档不将就错误行为。
- **术语一律来自 GLOSSARY**，首次出现给定义；自造词先登记进术语表再使用。
- 例子优先，命令写到可复制执行（细则见 ref-writing，落盘前装载）。

## 4. 出口门禁（全部通过才算完）

1. 落盘前用 Skill 工具装载 ref-writing，一次只载一个。
2. 按批准的变更清单落盘，然后过一遍自查口令：哪一句要问作者才能懂？
   每个形容词换成事实了吗？命令复制出来能执行吗？术语在 GLOSSARY 里找得到吗？
3. 提交留痕：纯文档改动用 `[trivial]` 并写明豁免理由；在办工单同批交付
   挂 `[#NNNN]`。只 add 本任务改动的文件，工作树上无关改动原样保留。
4. **出口（指路，不自动串联）**：报告三件——改了哪些文档、每处核验方式与
   结果、未核验项清单——然后指路：行为有缺陷 /dev-fix，要发布 /dev-release，
   要沉淀 /dev-retro。不做完沉默等指令。

## 5. 中断与交接

已改未提交的文档就是断点（git status 可见），重入判定先行即指此；
未落笔的意图不构成状态。
状态在盘上，不在对话里。

## 禁止事项（任何时候）

- 无核验写行为断言——"应该""通常"式措辞进不了文档。
- 文档与代码冲突时默默选边——改文档还是改代码必须问人。
- 改流程产物、METHOD.md、CHANGELOG、源码文件（含 docstring）——只指路，不代写。
- 顺手修代码——回 /dev-fix 开票。
- 提交时 add 本任务之外的文件。
