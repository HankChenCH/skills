# ref-review：什么是好的评审

评审的价值 = 拦住的真问题 − 制造的噪音。下面每条规则都为这个差值服务。

## 行为规则

1. **只评 diff 范围内的事。** 范围外的真问题（如相邻模块的既有缺陷）记入报告的
   "范围外备注"，不算 finding——顺手评审是范围蔓延的开始。
2. **每条 finding 必须可执行**：`文件:行` + 怎么改 + 为什么。缺"怎么改"的是抱怨，
   不是评审意见。
3. **每条 finding 定级：阻断 / 建议。**
   - 阻断：违反已文档化的标准、正确性 / 安全 / 数据风险、偏离 spec。
   - 建议：改了更好，不改不算错。
4. **区分"违反标准"与"个人品味"**：判断依据必须写得出——出自 CODING_STANDARDS.md
   或下方坏味道基线；写不出依据的，降为建议或不提。品味差异永远不是阻断。
5. **优先级**：repo 已文档化的标准 > 本基线；lint / 编译器已强制的跳过——工具管住的
   事不值得人再说一遍。

## finding 范例（好 / 差对照）

差："这里抽象得不好，建议重构。"——不可执行，无依据，无法定级。

好："`services/order.ts:42`——金额计算在 checkout 与 refund 各写了一份（重复代码），
建议抽 `calcTotal()` 供两处调用；两处口径不一致会产生对账 bug。（阻断）"

差："变量名 `data` 不好。"——品味，无信息量。

好："`parse.ts:8`——`data` 实际是"解析失败的行集合"，下一个人会误当原始输入用；
建议改 `failedRows`。（建议）"

## 代码坏味道基线（Fowler《重构》；每条：是什么 → 怎么修）

| 坏味道 | 是什么 → 怎么修 |
|---|---|
| 神秘命名 | 名字要读完代码才懂 → 改名，让名字说出意图 |
| 重复代码 | 同样逻辑出现两处以上 → 收敛到一处（函数 / 模块） |
| 过长函数 | 一屏放不下、干多件事 → 按意图拆小函数，用函数名当注释 |
| 过长参数列表 | 参数一长串、顺序易错 → 收拢成对象 |
| 发散式变化 | 一个类因多种不相关的原因被反复改 → 按变化方向拆分职责 |
| 霰弹式修改 | 一个小改动要同时碰很多文件 → 把总是一起变的东西聚到一起 |
| 依恋情结 | 函数对别的模块的数据比对自家的亲 → 把函数搬去和数据待在一起 |
| 数据泥团 | 几个字段 / 参数总是一起出现 → 收拢成对象 |
| 基本类型偏执 | 领域概念用裸 string / number 装 → 定义领域类型，顺带收拢校验 |
| 重复 switch | 同一判断散布多处，加分支要全改 → 多态或查表收敛到一处 |
| 投机泛化 | 为想象中的未来加的抽象 → 删掉，真需要时再建 |
| 死代码 / 注释掉的代码 | 不再被执行的逻辑 → 直接删，git 记得它 |

## 汇总纪律

- 标准轴 / Spec 轴各自独立出具 findings，不合并重排、不互相稀释（两轴定义在 dev-review）。
- 汇总只报数字：各轴阻断数、建议数。评审结论由阻断数决定，不由评语长度决定。
