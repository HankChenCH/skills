# ref-writing：什么是人类可理解的文档

总标准只有一条：**读者不在你的对话里。** 半年后的你、协作者、新会话的 AI 读这份文档时，
没有产出它的那次对话——文档必须靠自身站住：断言可验证、例子可执行、术语有定义。
以下每条都是它的分解，need / spec / 调研报告 / 验收报告 / 用户文档共用同一份标准。

## 规则

1. **平实具体**：写事实与行为，不写形容。"大幅""显著""流畅"是读者的税——每处都要能
   换成数字、命令或文件路径，换不出来就删掉。
2. **例子优先**：能用一个例子说清的，不用一段抽象；抽象规则后面必须紧跟例子。
   读者从例子归纳比从定义演绎快——文档为读者省时间，不为作者省力气。
3. **一段一个观点**：段首句就是该段的观点，其余句子只做支撑；发现第二句在讲另一件事，
   拆段。并列事实用列表，不堆成长句串。
4. **术语一律来自 GLOSSARY，首次出现给定义**：用词与 GLOSSARY.md 一致（工单、
   验收场景、工单级 / 集成级、frontier…）；自造词要么先登记进术语表，要么别用；
   术语首次出现给一句话定义，此后只用该词。
5. **禁空洞抽象词，写可验证的陈述**："提升效率""优化体验""增强健壮性"没法验证——
   改写成：什么对象、什么行为、什么指标、从多少到多少、怎么测的。
6. **给数字、给命令、给文件名**：证据的具体形态。命令写到可复制执行，文件写到路径，
   数字带单位与测量来源；给不出来，说明断言还没落到底——先补证据，再写文档。

## 范例（好 / 差对照）

差："支持批量导入，极大提升用户处理数据的效率，体验更加流畅。"

好："支持单次最多 5000 行的 CSV 导入（`/import ledger.csv`），超限时报错并列出行数；
5000 行导入耗时 ≤ 2s（验收场景 FR-3）。"

差句没法验证——验收时说不出"通过"长什么样；好句有上限、有命令、有指标、有 FR 追溯，
dev-plan 能直接把它映射进工单的验收标准。

差（术语未定义，读者只能追问作者）："受水位线影响，本轮只推进一个阶段。"

好："上下文 token 水位线（会话上下文 token 用量占模型窗口的百分比）到黄档（30%–50%），
本轮只推进单阶段，出口不自动串联下一技能。"

## 自查口令（落盘前过一遍）

拿走产出它的对话，只读这份文档：哪一句要问作者才能懂？每个形容词换成数字或事实了吗？
每个术语在 GLOSSARY 里找得到吗？命令复制出来能执行吗？
