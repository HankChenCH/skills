# dev-execute：整 spec 编排运行

你只做一件事：把**一张已批准 spec 名下的全部工票**变成**按依赖序实现、评审、合回并预演通过的运行**。
其余一切（spec 未 approved、点名单张工票、范围外话题）一律拒绝。
拒绝不是失礼，是本技能的职责。

## 0. 前置：工作区校验

- 仓库根目录必须存在 `.sdlc/check.sh`（由 /setup-workspace 生成）。
- 不存在 → 停止："本仓库未接入开发流程，先运行 /setup-workspace"，不做任何编排。

## 1. 入口门禁（全部通过才继续）

1. **确定编排对象**。入参必须是**一张 spec**（编号或路径）。用户点的是单张工票 →
   拒绝："单票实现请用 /dev-implement"；没点名 → 运行 `.sdlc/check.sh phase` 列出
   全部 `status: approved` 的 spec 供用户选择，禁止猜测或自行挑一张。
2. **校验 spec**：存在且 `status: approved`。仍是 draft → 拒绝并指路
   "/dev-spec 完成批准"；已 done → 拒绝并指路 /dev-accept。名下没有任何工票 →
   拒绝并指路 /dev-plan。名下工票已全部 done → 拒绝："无可运行工票，走 /dev-accept"。
3. **重入判定**：`git worktree list` 已发现该 spec 的运行分支 worktree → 运行已在
   进行中，跳过建图与开工确认，直接按 §7 续接（断点推导方法见 run-mechanics §5）。

## 2. 装载上下文

按顺序读：spec 全文 → 名下每张工票全文 → GLOSSARY.md（术语"运行""运行依赖顺序图"）
→ CODING_STANDARDS.md。再用 Skill 工具装载三个参考：ref-implementation、
ref-testing、ref-git-commit——它们随派发传给实现子代理，合回信息规范也以
ref-git-commit 为准。

然后用三五句话向用户复述：这张 spec 交付什么、共几张票几层并行、打算怎么推进。
有偏差，用户此刻纠正的成本最低。

## 3. 建运行依赖顺序图，请求开工确认

1. 对 spec 名下全部工票按 blocked-by 拓扑分层建图（算法与辅助命令见
   run-mechanics §2）：同层票无依赖可并行，层间 blocked-by 边串行；标注关键路径
   （最长票链）；开工前已 done 的票列图外"已完成"；被 spec 外工票阻塞且未完成的票
   标注"外部阻塞"，若因此全图无法开工 → 停下报告，不进入运行。
2. 向用户展示分层图，并请求**开工确认**：将建立运行分支与运行 worktree、每票一个
   票分支与票 worktree（命名与放置约定见 run-mechanics §1，命令见 §3/§4）、
   同层并行派发。决策点必须问人，带默认建议（建议：按图开工）。
3. **未确认不创建任何 worktree**。用户拒绝或要求调整 → 中止，零写入退出；
   要调整分层或拆票 → 指路 /dev-plan（编排不拆票）。

## 4. 运行建立

- 建运行分支与运行 worktree（命令与核对清单见 run-mechanics §3）。
- 建立后核对：`git worktree list` 出现运行 worktree 与运行分支；主工作区仍停留
  主分支且 `git status` 干净。任一不满足 → 停下报告，不派发任何票。

## 5. 流水线调度：实现 → 评审 → 合回 → 预演

按票推进，层屏障取消：运行依赖顺序图的"层"只作展示与依赖满足判定视图（同层票
无依赖可并行，层间 blocked-by 边决定派发与合回时机），任何一票走完一步即推进
下一步，不等同层其余票。

1. **派发实现**：blocked-by 全部满足（依赖票已合回或 done）的票，从运行分支切出
   票分支与票 worktree（细则见 run-mechanics §4），派一个子代理实现，子代理执行
   dev-implement 纪律全文（红绿循环、只做工单内的事、Progress 交接）。派发时机：
   开工后先派第 1 层，此后每次合回预演绿即重查图、派发新满足依赖的票。宿主支持
   后台派发时用后台派发——完成通知驱动后续编排，不轮询，主会话派发后可随时响应
   用户输入；不支持则同步派发，语义不变。并行度默认上限 4，调用参数可覆盖，
   超出分批。
2. **编排评审**：票 implemented（后台派发即完成通知到达时；同步派发即返回时）
   立即在该票 worktree 内用 Skill 工具调 dev-review，**先行评审，不等同层其余票**。
   **编排模式入参**："编排评审：工单 <NNNN>，基线 <运行分支>"。评审报告按入参
   填报：`branch` 记该票分支、`tickets` 记该票（pre-push 在运行分支按覆盖面校验，
   契约见蓝图 §11.7）。评审在票 worktree 内进行、不触碰运行分支，与在办票互不
   干扰。评审出口止于 approved——编排模式下它不准备 PR、不调 dev-ship。有阻断 →
   按评审的决策问题处置（机械问题修后重审，不停运行；设计级阻断 → §8 异常流）。
3. **机械合回**：票 approved 且 blocked-by 满足 → 合回运行分支，不设人工门。合回
   前完成两件预备：物化同步（翻转副本与评审报告从票 worktree 同步到运行
   worktree）+ merge-tree 干跑预检序（同层候选票取干跑无冲突者先合，候选序全部
   冲突才停机问人；预检只排序、不解冲突内容）——细则见 run-mechanics §7。同层票
   在各自派发时基线上实现，合回后不重放基线（改动面互斥保证合回干净）。合回冲突
   → §8 异常流。
4. **预演**：每次合回后在运行 worktree 跑 `check.sh all`，加上 spec 验收场景中
   已有自动化承载的集成级测试（细则见 run-mechanics §6）。绿灯才合回下一票、
   派发后续票；红灯 → §8 异常流。
5. 全部票 implemented 且预演绿 → 运行全绿，随即自动转入 §6 收口（逐票终态与
   预演记录并出入口报告，见 §6.7）。

## 6. 收口链：一次 PR → 合并确认 → 票 done → 清理 → 出口报告

运行全绿后自动进入，人交互只有合并确认这一次；操作细则见 run-mechanics §8。
逐票评审出口止于 approved（§5.2），任何 PR 准备动作都只发生在本节。

1. **准备 PR**：在运行 worktree 重跑 `.sdlc/check.sh all` 作收口门禁（证据必须
   新鲜），按 dev-ship 前半三节模板写 PR 正文：`## Summary`（运行视图：几层几票、
   逐票一句话）/ `## Evidence`（收口门禁输出 + 逐票评审报告编号）/ `## Merge
   Danger`（单向门判定 + 影响半径）。落点跟 TRACKER 走（dev-ship §3 同款）：
   平台建 PR；local 则正文作为合并清单在会话中完整呈现，不让用户盲批。
2. **pre-push**：`.sdlc/check.sh pre-push` 必须通过——它机械校验运行分支领先
   提交中全部 implemented 票都有 approved 评审覆盖。不过 → §8 异常流。
3. **合并确认（单向门，必须问人）**：一次问清 ① 合并方式（merge commit /
   squash / fast-forward，跟仓库历史约定给建议）；② 是否打 tag（默认不打——
   发布点 tag 的语义化版本与 CHANGELOG 归 dev-release）。**用户显式确认才执行，
   沉默或"都行"不算。** 拒绝 → 运行停在收口，状态在盘上（§7 续接），不强推。
4. **执行合并**：dev-ship §4.2 同款——平台 PR 按确认方式在平台合并；本地在
   主工作区（BASE_REF）合并运行分支并 push（细则见 run-mechanics §8.3）。
5. **票 → done**：合并后把本 spec 名下全部工票 `status` 改为 `done` 并追加
   `done: <今日>`，状态变更**落盘不提交**（ADR 0003 物化语义：过程档无可提交
   内容，validate 通过即终态；审计链 = tracker 投影 + 源码 `[#NNNN]` 引用 + 盘上
   状态，细则见 run-mechanics §8.4）。
6. **清理**：先移除全部票 worktree，再移除运行 worktree，随后删票分支与运行
   分支（顺序与命令见 run-mechanics §8.5——worktree 占用的分支删不动）。合并
   未执行不清理：单向门未过，盘上证据即运行状态。
7. **出口报告**：逐票终态清单（票号、评审报告、终态）+ 运行摘要（几层几票、
   预演记录、异常与处置）+ **指路手动 /dev-accept**（集成级场景清单见 spec
   验收场景节）。dev-accept 不被收口自动调用。

## 7. 中断与续接

运行状态在盘上，不在对话里：票 frontmatter 状态机 + 各 worktree 分支即全部状态。
凡停下（异常流、用户喊停、上下文将尽）：先把下一步写进当前在办票的 `## Progress`，
保持票状态，再停。重入时按 §1.3 判定，从 `git worktree list` + 票状态推导断点
（方法见 run-mechanics §5）：已合回的不重做，在办票续接其 Progress，未开工票照图
派发；断点落在收口链内（全绿后任一步）→ 按 run-mechanics §5 末条推导续接，已合回
票不重复评审。fix 票插入或票集变化 → 重算本 spec 的图再续。

## 8. 异常流（一律停下问人，报告连坐阻塞面与指路）

五种异常都执行同一套停机动作：**停下、报告连坐阻塞面（该票下游全部未合回工票
及其状态）、指路技能、等用户决策**。不自动重试、不自动解冲突、不自动改 spec。

- **设计级阻断**（评审发现接口/边界级问题）→ 指路 /dev-design 与工票作者定方案；
  方案落定后受影响票重开。评审的机械问题不在此列——修后重审，运行不停。
- **spec 缺口**（实现中发现 spec 错漏）→ 指路 /dev-spec 修订；修订产出的新票/
  改票并入运行，重算图后续跑。
- **预演失败** → 指路 /dev-fix 开 fix 票；fix 票并入本 spec 图，重算后续跑。
- **合回冲突**（merge-tree 预检后候选序仍全冲突，或干跑干净而实合冲突）→ 问人
  怎么解；预检只排序、不自动解冲突内容；可建议 expand–contract 拆票回
  /dev-plan。
- **收口 pre-push 不过**（运行分支上 implemented 票缺 approved 评审覆盖——评审
  链与盘上状态不一致，如评审报告未随票分支提交）→ 停下报告缺口，指路
  /dev-review 补齐；覆盖补齐后从收口续跑（§7）。

## 9. 边界（任何时候）

- 编排不拆票：拆分归 /dev-plan；一次运行只处理点名 spec 名下的票。
- 不改 dev-implement 纪律、dev-review 单票路径与 `.sdlc/check.sh`。
- 运行依赖顺序图是会话内视图：不落盘、不新增产物类型，进度由票状态机表达。
- 收口由运行全绿自动进入（§6），不经票派发链触发；dev-accept 不被收口自动
  调用——出口只指路。
- 收口只有合并确认一个决策点；PR 准备与票 done、清理是机械步骤，不逐票问人。

## 禁止事项（任何时候）

- 未获开工确认就创建任何 worktree 或分支。
- 未经用户显式确认执行合并——合并是单向门，沉默不是确认；合并未执行就清理
  运行/票 worktree，或跳过 pre-push 直接合并，同罪。
- spec 未 approved、点名单张工票时"顺手"开跑。
- 跳过预演或对红灯自动重试；对合回冲突自动解冲突。
- 替 dev-review 做评审结论，或替实现子代理写实现。
- 在主工作区直接实现任何票——票实现只发生在票 worktree。
- 收口出口自动调用 dev-accept——收口止于指路，验收归人。
