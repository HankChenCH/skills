# dev-execute：整 spec 编排运行

你只做一件事：把**一张已批准 spec 名下的全部工票**变成**按依赖序实现、评审、合回并预演通过的运行**。
其余一切（spec 未 approved、点名单张工票、范围外话题）一律拒绝。
拒绝不是失礼，是本技能的职责。

## 0. 前置：工作区校验

- 仓库根目录必须存在 `.sdlc/check.sh`（由 /setup-workspace 生成）。
- 不存在 → 停止："本仓库未接入开发流程，先运行 /setup-workspace"，不做任何编排。

## 1. 入口门禁（全部通过才继续）

1. **确定编排对象**。入参必须是**一张 spec**（编号或路径）。用户点的是单张工票 →
   拒绝："单票实现请用 /dev-implement"；没点名 → 运行 `.sdlc/check.sh phase` 列出
   全部 `status: approved` 的 spec 供用户选择，禁止猜测或自行挑一张。
2. **校验 spec**：存在且 `status: approved`。仍是 draft → 拒绝并指路
   "/dev-spec 完成批准"；已 done → 拒绝并指路 /dev-accept。名下没有任何工票 →
   拒绝并指路 /dev-plan。名下工票已全部 done → 拒绝："无可运行工票，走
   /dev-accept"。**门级例外（唯一）——验收段未走完的运行在途态**：以下任一命中
   时不拒绝、越过本条各拒绝句（含已 done 与无工票句——done spec 的工票已被
   dev-accept 清扫删除，"名下没有任何工票"字面为真不构成拦截），视为运行在途，
   按 §1.3 重入判定与 §7 续接（run-mechanics §5 第 6 条收口链分支）：
   ① docs/acceptance/ 无本 spec 报告且 spec 仍 approved，且名下工票非空并已全部
   implemented（运行全绿至合并候选验收启动之间的在途态；全新运行工票 ready 不
   命中，照常走建图与开工确认）；
   ② 报告 `status: draft`（验收中段 / 重验环在办，spec 仍 approved）；
   ③ 报告 `status: rejected` 在盘（首轮重验环在途或二轮待判断停点——"验收未
   passed 且合并未执行不清理"，运行分支与 worktree 必在盘；按 run-mechanics
   §5 第 6 条判读次序分支续接）；
   ④ 报告 `status: passed` 而 spec 仍 approved（停合并门，或合并后序列/清理在途）；
   ⑤ spec 已 `done` 而 need 未置 fulfilled（序列走完，停在 fulfilled 门等人）。
   passed 且 need 已 fulfilled（完成态）→ 例外不命中，照旧拒绝改道 /dev-accept。
3. **重入判定**：`git worktree list` 已发现该 spec 的运行分支 worktree，或 §1.2
   门级例外命中 → 运行已在进行中，跳过建图与开工确认，直接按 §7 续接（断点推导
   方法见 run-mechanics §5）。

## 2. 装载上下文

按顺序读：spec 全文 → 名下每张工票全文 → GLOSSARY.md（术语"运行""运行依赖顺序图"
"整图单运行""值守模式""有人值守""无人值守"）→ CODING_STANDARDS.md。再用 Skill 工具装载三个参考：ref-implementation、
ref-testing、ref-git-commit——它们随派发传给实现子代理，合回信息规范也以
ref-git-commit 为准。

然后用三五句话向用户复述：这张 spec 交付什么、共几张票几层并行、打算怎么推进。
有偏差，用户此刻纠正的成本最低。

## 3. 建运行依赖顺序图，请求开工确认

1. 对 spec 名下全部工票按 blocked-by 拓扑分层建图（算法与辅助命令见
   run-mechanics §2）：同层票无依赖可并行，层间 blocked-by 边串行；标注关键路径
   （最长票链）；开工前已 done 的票列图外"已完成"；被 spec 外工票阻塞且未完成的票
   标注"外部阻塞"，若因此全图无法开工 → 停下报告，不进入运行。
2. **开工预检**（建图后、开工确认前执行一次；判定口径与报告格式见 run-mechanics
   §2 末）：逐层比对同层票正文"改动面"行并与代码现状粗扫交叉——同层两票改动面
   相交即记高重叠对（票号 + 重叠面）；票正文无"改动面"行的标"改动面未知"，
   不猜测。预检不硬拦、不新增人工门：报告并入开工确认一并呈现，决策归人。
3. 向用户展示分层图与预检报告，并请求**开工确认（双点选）**：将建立运行分支与
   运行 worktree、每票一个票分支与票 worktree（命名与放置约定见 run-mechanics §1，
   命令见 §3/§4）。
   - **并行档点选**：确认前做一次能力探测（运行中不重探测，既有约定）——派发
     回退链降格为**能力约束**（档 1 整图单运行（声明式工作流）、档 2 后台子代理、
     档 3 同步子代理、档 4 串行逐票；逐档判据见 run-mechanics §4，探测对象按
     docs/research/0003 落具体原语），只决定菜单里有什么与次优落点，不再决定默认
     落哪档。呈现**全部可用档菜单**：可用性按既有判据判定，缺能力档不进菜单并
     声明缺什么；**默认建议档 2 后台子代理**，理由随建议声明（脚本生成成本 +
     逐票完成通知进度透明），宿主无档 2 能力时建议次优可用档并声明理由；用户点名
     任意可用档即定档，不点名按默认建议走——**档 1 仅点名进入**（判据保留用于
     判定"可用"，机制原样保留：点名后主会话生成一个工作流脚本承载整张运行依赖
     顺序图）；无子代理宿主菜单可能只剩档 4，自动落唯一可用档并声明。
   - **值守模式点选**：有人值守（默认，行为与现行零差异）或无人值守（发起时一次
     点选后，运行中除合并到主分支外全部决策点由大模型按流程纪律自主选优并继续，
     逐点语义见 §8）。点选无人值守时**声明宿主权限模式前提**——运行中间零停机以
     权限模式不在工具调用中间打断为前提（如全自动化权限模式），未满足时提示先行
     配置；声明不阻断，宿主配置归运行环境。
   - **开工确认声明口径（三处一致：SKILL.md §3.3 / run-mechanics §4 / 蓝图
     §11.17）**：**本次并行档（点选或默认）+ 本次值守模式 + 形态差异说明**——
     命中档 1 时说明与逐票档的编排模型差异（图承载全链 vs 主会话逐票编排）；
     点选无人值守一并声明自主处置范围与合并门保留人工。
   决策点必须问人，带默认建议（并行档默认建议档 2；无高重叠对：建议按图开工；
   有：建议串行化重叠对或回 /dev-plan 重切——落盘归 /dev-plan，用户坚持按图开工
   也放行，合回冲突由 §5.3 预检序与 §8 异常流兜底）。
4. **未确认不创建任何 worktree**。用户拒绝或要求调整 → 中止，零写入退出；
   要调整分层或拆票 → 指路 /dev-plan（编排不拆票）。

## 4. 运行建立

- 建运行分支与运行 worktree（命令与核对清单见 run-mechanics §3）。
- 建立后核对：`git worktree list` 出现运行 worktree 与运行分支；主工作区仍停留
  主分支且 `git status` 干净。任一不满足 → 停下报告，不派发任何票。

## 5. 流水线调度：实现 → 评审 → 合回 → 预演

按票推进，层屏障取消：运行依赖顺序图的"层"只作展示与依赖满足判定视图（同层票
无依赖可并行，层间 blocked-by 边决定派发与合回时机），任何一票走完一步即推进
下一步，不等同层其余票。

1. **派发实现**：blocked-by 全部满足（依赖票已合回或 done）的票，从运行分支切出
   票分支与票 worktree（细则见 run-mechanics §4），按开工确认点选确定的并行档派发
   （§3.3 双点选定档；逐档判据与形态细则见 run-mechanics §4，探测对象按
   docs/research/0003 落具体原语）。
   - **档 1 整图单运行（点名进入）**：开工确认后主会话生成一个工作流脚本，把整张运行依赖顺序图
     声明进去——同层票 fan-out 并行、blocked-by 边用控制流表达；票清单、blocked-by
     边、并行度上限以类型化参数传入，并行度默认上限 4 经工作流并发度参数承载
     （SKILL 调用参数透传覆盖），图仍会话内计算、不落盘。每票在图内为一条
     **票阶段链**（worktree+物化 → 实现子代理 → 评审子代理 →
     merge-tree 预检序合回 + 翻转副本同步 → 预演确定性门），
     逐票在链内串行、跨票按依赖并行，依赖满足即
     启动；实现子代理仍执行 dev-implement 纪律全文（红绿循环、只做工单内的事、
     Progress 交接）。整图脚本形态细则（阶段结构、参数形状、人工门落点、脚本修订
     补图续接）见 run-mechanics §4。
   - **档 2–4 逐票派发与串行**（形态与行为零变化）：后台子代理档每票一个后台子代理
     执行 dev-implement 纪律全文，完成通知驱动后续编排，不轮询，主会话派发后可
     随时响应用户输入；同步子代理档并行派发等全部返回，子代理执行同款纪律，返回
     即编排（批次期间主会话不可响应，宿主形态）；串行档主会话逐票亲做同款纪律。
     派发时机：开工后先派第 1 层，此后每次合回预演绿即重查图、派发新满足依赖的票。
     并行度默认上限 4，调用参数可覆盖，超出分批；串行档天然逐票。
2. **编排评审**：票 implemented（后台类档即该票完成通知到达时；同步子代理档即
   同步返回时；串行档即亲做完成时；档 1 即该票评审阶段在图内启动）立即在该票
   worktree 内启动评审，**先行评审，不等同层其余票**。
   **编排模式入参**："编排评审：工单 <NNNN>，基线 <运行分支>"。评审报告按入参
   填报：`branch` 记该票分支、`tickets` 记该票（pre-push 在运行分支按覆盖面校验，
   契约见蓝图 §11.7）。评审在票 worktree 内进行、不触碰运行分支，与在办票互不
   干扰。评审出口止于 approved——编排模式下它不准备 PR、不调 dev-ship。
   - **档 1**：评审由**图内评审子代理**承载而非通知主会话介入——运行中间态无逐票
     完成通知，主会话介入须轮询，违背"通知驱动不轮询"约束；入参与报告契约
     branch/tickets 不变。有机械问题 → 修后图内重跑该票评审阶段，不停运行；
     设计级阻断 → §8 异常流。
   - **档 2–4**：主会话用 Skill 工具调 dev-review。有阻断 → 按评审的决策问题处置
     （机械问题修后重审，不停运行；设计级阻断 → §8 异常流）。
3. **机械合回**：票 approved 且 blocked-by 满足 → 合回运行分支，不设人工门。合回
   前完成两件预备：物化同步（翻转副本与评审报告从票 worktree 同步到运行
   worktree）+ merge-tree 干跑预检序（同层候选票取干跑无冲突者先合，候选序全部
   冲突即触发 §8 异常流；预检只排序、不解冲突内容）——细则见 run-mechanics §7。
   同层票在各自派发时基线上实现，合回后不重放基线（改动面互斥保证合回干净）。
   合回冲突 → §8 异常流。档 1 本阶段含两件预备由脚本承载，命令、次序与判据不变，
   候选序全部冲突按值守模式处置（有人值守经升级提问停下问人，无人值守自主决策）。
4. **预演**：每次合回后在运行 worktree 跑 `check.sh all`，加上 spec 验收场景中
   已有自动化承载的集成级测试（细则见 run-mechanics §6）。绿灯才合回下一票、
   派发后续票；红灯 → §8 异常流。档 1 预演由脚本**确定性门**承载（命令门，同款
   命令与判据）：门不过即拦截后续合回与派发，按值守模式触发 §8（有人值守经升级
   提问，无人值守自主处置）。
5. 全部票 implemented 且预演绿 → 运行全绿，随即自动转入 §6 收口（逐票终态与
   预演记录并出入口报告，见 §6.8）。

## 6. 收口链：收口门禁 → 合并候选验收 → PR → 合并确认 → 票 done → 清理 → 收口序列 → 出口报告

运行全绿后自动进入。链序（v1.35 反转 v1.29"清理后自动启动验收"排布）：**合并候选
先验收、passed 才卡合并门**——验收 rejected 的改动停在运行分支上，主分支不被缺陷
污染，负责人凭验收证据做单向门决策。运行内人工交互按值守模式分档：两模式恒有开工
确认图外与合并确认；有人值守另有验收段交互（复述确认、人工段实操走查）；**二轮
rejected 待判断点为条件性全模式停点（触发才出现）**；need 置 fulfilled 门仍是
运行后停点（不计入运行内交互；档 1 图内浏览器场景停回主会话为非人工门停点、不停
等人，见 run-mechanics §4）。逐票评审出口止于 approved（§5.2），任何 PR 准备动作
都只发生在本节。操作细则见 run-mechanics §8。
**档 1 收口链全入图**：fresh 全量检查（确定性门）→ 合并候选验收代理阶段（含
rejected 重验环与二轮 rejected 待判断升级提问；v1.33 浏览器场景停回主会话照旧）
→ 验收报告同步 → PR 准备 → pre-push 门 → 合并确认升级提问 → 执行合并 → 票 done
→ 清理 → passed 收口序列承载 → fulfilled 升级提问 → 运行结算报告即出口报告，
全部由图内承载。

1. **收口起点核对与门禁**：在运行 worktree 重跑 `.sdlc/check.sh all` 作收口门禁
   （证据必须新鲜，出口报告 Evidence 引本次输出；起点核对清单见 run-mechanics
   §8.1）。红灯 → §8 异常流。
2. **合并候选验收（义务，合并前的放行段）**：自动调 dev-accept（Skill 工具），
   随派发声明**验收承载 = 合并候选**（指向运行分支）——验收在运行 worktree 的运行
   分支上执行，先自动化段后人工段（dev-accept 纪律全文；入口门禁编排形态五条件
   机械满足：spec approved、票全 implemented、逐票评审 approved 在盘、预演绿 =
   第 1 步收口门禁输出、当前分支 = 运行分支）。**验收报告随每轮完成即同步回主工作
   区 docs/acceptance/（先于 PR 准备）**。passed 判定即停——不即时走 dev-accept
   收口序列（蒸馏/清扫/置 done 时点延后到合并后，第 9 步承载调用）。
   **rejected 重验环（限一轮）**：第一轮 rejected → 按 dev-fix 纪律**自动开 fix
   票入运行图**（档 1 经脚本修订补图；门红期间只放行 fix 票合回）→ 修复 → 评审 →
   合回 → 预演绿 → **自动重新验收**（新报告标注重验轮次、引用前轮报告编号——
   dev-accept 重验入口三条件）；无人值守下为纪律化自主处置 + 逐条留痕。
   **第二轮仍 rejected → 待判断停点：全模式停点等人，无人值守不豁免**——语义同
   合并门（沉默不算放行），运行分支与 worktree 保留（"验收未 passed 且合并未执行
   不清理"），停点呈现两轮验收报告结论，处置归人（再开 fix 轮 / 放弃运行 / 手动
   接管，不预设）。**验收未 passed 不放行第 5 步合并确认门。**
3. **准备 PR**：验收 passed 后按 dev-ship 前半三节模板写 PR 正文：`## Summary`
   （运行视图：几层几票、逐票一句话）/ `## Evidence`（收口门禁输出 + 逐票评审报告
   编号 + **验收报告编号、终态 passed 与硬伤/瑕疵结论摘要**）/ `## Merge Danger`
   （单向门判定 + 影响半径）。落点跟 TRACKER 走（dev-ship §3 同款）：平台建 PR；
   local 则正文作为合并清单在会话中完整呈现，不让用户盲批。
4. **pre-push**：`.sdlc/check.sh pre-push` 必须通过——它机械校验运行分支领先
   提交中全部 implemented 票都有 approved 评审覆盖。不过 → §8 异常流。
5. **合并确认（单向门，必须问人，全模式人工——无人值守不豁免）**：一次问清
   ① 合并方式（merge commit / squash / fast-forward，跟仓库历史约定给建议）；
   ② 是否打 tag（默认不打——发布点 tag 的语义化版本与 CHANGELOG 归 dev-release）。
   **用户显式确认才执行，沉默或"都行"不算。** 档 1 本确认经升级提问在图内承载
   （无人值守 × 档 1 同样保留人工，图内停等人答）。
   拒绝 → 运行停在合并确认门，盘上状态即运行状态（§7 续接），不强推、不清理，
   **已 passed 的验收判定不回滚**。
6. **执行合并**：dev-ship §4.2 同款——平台 PR 按确认方式在平台合并；本地在
   主工作区（BASE_REF）合并运行分支并 push（细则见 run-mechanics §8.4）。
7. **票 → done**：合并后把本 spec 名下全部工票 `status` 改为 `done` 并追加
   `done: <今日>`，状态变更**落盘不提交**（ADR 0003 物化语义：过程档无可提交
   内容，validate 通过即终态；审计链 = tracker 投影 + 源码 `[#NNNN]` 引用 + 盘上
   状态，细则见 run-mechanics §8.5）。
8. **清理**：先同步评审报告回主工作区 docs/reviews/（验收报告已在第 2 步每轮
   完成即同步），再移除全部票 worktree，随后移除运行 worktree、删票分支与运行
   分支（顺序与命令见 run-mechanics §8.6——worktree 占用的分支删不动）。**验收
   未 passed 且合并未执行不清理**：单向门未过或验收在途，盘上证据即运行状态。
9. **passed 收口序列承载**：合并与清理完成后，承载调用 dev-accept passed 出口
   固定序列（内容不变、时点由本链承载）：蒸馏四路 → 过程档清扫 → spec 置 done →
   原子提交。随后 **fulfilled 门（运行后停点等人显式确认，全模式不豁免，沉默不算
   接受残余风险）**——存在未核销标准或未接受风险 → 抛"开不开下一轮"决策问题
   （默认建议按残余风险性质给，用户显式确认才开轮）。
10. **出口报告**：逐票终态清单（票号、评审报告、终态）+ 运行摘要（几层几票、
    预演记录、异常与处置）+ **验收报告编号与最终轮次终态**（passed / rejected；
    待判断停点收场时载两轮结论）。档 1 运行结算报告即出口报告。
    **无人值守运行另附"自主决策记录"清单**：逐条 = 决策点类型 + 候选与所选 +
    一句理由，可按票号追溯（验收 rejected 一轮的自动重验决策同入清单；逐条留痕
    随各票 Progress 在盘，清单汇总于报告）；有人值守无此清单（对话即记录）。

## 7. 中断与续接

运行状态在盘上，不在对话里：票 frontmatter 状态机 + 各 worktree 分支即全部状态。
开工确认双点选结果随派发写入各票 `## Progress` 首行**运行声明段**（值守模式 +
并行档 + 默认建议理由；盘上承载、零新产物类型，档 1 另由 journal 记录）——续接
据此恢复值守语义。
凡停下（异常流、用户喊停、上下文将尽）：先把下一步写进当前在办票的 `## Progress`，
保持票状态，再停。重入时按 §1.3 判定，从 `git worktree list` + 票状态推导断点
（方法见 run-mechanics §5）：已合回的不重做，在办票续接其 Progress，未开工票照图
派发；断点落在收口链内（全绿后任一步，含合并候选验收段、重验环与合并后收口序列）→ 按 run-mechanics §5 第 6 条
收口链分支推导续接，已合回
票不重复评审。档 1 在既有推导之上**结合工作流运行记录恢复**续跑（journal 重放
已完成步、缓存复用），已合回票不重做。**档 2–4 无人值守运行中断续接：恢复无人
值守语义（异常自主处置 + 留痕，合并门保留人工）并向用户声明**；有人值守续接照常
停下问人。fix 票插入或票集变化 → 重算本 spec 的图
再续（档 1 经脚本修订补图并入运行图重算后续，已完成步经缓存复用不重做）。

## 8. 异常流（按值守模式分档处置）

处置归属按开工确认点选的值守模式分档：

- **有人值守（默认）**：五种异常都执行同一套停机动作——**停下、报告连坐阻塞面
  （该票下游全部未合回工票及其状态）、指路技能、等用户决策**。档 1 五类异常经
  **升级提问/洞穴**在图内停下问人——只迁移承载方式，语义零回退；其余档主会话
  停下问人。禁令全量生效：不自动重试、不自动解冲突、不自动改 spec。
- **无人值守**：除合并确认、验收段 need 置 fulfilled 门与二轮 rejected 待判断停点（§6，全模式留人）外，决策点由大模型按流程纪律**自主选优并继续，运行
  不停**；每次自主处置逐条**留痕**（决策点类型 + 候选与所选 + 一句理由，进该票
  Progress 与出口报告"自主决策记录"清单，§6.8）。自主处置是**纪律化处置**
  （走 dev-fix / dev-spec / 既有冲突处置动作），不是盲目重试——禁令改述为
  **不脱离纪律重试**（重跑同一命令不算处置）。无人值守 × 档 1：五类异常的图内
  升级提问替换为**自主决策阶段**（选优 + 留痕，journal 记录）。
- 三条例外**不分档、全模式生效**：沉默不算确认（合并确认必须显式）；验收未 passed
  且合并未执行不清理；二轮 rejected 待判断停点留人（语义同合并门，沉默不算放行）。

- **设计级阻断**（评审发现接口/边界级问题）→ 有人值守：指路 /dev-design 与工票
  作者定方案，方案落定后受影响票重开；无人值守：大模型自行定方案（落选候选与
  理由留痕），受影响票重开实现，运行不停。评审的机械问题不在此列——修后重审，
  运行不停（两模式同）。
- **spec 缺口**（实现中发现 spec 错漏）→ 有人值守：指路 /dev-spec 修订；无人
  值守：按 dev-spec 修订纪律自行修订 spec 并留痕。修订产出的新票/改票并入运行，
  重算图后续跑（两模式同机械语义）。
- **预演失败** → 有人值守：指路 /dev-fix 开 fix 票；无人值守：按 dev-fix 纪律
  自行开 fix 票并留痕。fix 票并入本 spec 图，重算后续跑（两模式同）。档 1 经
  **脚本修订补图**把 fix 票并入运行图重算后续，已完成步经缓存复用不重做；
  修订不成：有人值守停机问人，无人值守入自主决策阶段选优留痕。
- **合回冲突**（merge-tree 预检后候选序仍全冲突，或干跑干净而实合冲突）→
  有人值守：问人怎么解，可建议 expand–contract 拆票回 /dev-plan；无人值守：
  大模型自行解冲突内容后继续合回——标准动作仍含先 `git merge --abort` 还原再
  处置（处置者从人换为大模型，机械语义不变），决策留痕。预检只排序、预检序
  本身不解冲突内容（两模式同）。
- **收口 pre-push 不过**（运行分支上 implemented 票缺 approved 评审覆盖——评审
  链与盘上状态不一致，如评审报告未随合回前同步落到运行 worktree）→ 有人值守：
  停下报告缺口，指路 /dev-review 补齐；无人值守：按评审纪律自行补齐覆盖（缺
  同步先补同步，缺评审重跑该票编排评审）并留痕。覆盖补齐后从收口续跑（§7），
  覆盖不齐不进合并确认（两模式同），不自动强推。
- **验收 rejected 一轮**（合并候选验收首轮判 rejected）→ 两值守模式同为**纪律化
  重验环**：按 dev-fix 纪律自动开 fix 票入运行图（档 1 经脚本修订补图；门红期间
  只放行 fix 票合回——预演失败既有机制同款），顺序"修复 → 评审 → 合回 → 预演 →
  重新验收"（新报告标注重验轮次、引用前轮报告编号），**重验上限一轮**；无人值守
  下为自主处置 + 逐条留痕（随票 Progress 与出口报告自主决策清单）。
- **验收 rejected 二轮**（重验后仍 rejected）→ **待判断停点：全模式停点等人，
  无人值守不豁免**——语义同合并门（沉默不算放行），运行分支与 worktree 保留
  （验收未 passed 且合并未执行不清理），停点呈现两轮验收报告结论，处置归人
  （再开 fix 轮 / 放弃运行 / 手动接管），不预设菜单；档 1 经升级提问承载、其余档
  主会话停点。出口报告载两轮结论。
- **合并门拒绝**（负责人在合并确认拒绝合并）→ 现状语义保持：运行停在合并门、
  盘上状态即运行状态，不强推不清理，**已 passed 的验收判定不回滚**（验收停点不
  触发，续接从 §6 第 5 步合并确认起）。

## 9. 边界（任何时候）

- 编排不拆票：拆分归 /dev-plan；一次运行只处理点名 spec 名下的票。
- 不改 dev-implement 纪律、dev-review 单票路径与 `.sdlc/check.sh`。
- 运行依赖顺序图与工作流脚本都是会话内产物：图不落盘、工作流脚本不落盘为仓库
  产物、不新增产物类型，进度由票状态机表达（票 frontmatter + worktree 仍是唯一
  运行真源）。
- 收口由运行全绿自动进入（§6），不经票派发链触发；**合并候选验收是收口链的合并
  前置段（义务，含无人值守）**——验收在运行 worktree 的运行分支上先行于合并
  （v1.35 反转 v1.29 合并后排布），passed 的收口序列在合并后由收口链承载调用。
- 运行内收口的全模式决策点 = 合并确认 + 条件性待判断停点（二轮 rejected 触发才
  出现）；有人值守另有验收段交互（复述确认、人工段实操走查）；PR 准备与票 done、
  清理、passed 收口序列承载是机械步骤，不逐票问人；need 置 fulfilled 门仍是
  运行后停点（档 1 图内浏览器场景停回主会话为非人工门停点，见 run-mechanics §4）。
- 值守模式发起时一次点选、运行中不变更；宿主权限模式前提归运行环境（技能层只
  声明不配置）。运行声明段随派发写入票 Progress（§7），不新增产物类型。

## 禁止事项（任何时候）

- 未获开工确认就创建任何 worktree 或分支。
- 未经用户显式确认执行合并——合并是单向门，沉默不是确认（**全模式生效**：无人
  值守运行全绿停在合并门等人回来）；**验收未 passed 放行合并门**、**验收未 passed
  且合并未执行就清理运行/票 worktree**，或跳过 pre-push 直接合并，同罪；**二轮
  rejected 待判断停点不留人**（无人值守不豁免，沉默不算放行），同罪。
- spec 未 approved、点名单张工票时"顺手"开跑。
- 有人值守：跳过预演或对红灯自动重试、对合回冲突自动解冲突、自动改 spec——禁令
  全量生效。无人值守：自主处置必须是纪律化处置（走 dev-fix / dev-spec / 既有
  冲突处置动作并逐条留痕）——**不脱离纪律重试**；红灯盲目重跑同一命令、绕过
  预演判定、未经 dev-spec 纪律直改 spec，同罪。
- 替 dev-review 做评审结论，或替实现子代理写实现。
- 在主工作区直接实现任何票——票实现只发生在票 worktree。
- 全绿后停而不验、把验收留给合并后或手动指路——收口链必须在合并前自动启动合并
  候选验收（义务，含无人值守；v1.35 反转 v1.29 合并后排布）；need 置 fulfilled
  不留人显式确认（沉默不算接受残余风险），同罪。
