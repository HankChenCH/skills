# dev-overview：开工前总览合成与走查

你只做一件事：把**一张 approved spec 名下的产物**纯读合成**五节总览**，陪用户走查并把缝隙归置回 spec 与工单。
其余一切（改 spec、改票、写代码、替用户拍板）一律拒绝。
拒绝不是失礼，是本技能的职责。

## 0. 前置：工作区校验

- 仓库根目录必须存在 `.sdlc/check.sh`（由 /setup-workspace 生成）。
- 不存在 → 停止，告诉用户"本仓库未接入开发流程，先运行 /setup-workspace"。

## 1. 入口门禁（全部通过才继续）

1. **确定 spec**。用户给了编号或路径 → 用它；没给 → 运行 `.sdlc/check.sh phase`，
   列出 `approved` 的 spec 及各自名下 ready 票数，请用户点名。禁止自行挑一张没被点名的 spec。
2. spec 的 `status` 不是 `approved` → **停止**："spec NNNN 还是 draft，先 /dev-spec 完成批准。"
3. **名下一张 ready 票都没有**（docs/tickets/ 没有 `spec: NNNN` 且 `status: ready` 的工单）→
   **停止**："spec NNNN 的票还没拆完，先 /dev-plan——全景矩阵的票号列依赖票在盘上。"
4. **重入**：docs/overviews/ 已有 `spec: NNNN` 指向它的 draft 总览 → 从 §4 走查续接，
   不重新合成（盘上的 draft 就是进度）。

## 2. 装载上下文（全程纯读）

按顺序读：need 全文 → spec 全文（重点 `## 方案`、`## 实现决策`、`## 测试决策`、`## 验收场景`）→
design 全文（若有）→ 名下全部工单（做什么 / 改动面 / 验收标准）→ GLOSSARY.md。
装载阶段不改任何产物文件——合成是纯读动作，装载时就改字，总览就成了第二真相源。

## 3. 合成纪律

- **落盘**：运行 `.sdlc/check.sh claim overview <slug> spec <spec-ID>` 取号——返回
  `docs/overviews/` 下的占位文件路径，号由入口原子分配、全历史唯一，父为 spec
  （知识档）自动带 `spec<父ID>-` 谱系前缀；slug 用 ASCII 小写短横线。用五节模板
  写正文覆盖占位文件（frontmatter 固定 `id`（填文件名的 ID 段）`spec` `status: draft`
  `created`）。五节模板内嵌如下，节序固定：

```markdown
---
id: <ID 段，YYYYMMDD-4hex>
spec: 0003
status: draft
created: <date>
---
# <ID 段>: <标题>

## 全景一行
一句话说清功能形态与交付切分。（来源：spec NNNN 方案；need NNNN FR 覆盖面）

## 全景矩阵
| actor | FR | 场景 | 票号 |
|---|---|---|---|
| <角色> | FR-N | <场景一句话>（spec NNNN 验收场景 FR-N） | ticket NNNN |

指不回任何票的格子，票号列写「缺口：指不回任何票」，同条进差距清单。

## 黄金场景走查
### 走查一（正常流）：<名字>
你<第二人称叙事，一句一个动作>。剧本逐句：Given … When … Then …（来源：spec NNNN 验收场景 FR-N）

（2–3 条；至少一条异常流，空/错误态各覆盖）

## 样张
<按媒介判定出样：UI→三态可点 HTML 原型 / CLI→输出样例 / API→调用序列+请求/响应样例>
（来源：spec NNNN 实现决策；ticket NNNN 验收标准）

## 差距清单
- <FR-N 或格子>：<缺口一句话>→ 归置建议（回 dev-spec / 回 dev-plan / 非目标），由用户拍板。
无缺口写「无」并注明来源（矩阵逐行指回票）。
```

- **硬纪律三条**：
  1. **每段可溯源**：正文每段标注来源（need FR-N / spec 验收场景 / ticket NNNN），
     不产新决策——总览不引入 spec、票上没有的目标、接口或承诺，它是呈现，不是第二真相源。
  2. **写不出的格子进差距清单**：某 FR 指不回票、某场景出不了样张、某叙事剧本对不上
     spec 验收场景——如实标缺口，不现场拍板，不留空白，不写"略"。
  3. **保真度 JBGE**：样张只做状态可见性（三态：正常/空/错误），不做高保真视觉稿，
     不陪评配色字体。
- **样张媒介判定**（读 spec `## 实现决策` 判对象类型）：UI → 三态可点 HTML 原型，落系统临时目录；
  CLI → 输出样例（输出即线框）；API → 调用序列 + 请求/响应样例；混合对象分节各出。
  判定拿不准（多类型交织、无从判断）→ 决策卡问用户，不猜。
- **UI 原型**沿 skills/dev-clarify/references/prototype.md 规格执行：单文件、零依赖、≤200 行、
  三态切换钮、主流程可点通、异常流有入口；落系统临时目录、不进仓库、用完即弃；
  样张节只留落盘说明、打开命令与拍板要点——原型的每个写不出的格子即决策点。
- **黄金场景走查**：2–3 条第二人称叙事（每条对应一个验收场景；场景多于 3 条取黄金路径 + 异常流），
  异常流至少一条，空/错误态覆盖；剧本取自 spec 验收场景（集成级优先），逐句对得上——
  对不上的句子就是缝隙，进差距清单。

## 4. 走查与三路归置

1. 合成完成后逐节念给用户走查：五节按序，样张给出打开命令。
2. 暴露的缝隙**三路归置**，落点永远在 spec 与工单上，总览不替用户拍板：
   - 缺 FR 或场景错 → 回 dev-spec 补 FR 改场景（回路，不是失败）；
   - 缺票或切分错 → 回 dev-plan 补票重切；
   - 明确不做 → 经用户确认记入 spec `## 非目标`。
3. 归置改动了 spec/票 → **先更新产物，再更新总览**对应格子，再走确认。
4. **状态推进**：走查完成、差距清单已清零（或归置为非目标）后，须用户显式确认
   （沉默不算、"都行"不算）才置 `status: reviewed`，并追加 `reviewed: <日期>`；
   未确认时总览保持 draft，停下不丢进度。
5. `reviewed` 是名下票 ≥2 的 spec 的开工前置条件（`check.sh ticket` 读取）；单票 spec 无此门。

## 5. 出口门禁（全部通过才算完）

1. 运行 `.sdlc/check.sh validate <取号返回的路径>`，必须通过；不过 → 修复后重跑。
2. 硬纪律自查：每节来源标注齐（grep 可核）；差距清单无未暴露的缺口；样张三态齐。
3. 总览是过程档：不进任何提交（`.gitignore` 已排除 docs/overviews/），落盘后 `git status` 干净。

## 6. 中断与交接

会话可能在任何时刻结束。凡是停下（等用户走查、上下文将尽、被卡住）：
总览以 `status: draft` 保持盘上（合成到几节是几节），待归置的缝隙写进差距清单，再停。
重入从 §1 的重入分支续接——盘上的 draft 就是进度。状态在盘上，不在对话里。
临时目录里的原型用完即弃，中断后按样张节的说明重开即可——拍板要点已在样张节。

## 禁止事项（任何时候）

- 产新决策、加新目标、替用户拍板——总览只暴露缝隙，拍板永远落在 spec 与工单上。
- 写不出的格子现场编一个说法，或把差距清单写成"无"来消音。
- 用户未显式确认（沉默、"都行"不算）就把 `status` 写成 `reviewed`。
- 样张进仓库、接真数据、上框架、做高保真视觉稿、陪评配色字体。
- 跳过 validate；或为"消掉"差距擅自改 spec/票——归置须经用户拍板，落点在产物上。
