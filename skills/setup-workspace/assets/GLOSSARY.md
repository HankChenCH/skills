# GLOSSARY

本文档分两章：**流程术语与状态**由 setup-workspace 首建，是全仓库对流程词汇的共识来源，AGENTS.md 哨兵块引用本章；**项目术语**由各技能与用户在使用中续写，先到这里登记定义，再在文档与对话中使用。

## 流程术语与状态

### 产物类型

| 术语 | 定义 |
|---|---|
| need | 需求纪要：业务目标、干系人、系统能力需求（FR-N）、场景、假设与风险。一轮迭代的最上层依据。 |
| spec | 规格：用户视角的问题陈述、方案、用户故事、实现与测试决策、验收场景。改源码前的必要产物。 |
| design | 技术方案：模块划分、数据流、seam（测试边界）。配合 ADR 记录架构决策。 |
| ticket | 工单：一张可独立开工、可独立验收的实现单元，分 feature / fix 两类，同池编号。 |
| overview | 总览：开工前对单张 spec 名下产物的纯读合成文档，固定五节（全景一行、全景矩阵、黄金场景走查、样张、差距清单）；过程档归置，详见项目术语章。 |
| review | 评审报告：双轴（标准轴 + Spec 轴）findings 汇总，`tickets: []` 声明覆盖面。 |
| acceptance | 验收报告：集成后逐条运行集成级场景、逐 FR 核销、风险复审的结果。 |
| adr | 架构决策记录：难逆转、无上下文会困惑、真实权衡的决策，accepted → superseded。 |
| research | 调研报告：带来源引用的参考资料，无状态机。 |
| retro | 复盘报告：dev-retro 落盘 docs/retros/ 的复盘记录——豁免审计结论、改动清单与采纳记录。轻产物，不进 check.sh 门禁。 |

### 关键机制

- **FR-N**：系统需求编号（need 定义，spec 验收场景覆盖，acceptance 核销）。没有场景覆盖的 FR 是孤儿，`check.sh validate` 报错。
- **工单级 / 集成级**：验收场景的验证层级。工单级映射进单张工单的验收标准；集成级拆不进单票，是 acceptance 的运行清单。
- **承载票 / 承载声明**：集成级验收场景的自动化测试归属。承载票 = dev-plan 指定编写并运行该集成测试的工单；承载声明 = spec 验收场景标签中的承载方式标注（自动化指向承载票，人工写理由），dev-accept 据此先跑自动化段再走人工段（首现：need 20261109-1a94）。
- **round**：spec 的迭代轮次。round 1 覆盖风险最大的最小范围（MVP），后续轮次由验收后的"下一轮建议"驱动。
- **frontier**：阻塞已清、可开工的工单清单，`check.sh frontier` 输出。
- **[trivial]**：提交豁免标记，限 typo 与纯文档改动；唯一例外 = 门禁自指场景（修复门禁的改动被该门禁拦截且流程内无解），须经用户显式拍板、commit message 记完整因果，dev-retro 复核其语义；每次豁免留痕于 commit message，dev-retro 审计。
- **哨兵块**：AGENTS.md 中 `<!-- sdlc:begin/end -->` 之间的内容，由 setup-workspace 管理，勿手改。
- **盘上主本 / tracker 投影**：docs/ 是唯一真相源，tracker（GitHub/GitLab/Codeup）只单向接收发布，不回读。
- **门禁分级**：commit-msg 查轻量项（[#NNNN] 状态合法或 [trivial]；Merge/Revert 信息头机械豁免）；pre-push 查重项（implemented 工单须有 approved 评审覆盖）。
- **L4 hook**：平台层拦截（`.sdlc/hooks/l4-guard.sh`，经 ZCode PreToolUse 触发）：拦含 `--no-verify` 的命令与无在办（in-progress）工单的 CODE_DIRS 源码编辑；失效安全为放行（fail-open），自身故障不锁死工作。
- **红绿循环**：每个行为先写一个失败的测试（红），再写刚好让它通过的实现（绿）的实现节奏；标准细则见 ref-testing 技能。
- **分诊定级**：dev-fix 对缺陷的定级（阻断：主流程不可用/数据错误或丢失/安全漏洞；重要：功能受损有绕行、影响面大；一般：影响面小；轻微：文案样式纯文档）与处置决策（现在修/排期/不修），落进 fix 票正文。
- **seam**：测试边界——测试只写在预先约定的接口处，不穿实现内部。design 的 seam 清单是 spec 测试决策的细化，dev-implement 在其上落测试（细则见 ref-testing）。
- **评审轴**：dev-review 的一条独立评审纪律单元 = 轴名 + 判断依据（该轴允许装载的材料清单）+ 产出节；当前清单两条（标准轴、Spec 轴）。每轴派发恰一个独立子代理、只装本轴材料，隔离靠独立上下文（v1.24）。
- **面向人的文档**：README、用户文档、API 文档等描述仓库实际行为、给人读的文档，dev-docs 的维护对象；与流程产物（docs/ 各产物目录）、METHOD.md（归 setup）、CHANGELOG（归 dev-release）分界；不含源码内注释与 docstring——那属源码文件，改动走工单。

## 项目术语

（首个项目术语落盘时由对应技能在此追加；格式：`术语 —— 定义（首次出现的产物）`）

- **稳态假设** —— 混沌测试的前置判据：一句可度量的系统正常状态描述，加"用哪些指标证明它成立"（如"下单成功率 ≥99.9%，以订单表增长与错误率为证"）；先有稳态假设才准注入故障（首次出现：ref-testing 技能 references/chaos.md）。
- **投影** —— tracker 适配器把 docs/ 产物单向镜像到平台对象（GitHub/GitLab issue、Codeup 工作项+评论）的行为；投影失败一律警告跳过不阻断，盘上产物永远是真相源（首次出现：need 0002 / spec 0004）。
- **映射文件** —— 适配器同目录的 `<tracker>.map` 三字段表（盘上相对路径、平台对象编号、对象 URL），支撑同一产物重复 publish 时更新而非新建；丢失映射的后果仅是可能新建重复对象（首次出现：spec 0004 实现决策）。
- **运行（run）** —— dev-execute 对一张 approved spec 的一次完整编排执行：独立运行分支 + 运行 worktree 内按运行依赖顺序图推进名下全部工票，止于一次合并确认；票合回运行分支是机械操作，不设人工门（首次出现：need 0004）。
- **工作区仓库** —— 多仓工作区形态下由 setup-workspace 在根目录 git init 出的仓库：只装流程基础设施（`.sdlc/`、`docs/`、AGENTS.md 等），不装子仓库源码（首次出现：need 0008）。
- **成员子仓库** —— 根目录第一层经用户确认入册的 git 仓库；受门禁、被扫描，各为单仓或 monorepo（首次出现：need 0008）。
- **成员清单** —— 工作区成员子仓库的落盘名册：初始化确认后生成，重跑按其 diff 增补/移出（首次出现：need 0008）。
- **运行依赖顺序图** —— 对一张 spec 名下全部工票按 blocked-by 拓扑排序得到的分层视图：同层票无依赖可并行，层间 blocked-by 边是串行约束；会话内计算、不落盘，执行进度由工单状态机表达（首次出现：need 0004）。
- **知识档** —— 价值越过终态仍被回读的产物档：need、spec、design、adr、research、standards；终态后留存于工作区与版本库（首次出现：need 0005）。
- **过程档** —— 价值在终态耗尽的产物档：ticket、review、acceptance、overview；过程中盘上存在、被 `.gitignore` 排除、不进任何提交，验收通过后随蒸馏清扫删除（首次出现：need 0005）。
- **蒸馏** —— dev-accept 在验收通过时把过程档产物中的耐久内容折回知识档的动作，四路落点：残余风险与证伪假设回 need、行为契约修正回 spec 验收场景、架构决策立 ADR、模式学习进编码标准；必须先于清扫（首次出现：need 0005）。
- **清扫** —— 蒸馏完成后删除该 spec 名下全部过程档产物（tickets / overviews / reviews / acceptance 报告）的动作，与蒸馏、spec 置 done 同一提交原子完成；不回删 tracker 投影（首次出现：need 0005）。
- **逆向产物** —— 扫描技能从存量代码逆向推断出的知识档沉淀物：need/spec/adr 形态与 AGENTS.md、GLOSSARY 项目术语章、docs/standards/ 的折叠内容；每条行为断言带文件:行证据与置信标注，逆向 need/spec 落盘即置 `status: reconstructed`，不进正向待办流（首次出现：need 0006）。
- **扫描基线** —— 逆向产物记录的扫描覆盖快照：扫描时点的 commit 与日期、已覆盖与未覆盖范围；补扫增量对齐后随之更新，未覆盖区不得被读成"不存在"（首次出现：need 0006）。
- **对账清单** —— 迁移技能产出的逐件归宿清单：每件外来产物一行，来源（本地路径 / issue 编号）→ 归宿（新产物路径 / 归档位置 / 显式弃置及理由）；外来 issue 处置失败也在此留痕（首次出现：need 0007）。
- **翻译映射** —— 迁移技能把外来产物逐件译为本套件形态的动作：未完成的外来工作进正向流程现态（spec 落 draft、ticket 落 ready，照常推进），已完成的历史产物译为沉淀形态（落盘即 reconstructed）或折进既有沉淀产物；逐件翻译不以原样归档替代，来源区分走产物正文「来源」行与对账清单，不走状态机（首次出现：spec 0010）。
- **改动面互斥** —— dev-plan 拆分纪律约束：同层（无 blocked-by 边）工票的预估改动文件/模块集合不相交；确需改动同一处的票并票、标 blocked-by 串行或按 expand–contract 重切三选一，用并行度换零合回冲突（首次出现：need 0010）。
- **层屏障** —— dev-execute 既有的层推进节奏：当前层全部票合回且预演绿才调度下一层；与流水线合回相对，need 0010 以流水线合回替代它（首次出现：need 0010）。
- **流水线合回** —— dev-execute 的目标推进节奏：票评审 approved 且依赖满足即合回运行分支并预演，不等同层其余票完成；前提是同层票满足改动面互斥（首次出现：need 0010）。
- **整图单运行** —— dev-execute 档 1（声明式工作流）的派发形态：整张运行依赖顺序图声明为一个工作流运行，同层并行与跨层依赖由脚本控制流表达（fan-out/join），预演走脚本确定性门、人工门走升级提问/洞穴；与逐票派发形态（每票一个工作流运行，档 2–4 同构基线）相对（首次出现：need 0011）。
- **总览（overview）** —— 开工前对单张 spec 名下产物的纯读合成文档，固定五节：全景一行 / 全景矩阵 / 黄金场景走查 / 样张 / 差距清单；不产新决策、正文每段可溯源到既有产物，过程档生命周期（首次出现：need 0012）。
- **走查** —— 评审人以用户视角沿黄金场景叙事与样张过一遍总览、把暴露的缝隙三路归置（回 dev-spec / 回 dev-plan / 非目标）的评审动作；走查完成总览置 reviewed，是名下多票 spec 的开工前置条件（首次出现：need 0012）。
- **样张** —— 总览中按对象类型选媒介的具象样例：UI→三态（正常/空/错误）可点 HTML 原型（落系统临时目录不进仓库）、CLI→输出样例、API→调用序列+请求/响应样例（首次出现：need 0012）。
- **述标** —— design-* 套件向验收方呈现设计的方式：在 design 产物「界面设计」节写明设计意图与取舍，配套可点 HTML 界面原型（落 docs/designs/assets/）供评审；design 的 approved 门即述标评审门，比喻源自建筑设计院述标（首次出现：need 0013）。
- **设计基线** —— 项目级设计语言标准：落 docs/standards/ 设计标准分册（按平台分文件）并登记 CODING_STANDARDS.md 索引，由 design-baseline 技能建立与跟随；存在时界面设计须先读基线，偏离须逐条声明理由（首次出现：need 0013）。
- **时间戳派生 ID** —— 产物编号方案（need 0014 拍板）：号由创建时刻的时间戳加随机段派生（如 `20261104-a3f2`），不依赖目录现存文件或 tracker map 推导；多会话并发取号与清扫后不复用由格式本身保证，旧四位纯数字纪元止于存量产物，新旧格式可区分（首次出现：need 0014）。
- **谱系前缀** —— 有父产物的产物号前缀（need 0014 拍板）：父产物号作前缀、后接本产物时间戳派生段（如 spec 0017 派生工票 `spec0017-20261104-a3f2-slug.md`），按号即读归属；最小覆盖 spec 派生工票，其余父子关系按同一原则扩展（首次出现：need 0014）。
- **值守模式** —— dev-execute 开工确认点选的运行中决策归属模式，与并行档位点选正交：有人值守（默认）运行中决策点全部停下问人，无人值守除合并到主分支与验收二轮 rejected 待判断停点外全部决策点由大模型自主选优（首次出现：need 20261107-873f）。
- **有人值守** —— 值守模式默认档：开工确认、评审阻断处置、原五类异常流（新增三类按各自条目：验收 rejected 一轮两模式自动重验环不停机，二轮 rejected 待判断停点与合并门拒绝全模式停点）、合并确认全部停下问人，验收段交互前置（复述确认、人工段实操走查），"不自动重试、不自动解冲突、不自动改 spec"禁令全量生效（首次出现：need 20261107-873f）。
- **无人值守** —— 值守模式档：发起时随开工确认一次点选后，运行中除"合并到主分支与验收二轮 rejected 待判断停点"外全部决策点由大模型自行判断选最优解并继续运行（含设计级阻断自行定方案、合回冲突自行解、spec 缺口自行修订、预演失败与首轮验收 rejected 自行开 fix 票入图重验——重验限一轮）；每次自主决策逐条留痕进该票 Progress 与出口报告；合并到主分支仍是需显式确认的单向门，确认不执行则运行停在合并门；验收二轮 rejected 待判断停点全模式留人、无人值守不豁免（语义同合并门，沉默不算放行）（首次出现：need 20261107-873f）。
- **视觉层级** —— 界面里各元素相比之下显得有多重要的相对关系：靠字重与颜色而非单靠字号营造，主要的一眼可见、次要的清晰不抢眼、第三级的可发现不打扰；定名沿用译文仓库 github.com/read-x/refactoring-ui-zh @ ec3aa73 术语表 visual hierarchy 译名（首次出现：ref-refactoring-ui 技能 references/hierarchy.md）。
- **间距阶梯** —— 预先定好的受限间距与尺寸取值序列：以 16px 为基准、相邻取值差距不低于约 25%，所有间距与尺寸决定只从阶梯里选，不做逐像素临场微调（首次出现：ref-refactoring-ui 技能 references/layout-spacing.md）。
- **色阶** —— 一种颜色按深浅预先排定的一组变体：灰色系备 8–10 阶、主色与强调色各备 5–10 阶（编号如 100–900），用时取阶、禁止临时计算新色；定名沿用译文仓库 @ ec3aa73 术语表 shade 译名（首次出现：ref-refactoring-ui 技能 references/color.md）。
- **强调色** —— 主色之外用于传达信息或突出语义状态的颜色（警示黄、破坏性红、成功绿等）：克制使用并按色阶体系管理；定名沿用译文仓库 @ ec3aa73 术语表 accent color 译名（首次出现：ref-refactoring-ui 技能 references/color.md）。
- **复杂守恒定律** —— 产品的内在复杂性不可移除也不可隐藏，设计能决定的只是它归谁处理：以客户视角重构复杂性的归属，把复杂扛在设计侧、把简单留给客户，落到体感是"找得到 + 看得懂"（首次出现：ref-b-side-design 技能 references/understand-customer.md）。
- **MECE** —— 功能归类的硬判据：互相独立、完全穷尽；ref-b-side-design 主要取"互相独立"一翼——一个功能只归一个大类，归类维度从客户业务逻辑取而非技术实现取，出现"归 A 还是归 B"的犹豫即耦合信号（首次出现：ref-b-side-design 技能 references/architect-structure.md）。
- **泳道图** —— 按角色分列的流程图绘制形式：第一列客户逐动作记录（多角色全排左侧）、第二列产品界面内容、第三列后台数据读取储存判断；用于还原原有流程、识别最高频最耗精力的界面与等待出错点位，是 B 端流程优化的前提工具（首次出现：ref-b-side-design 技能 references/architect-structure.md）。
- **5E 原则** —— 可用性工程给出的体验五要素自查清单：易学性、效率、容错性、有效性、吸引力；B 端核心界面按此顺序自查——对执行者易学性第一、效率第二，吸引力在面向决策者的报表与大屏场景升到第一（首次出现：ref-b-side-design 技能 references/craft-key-interface.md）。
- **多尔蒂门槛** —— 系统须在 400ms 内对使用者操作给出响应的体验判据（源自 IBM 研究员多尔蒂的响应时间研究）：超出即被感知为卡顿；B 端数据量大、加载慢不是豁免理由，设计侧以即时出现的 loading 动画与久候引导文案缓解（首次出现：ref-b-side-design 技能 references/craft-key-interface.md）。
- **使用方走查轴** —— dev-accept 的一条独立验收纪律单元，与评审轴同构：轴名 + 判断依据（允许装载的材料清单）+ 产出节；当前清单恰一条，判断依据 = need 全文、spec「验收场景」节、design 产物「界面设计」节（述标）、docs/designs/assets/ 可点原型、BASE_REF 上的集成后交付物（无述标时补工单「验收标准」节），产出节 = 验收报告「场景结果」「假设验证」「残余风险」；禁装清单 = 工单 Progress、实现交接记录、实现会话上下文——验收代理不读实现叙事（首次出现：spec 20261108-2fe1）。
- **硬伤 / 瑕疵** —— dev-accept 验收发现的分级判据：硬伤 = 功能缺失、操作行为不符预期、交付比原型差，阻塞判定 rejected；瑕疵 = 不影响使用方完成任务的样式、文案、措辞类偏差，留痕不阻塞 passed、写进「残余风险」与「下一轮建议」；rejected 判据 = 存在硬伤或 `check.sh all` 红灯（首次出现：spec 20261108-2fe1）。
- **混合验收形态** —— dev-accept 验收报告的三种形态声明之一：浏览器操作原语仅限主会话（工具自述 main agent only）的宿主上，Web 界面集成级场景由当前会话（执行体 / 编排会话）真实操作浏览器取证亲判、场景行不带【降级】标记，其余介质场景（CLI / API / 文档）仍由恰一个隔离验收代理承载，报告「场景结果」首行声明混合（隔离验收代理 + 主会话浏览器走查）；浏览器原语对子代理可用时仍隔离优先（恰一个隔离验收代理承载全部场景），确无可用原语（态 ③）时 Web 场景行走降级路径并带【降级】标记、形态行仍为恰一个隔离验收代理，宿主连子代理原语也无时才整单声明单上下文降级；【降级】标记只用于态 ③ 降级行（首次出现：spec 20261109-c8f6）。
- **合并候选验收** —— dev-accept 的验收承载声明形态：编排串联调用（dev-execute 收口链）随派发声明承载 = 合并候选，指向运行分支，验收在运行 worktree 的运行分支上于合并前执行，入口门禁按"spec approved + 工票全 implemented + 逐票评审 approved + 预演绿 + 当前分支 = 声明承载分支"放行（不要求工票 done 与 BASE_REF），承载写入验收报告首行形态行；缺省形态（手动调用不声明）承载 = BASE_REF 现状，门禁语义逐条不变；配套重验入口 = 编排重验声明 + 上一份报告 rejected 终态 + fix 票 approved 合回且预演绿，三条件齐开新报告（标注重验轮次、引用前轮编号，旧报告不回改不删除）；与既有「承载声明」（集成级场景自动化归属标注）为两个概念——本词条的声明对象是验收承载（首次出现：spec 20261110-b2fc）。
