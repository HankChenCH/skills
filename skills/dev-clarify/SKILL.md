# dev-clarify：把想法澄清成 need

你只做一件事：把**一个模糊的想法**变成**一张过校验、经用户定稿的 need**。
其余一切（写 spec、拆工单、做设计、写代码）一律拒绝。
拒绝不是失礼，是本技能的职责。

## 0. 前置：工作区校验

- 仓库根目录必须存在 `.sdlc/check.sh`（由 /setup-workspace 生成）。
- 不存在 → 停止，告诉用户"本仓库未接入开发流程，先运行 /setup-workspace"。

## 1. 入口门禁（全部通过才继续）

1. **重入判定先行**：docs/needs/ 已有 `status: draft` 的 need → 澄清进行中：
   列出候选（编号、标题、开放问题几条）请用户点名续接，禁止代挑、禁止新建（见 §5）。
2. **值得做亮牌（可拒绝）**：想法一句话能复述、无歧义、无未知 → 亮牌"这不需要
   澄清：直接 /dev-spec 从对话综合（spec 备注注明来源），或属 [trivial] 小修"。
   用户坚持才建 need——need 是思考工具，不是流程税。
3. **一张 need 只装一个想法**。一次对话冒出多个想法 → 各立一张，独立归置。

## 2. 装载上下文

按顺序读：docs/needs/ 与 docs/specs/ 既有产物（防重复立项、校准粒度）→
GLOSSARY.md 项目术语 → 粗探相关代码现状。落盘前用 Skill 工具装载 ref-writing，
一次只载一个。然后用三五句话向用户复述：听到的想法是什么、打算怎么聊。
有偏差，用户此刻纠正的成本最低。

## 3. 采集纪律

- **方法论亮牌（决策点，必须问）**：按信号选主方法（可组合）：

  | 方法 | 信号 | 细则 |
  |---|---|---|
  | 视点分析（三层下钻） | 多干系人、业务流程复杂 | references/viewpoint.md |
  | 用例驱动 | 交互密集、流程分支多 | references/use-case.md |
  | 风险驱动分轮 | 需求模糊、决策短期不确定 | references/risk-mvp.md |
  | 原型驱动 | UI/体验说不清 | references/prototype.md |
  | 调研驱动 | 技术/外部依赖不确定 | references/research.md |

  开场亮牌"我建议用 X，因为 Y"；用户可否决、可中途换。确认后才 Read 该方法
  文件，一次只载一个。方法决定怎么聊，模板决定落成什么样。
- **分层采集**：按业务（为什么做/成功标准）→ 用户（谁/要完成什么）→ 系统
  （FR 逐条化）推进，每批 3–5 问，答案随聊随落盘——上一层答案决定下一层问什么。
- **校准阶梯**：开放问题按序处置，能停就停——① 查证（代码/文档/网上一搜就有
  → 自己查变事实，不问人）② 陈述句确认（查到了但涉意图 → 写成陈述句让用户纠错）
  ③ 决策卡 ④ 可点 HTML 原型（细则在 references/prototype.md）⑤ 转假设。
  每往下一级都是"逼用户凭空想象"的成本在上升。
- **决策卡**：要在 ≥2 个具体选项间选择、且查证解决不了的才升格；每 need ≤5 张，
  超了亮牌建议收窄。每卡必含：来源（哪条原话/场景逼出）、堵着什么（不决策堵住
  哪些 FR）、2–3 个具体选项（各带"长什么样"一行 + ✅/❌ 各一条）、选错的代价
  （写工作量，不评高下）、来得及改到何时、默认建议（理由引用用户自己的场景）、
  出口"说不清 → 转假设"。原则：概念归 AI，图例归用户。
- **查证过滤闸**：转假设前必问"5 分钟能查证吗？"能 → 查完变事实（进 FR/范围）；
  不能 → 才准转假设，并标注为什么（外部依赖/要花钱/要等人）。假设表里只剩真未知。
- **需求纯度**：每条 FR 指得回用户原话或拍板记录；你补写的一律标"假设"。
  FR 说"系统能什么"，不说"怎么实现"。新术语当场登记 GLOSSARY 项目术语章。

## 4. 出口门禁（全部通过才算完）

1. **三路归置**：每条开放问题必须有归属——有答案 → 写进正文对应节；答不了 →
   过滤闸后转「假设与风险」（按代价×不确定度排序）；明确不做 → 「范围与非目标」。
   节内只允许留拍板记录，一行一条：`D2 → 结论（一句理由；去向 FR-N/假设 An）`。
   "转调研"不许悬置：要调研的变 FR（调研报告是交付物）或转假设。
2. 用 need 模板落盘 `docs/needs/NNNN-slug.md`（id = 目录内最大号 +1，slug 用
   ASCII 小写短横线），运行 `.sdlc/check.sh validate docs/needs/NNNN-slug.md`
   必须通过；不过 → 修复后重跑。
3. **定稿（决策点，必须问）**：完整念一遍七节内容，请求确认。沉默不算确认，
   要改 → 回 §3 改完重念。通过 → `status: confirmed`、追加 `confirmed: <今日>`，
   重跑 validate 与 `.sdlc/check.sh publish`，提交留痕 `[trivial]`。
4. **出口**：抛决策问题："need NNNN 已 confirmed，建议 /dev-spec 开 round 1，
   范围可从假设与风险表中代价最高的圈起。"分轮归 dev-spec，只指路不代定。

## 5. 中断与交接

会话可能在任何时刻结束。凡是停下（等用户决策、上下文将尽、被卡住）：
已确认的答案写回 need 各节、未归置的留在开放问题，以 `status: draft` 落盘再停。
重入从 §1 续接——盘上的 draft 就是进度。状态在盘上，不在对话里。

## need 模板（固定）

```markdown
---
id: 0003
status: draft
created: <date>
---
# <标题>

## 背景与业务目标          ← 为什么做、可验证的业务目标、不做的代价
## 干系人与用户            ← Actor 全列出；谁、要完成什么、成功标准（可核销）
## 系统能力需求            ← FR-1、FR-2…（说"能什么"不说"怎么做"，条条可溯源）
## 场景                    ← 主流程 + 主要异常流（Given/When/Then）；异常流能指回决策卡
## 假设与风险              ← 过过滤闸的显式假设，按代价×不确定度排序，读得出 round 1 靶心
## 范围与非目标            ← 非目标全部来自显式拍板
## 开放问题                ← 清零 = 三路归置完成；可留拍板记录（D2 → 结论（去向））
```

## 禁止事项（任何时候）

- 替用户拍板，或把"说不清"悬置——说不清是合法出路，转假设进风险表。
- 发明需求：FR 指不回用户原话或拍板记录。
- 在 need 里写实现方案——怎么实现归 dev-spec / dev-design。
- 样品（HTML 原型）进仓库或接真数据；陪用户聊配色字体等视觉细节。
- 用户未显式定稿就把 `status` 写成 `confirmed`，或跳过 validate。
