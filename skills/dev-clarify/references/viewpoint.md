# 视点分析：业务/用户/系统三层下钻

dev-clarify 开场亮牌选中本方法后加载。适用：多干系人、业务流程复杂。
核心动作：逐层下钻——上一层答案决定下一层问什么，每批 3–5 问，答案随聊随落盘。

## 三层问题清单

### 业务层（喂「背景与业务目标」）
- 为什么是**现在**做？不做的代价是什么——谁每天多花多少时间/损失多少钱？
- 业务目标能不能说成一句可验证的话（带数字优先）："下单确认从 3 步变 1 步"，
  不是"提升下单体验"。
- 做成 90 天后，谁的哪个动作会不一样？（答不出来的目标不可验证）

### 用户层（喂「干系人与用户」）
- Actor 全列出：直接操作的人、只看结果的人、被数据波及的人（审批人/被通知者）。
  人和外部系统都算 Actor。
- 每个 Actor 一问：你现在怎么完成这件事（走查现状），哪一步最疼？
- 成功标准从 Actor 嘴里说出，不替他们说——将来 dev-accept 逐条核销的就是它，
  必须可验证（"导出在 5 秒内出文件"，不是"导出够快"）。

### 系统层（喂「系统能力需求」）
- 把上两层的答案逐条翻译成"系统能什么"（FR-N），一条能力一句话。
- 翻译时只留"能什么"，剥掉"怎么做"——出现表名/接口名/算法名就是越界，
  那是 spec 的活。
- 每条 FR 回指来源（原话/哪层答案）；模型自己补的标"假设"。

## 好/坏对照

- 好："库存不足时下单会发生什么？"——具体场景，答案直通 FR 与异常流。
- 坏："你对库存模块有什么需求？"——要用户替 AI 做分析，答案必然含糊。

## 落盘映射

业务层 → 背景与业务目标；Actor + 成功标准 → 干系人与用户；翻译产物 →
系统能力需求；层间冒出的选项冲突 → 决策卡；拍板不了的 → 查证过滤闸后
转假设与风险。

## 自查口令

这一层的答案指得回用户原话吗？下一层的问题是从上一层答案里长出来的吗？
三层下完，FR 拼得回业务目标吗？成功标准 dev-accept 拿来就能核销吗？
