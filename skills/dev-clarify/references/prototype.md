# 原型驱动：可点 HTML 原型操作法

dev-clarify 开场亮牌选中本方法后加载；其他方法聊到校准阶梯第④级（选项说不清，
尤其 UI/UX）也可临时加载。核心动作：与其逼用户凭空想象，不如做样品看着拍。

## 什么时候做样品

- 触发信号：用户说"说不好 / 大概是这样 / 画出来看看"；或决策卡上两个选项
  文字拉不开差距（只有看到才能分）。
- 媒介一行选：有界面 → 可点 HTML 原型（默认）；纯 CLI → 输出样例（输出就是
  CLI 的线框）；API/数据契约 → 调用序列 + 请求/响应样例。

## HTML 原型规格

- 单文件 HTML，CSS/JS 全内联，**零外部依赖**（不引 CDN，防离线/内网），≤200 行。
- 落系统临时目录（如 `/tmp/need-NNNN-mock.html`），**不进仓库**；环境支持内嵌
  预览就直接内嵌；给用户路径 + 打开命令（open / xdg-open）。
- **三态必须切换可看**（正常/空/错误，各一个切换钮）；主流程可点通（点击 →
  状态变化）；异常流有入口。两方案对比 → 同文件双 tab 或左右并排。
- 样品本身是提问：每个写不出来的格子（"空态显示什么？"）就是一个待决策点，
  逐个升格决策卡。空态和错误态是模糊需求的坟场，不许只画正常态。

## 防跑偏三条

1. 样式花在状态可见性上，不花装饰上；用户开始评配色圆角 → 亮牌"视觉细节
   不在澄清范围"，记开放问题或非目标。样品承诺的是结构与流程对不对。
2. vanilla JS 最笨实现（状态切换、假数据），不引框架——样品跑偏成工程的
   那一刻，澄清就成了偷跑实现。
3. 用完即弃：不进仓库、不接真数据；拍板后交互走查转写进 need 场景节
   （`Given 队列有失败构建，When 点[重跑]并确认，Then 插入队首且状态可见`），
   样品文件本身不留档——它换回的是拍板，拍板在盘上。

## 好/坏对照

- 好：空态页 + 三态切换钮——逼出"队列没任务时显示什么"这个真问题。
- 坏：三页精心配色的成品图——用户开始讨论字体，澄清跑偏成审美评审。

## 落盘映射

走查拍板的每一步 → 场景节 G/W/T；样品逼出的决策 → 决策卡 → 三路归置；
样品明确否掉的方案 → 范围与非目标（注明"原型否决"）。

## 自查口令

三态都能切出来吗？主流程不用解释就能点通吗？用户看完给的是拍板还是新的
形容？"写不出来的格子"都收进决策卡了吗？
