# 用例驱动：RUP 用例骨架走查

dev-clarify 开场亮牌选中本方法后加载。适用：交互密集、流程分支多。
核心动作：先圈用例清单，再对每个用例走 RUP 骨架——五个部件各喂 need 一节，
落盘同构不变。

## 用例清单（开工先画）

一行动词短语一条："领取任务 / 提交结果 / 退回重做"。请用户圈掉不属于本轮的——
圈掉的自然落「范围与非目标」。禁止不圈就开聊，防止范围失控。

## 用例骨架（每用例五部件）

1. **Actor**（谁在用）→ 干系人与用户节。主 Actor 发起用例，副 Actor 被波及；
   人和外部系统（支付网关、定时器）都算 Actor。
2. **前置条件**（用例开始前世界什么样）→ 场景节开头。
3. **主成功场景**（一路顺风怎么走）→ 场景节主线，逐步 Given/When/Then。
4. **扩展/异常流**（哪里会出错、谁会岔开）→ 场景节异常条目 + **决策卡原材料**：
   每条异常流追问一次"系统该自己兜，还是拦住问人？"——分歧就是一张卡。
5. **后置条件**（成功后世界什么样，可验证）→ 干系人与用户节的成功标准，
   dev-accept 将来逐条核销。

## 走查纪律

- 主场景先走"阳光路径"：**不许中途谈异常**，走通一条再回头收异常，
  防止一开工就散进边角。
- 异常流按三问收口：谁会发现、多久发现、发现后能干什么。
- 一个用例走完落盘一个用例，不攒——状态在盘上，不在对话里。

## 好/坏对照

- 好："提交结果时网络断了，草稿还在吗？"——具体异常流，直通 FR 与场景。
- 坏："系统要稳定可靠。"——不可验证，落不了任何节，是气氛不是需求。

## 落盘映射

Actor → 干系人与用户；前置 + 主场景 + 异常流 → 场景；后置条件 → 成功标准；
圈掉的用例 → 范围与非目标；异常流处置分歧 → 决策卡。

## 自查口令

每个 Actor 都有至少一条主成功场景吗？每条异常流都指得出决策卡或假设吗？
后置条件 dev-accept 拿来就能核销吗？
