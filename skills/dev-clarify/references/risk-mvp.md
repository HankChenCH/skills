# 风险驱动 MVP 分轮：假设排序操作法

dev-clarify 开场亮牌选中本方法后加载。适用：需求模糊、决策短期不确定。
核心动作：把模糊陈述变显式假设 → 四象限定级 → 排序。分轮范围决策归 dev-spec，
本方法只产出排序后的假设表和 round 1 靶心建议。

## 操作法

1. **假设化**：把每个"我们应该/大概/肯定"改写成可证伪句——"用户愿意每周
   录三次"不是需求是假设。每条写明：假设什么、错了伤谁、现在有多不确定。
2. **查证过滤闸**：转假设前必问"5 分钟能查证吗？"（读文档/看代码/搜一下）
   能 → 查完变事实进 FR 或范围；不能 → 才进假设表，标注为什么查不了
   （外部依赖 / 要花钱 / 要等人）。
3. **四象限定级**（错了代价 × 不确定度，每格一句动作指令）：

```
 错了代价
 高 │ ③ 先查证消掉             ① round 1 靶心
    │ （读码/调研，查完变事实，   （最小实验验证，
    │   不该以假设形态存在）      别的都别做）
    │
 低 │ ④ 随手拍板               ② 直接假设
    │ （不值得花一分钟）         （标"错了也不疼"，
    │                           忘了改也不心疼）
    └───────────────────────────→ 不确定度
```

   每条假设落一个格子；① 进 round 1 候选，②③④ 不进。
4. **排序落盘**：「假设与风险」按"错了代价 × 不确定度"从高到低排，每条一行：
   假设内容 / 哪个格子 / 错了伤什么 / 怎么验证。

## 好/坏对照

- 好：`A2 事件驱动的插件 API 形状可用（高代价×高不确定 → ①）——round 1 用
  10 行加载器验证，定不了就退钩子链方案`——可证伪、有验证动作。
- 坏："存在一定的技术风险。"——不可证伪，是气氛不是假设。

## 落盘映射

假设表 → 假设与风险；②④ 的随手拍板 → 对应 FR 或范围；① 的清单 → 定稿出口
时递给 dev-spec 当 round 1 范围建议；"明确不做但用户犹豫" → 决策卡。

## 自查口令

每条假设都可证伪吗（能设计一个实验证明它错）？表读完能说出 round 1 靶心吗？
有没有本该查证却被懒成假设的（过滤闸回查一遍）？
