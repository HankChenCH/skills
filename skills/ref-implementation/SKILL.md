# ref-implementation：什么是好的实现

总标准只有一条：**下一个人（未来的你、你的协作者、AI）能顺着读下去、改得动、改了不怕。**
以下每条都是它的分解，评审与实现共用同一份标准。

## 标准

1. **代码读起来像叙事**：函数按"做什么"的顺序组织，读主路径不需要来回跳转；
   分支是主叙事的插入语，不是迷宫。
2. **命名表意**：名字承载意图（`failedRows` 而不是 `data`）；名字与类型、单位、边界
   一致；不需要展开注释才能看懂。
3. **模块深**：接口窄、做的事多（Ousterhout《软件设计的哲学》）。暴露得少、解决得完整；
   浅模块（接口一大把、每个只干一点）是复杂度扩散的主因。
4. **错误处理显式**：失败路径是写出来的，不是"不会发生"——校验、边界、IO 失败都要有
   归宿；错误上抛时带上"发生在哪、为什么"的上下文；不吞错、不静默降级。
5. **边界情况被处理，而不是被注释**："这里假设 x 永远为正"是缺陷——要么代码保证它，
   要么处理它不成立的情况。
6. **无投机泛化**：只写当前工单需要的抽象。为想象中的未来加的参数、层级、配置项是
   负债（YAGNI）；第二个调用方出现时，你才知道该泛化什么。
7. **diff 最小化**：只改工单要求的事。顺手格式化、顺手重构会把评审与回滚成本放大
   数倍——想重构，开新工单。

## 范例（好 / 差对照）

差（浅模块 + 吞错）：

```ts
function process(input: any) {
  try { return doA(input); } catch (e) { /* 忽略 */ }
  return null;
}
```

接口说不清做什么，失败被静默吞掉，调用方拿到 `null` 无法分辨"没数据"还是"坏了"。

好（深模块 + 显式错误）：

```ts
export function parseLedger(raw: string): Ledger {
  const rows = raw.split("\n").map(parseRow); // parseRow 失败即抛，错误带行号
  return { rows, total: sumAmounts(rows) };
}
```

接口一句话说得清（文本进、账本出），校验与汇总都在里面，错误可定位到行。

差（投机泛化）：只有一个调用方，却写 `merge(lists, dedupeFn?, compareFn?, onConflict?)`。
好：写死当前需要的 `mergeTagLists(a, b)`；等第二个调用方出现再泛化。

## 自查口令（每完成一个验收标准过一遍）

读一遍刚写的 diff：错误路径有归宿吗？边界进了代码还是只进了注释？新名字脱掉上下文
还表意吗？有没有哪一行不属于这张工单？
