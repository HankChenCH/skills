# dev-accept 需求使用方视角验收 + dev-execute 右臂打通

## 背景与业务目标

用户原话（2026-11-08）：

1. "最近一次使用 execute 无人值守，停在最后 accept，调用只跑脚本，没有证据证明确实实现完了，还要人去看。"
2. "最近几次实现，会有 1、2 次要返工（就算验收通过了）。"
3. "我希望 dev-accept 能真正找出问题（功能缺失或不符合预期而不是鸡蛋里挑骨头）。"

现状痛点（量化）：

- dev-accept 验收 = 实现者视角：在集成后代码上逐条跑 spec 集成级场景 + `check.sh all`，证据是命令输出；界面 FR 只要求"对照述标观察"，不要求实际操作界面（dev-accept SKILL.md §3）。
- dev-execute 收口止于指路手动 /dev-accept，不自动调用（dev-execute SKILL.md §9；出处：spec 0006 拍板"收口不自动调 dev-accept，用例圈定圈掉"——本 need 显式推翻该拍板，见 D2）。
- 用户每次交付后人工动作 = 手动跑一次 /dev-accept + 自己上手点一遍，耗时 ≥30 分钟。
- 验收 passed 的交付仍出现 1–2 次/最近几次的返工；返工问题类型 = **行为不符合预期——脚本跑通，但人在操作上不对**（用户 2026-11-08 答复）。

业务目标（可验证）：

- 验收 **passed** 的交付，需求方上手试用时不再发现"功能缺失 / 行为不符合预期"类硬伤。
- 验收报告里挂掉的问题以硬伤为主，而非样式、措辞类形式化挑剔。
- 有原型关联的交付：原型设计场景的功能基本完成，可以更优化但不能更差（用户 2026-11-08 补充）。
- 用户人工验收投入从"手动跑 /dev-accept + 上手点一遍 ≥30 分钟"降到"只做 need 置 fulfilled 的最终确认"。

## 干系人与用户

| 角色 | 要完成什么 | 成功标准 |
|---|---|---|
| need 提出人 / 干系人（验收视角主体，用户 2026-11-08 拍板） | 拿到以使用方实际操作为证据的验收报告，直接判断"我要的东西交付了吗" | passed 交付上手试用无"功能缺失 / 不符预期"硬伤；人工投入只剩最终确认 |
| dev-execute 编排会话 | 合并 done 后自动串联验收（D2）；把使用方视角材料（不含实现上下文）交给隔离代理 | 收口到验收报告产出全自动衔接；人工交互恰两次（开工确认 + 合并确认）不变 |
| 隔离验收代理（AI 扮演使用方） | 只装使用方视角材料，按介质实操走查、对照原型、给问题分级、出报告 | 报告自证（证据 = 实操记录），无人值守下判 passed/rejected 不需人到场 |
| 拍板人（need 提出人本人） | 验收 passed 后确认 need 置 fulfilled（含逐条接受残余风险） | 沉默不算接受；无未核销标准、无未接受风险才置 fulfilled（现行纪律不变） |

## 系统能力需求

- **FR-1 使用方视角验收**（源：原话3 + 返工解剖）：验收证据以**需求使用方实际操作**为主来源——涉及用户操作的集成级场景，按用户操作路径实操走查后判过；只有自动化脚本绿灯、无实操证据的操作类场景**不得判过**。
- **FR-2 实操介质选择**（源：D3）：Web 交付 → 浏览器自动化真实操作（打开、点击、输入，截图 / 操作记录取证）；CLI → 真实终端调用；API/库 → 真实调用取输出；文档 → 打开阅读。
- **FR-3 降级不降标准**（源：D3）：宿主缺浏览器能力 → 脚本 + 启动服务 + 截图证据，报告声明降级。
- **FR-4 原型基线核销**（源：用户 2026-11-08 补充）：功能关联原型（design 述标 + `docs/designs/assets/` 可点原型）时逐原型场景实操对照——原型场景功能**基本完成为过；缺失或比原型差为挂（硬伤）；实现优于原型为过**。
- **FR-5 问题分级**（源：原话3"鸡蛋里挑骨头"）：硬伤（功能缺失 / 操作行为不符预期 / 比原型差）→ 阻塞、rejected；瑕疵（不影响完成任务的样式、文案、措辞类偏差）→ 不阻塞 passed，写进残余风险与下一轮建议。
- **FR-6 收口自动串联**（源：D2）：dev-execute 合并 done 后自动启动 dev-accept——有人值守按 dev-accept 现行交互走，无人值守全自动跑完出报告；人工交互仍只有开工确认 + 合并确认两次。
- **FR-7 无人值守判定权**（源：D1）：无人值守下 AI 判 passed/rejected；need 置 fulfilled 留人确认（沉默不算接受残余风险）。
- **FR-8 证据形态**（源：原话1"没有证据证明确实实现完了，还要人去看"）：报告场景结果行的证据 = 实操记录（截图路径 / 操作序列 / 命令与输出）原样引用，口径是"使用方能完成任务"；无人值守报告无需人到场即可自证。
- **FR-9 上下文隔离验收代理**（源：用户 2026-11-08 补充"避免被实现上下文污染"）：验收执行由独立代理承载（评审轴清单制同款模式，spec 0016），代理装载材料限使用方视角清单——need 全文、spec 验收场景、design 述标与原型、交付物本身；不装载实现过程材料（工单 Progress、实现交接、实现会话上下文）。无子代理宿主降级为单上下文亲做并声明降级。

## 场景

**UC-1 收口后自动验收（主成功场景）**
Given dev-execute 运行全绿、合并确认通过、全部票 done
When 清理完成
Then 自动启动 dev-accept：有人值守按现行交互（复述 → 实操 → 判定 → 报告 → 收口序列），无人值守全自动跑完出报告
后置：验收报告落盘 docs/acceptance/，passed → spec 置 done，rejected → 指路 dev-fix（现行链路，UC-7 不改）

**UC-2 使用方实操走查（主成功场景）**
Given 隔离验收代理只装载使用方视角材料（FR-9 清单）
When 逐条执行集成级场景
Then 按介质实操（FR-2）：Web 交付打开浏览器按用户操作路径点击、输入，截图取证；CLI/API 终端调用取输出
And 判过以实操证据为准（FR-1、FR-8）
异常流：宿主无浏览器能力 → 降级路径（FR-3）+ 报告声明降级

**UC-3 原型对照核销（主成功场景）**
Given FR/场景关联原型
When 逐原型场景实操对照
Then 按 FR-4 基线核销：基本完成 → 过；缺失或比原型差 → 挂（硬伤）；更优 → 过
异常流：无述标（无 design 产物）→ 按工单验收标准核销，报告注明"无述标"（现行降级不降标准纪律，保留）

**UC-4 问题分级判定（主成功场景）**
Given 实操走查发现偏差
When 定级
Then 按 FR-5：硬伤 → rejected；瑕疵 → 残余风险与下一轮建议，不阻塞 passed

**UC-5 无人值守验收出口（主成功场景）**
Given 无人值守运行验收完成、AI 判 passed（D1）
When 走收口序列（蒸馏 / 清扫 / spec 置 done）
Then need 置 fulfilled 停点等拍板人确认（FR-7）
异常流：拍板人回来不认可结论 → 与有人值守同路径返工（dev-fix / 下一轮）

## 假设与风险

- **A1 降级路径的证据强度**（源：FR-3）：宿主无浏览器能力时"脚本 + 截图"证据弱于真实操作，硬伤检出率可能下降。代价：中；不确定度：低（降级策略已拍板）。转假设原因：宿主能力矩阵随环境变化，实现期按宿主探测。缓解：报告强制声明降级，拍板人知情后自行决定是否人工补验。
- **A2 隔离材料清单的边界**（源：FR-9）：need 层只定原则（不含工单 Progress / 实现交接），"使用方视角材料"的逐项清单归 spec 定；清单画错（如把 design 述标误当实现材料排除）会伤核销质量。代价：中；不确定度：低。
- **A3 验收时机锁定**（源：D2）：合并即验收意味着无法"放几天再验"——D2 已拍板接受；若实际使用反悔，出口报告加"暂缓验收"选项可补，代价小。

round 1 靶心（读法）：FR-1 / FR-5 / FR-9 是"passed 无硬伤"的最大杠杆（视角 + 分级 + 隔离三位一体）；FR-2 / FR-3 / FR-4 是介质与原型细则；FR-6 / FR-7 是串联与判定权。

## 范围与非目标

- 非目标 ①：rejected → dev-fix 链路不改（UC-7，用户确认用例清单时接受"本 need 不改"标注）。
- 非目标 ②：评审轴隔离机制不重复建设——spec 0016 已交付，验收隔离复用其模式（"每轴恰一个独立子代理、只装本轴材料"）。
- 非目标 ③：dev-implement 纪律不改（实现侧红绿循环与本 need 无涉）。
