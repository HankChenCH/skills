# setup-workspace 多仓工作区接入（根目录非仓库 + 多个子仓库）

## 背景与业务目标

现状：setup-workspace 前置校验 `git rev-parse --show-toplevel` 必须成功，失败即拒绝
（skills/setup-workspace/SKILL.md §0）；仓库形态只有单仓 / monorepo 两种
（skills/setup-workspace/references/scan-signals.md §1），全部基础设施
（`.sdlc/`、`docs/`、AGENTS.md、GLOSSARY、git hooks）锚定在唯一的仓库根。

增补场景（用户 2026-10-29 确认）：入口目录本身不是 git 仓库，其下平铺多个独立子仓库，
每个子仓库各自是单仓或 monorepo；子仓库是多个相关服务（如前端 + 后端 + 上游微服务）
各自 clone 到同一父目录。规模两档：小型项目 2–4 个子仓库，大型项目 8 个以上。

关键事实（查证 + 拍板，2026-10-29）：

- 锚点假设是技能家族全局的：dev-clarify、dev-spec、dev-plan、dev-implement、
  dev-review、dev-fix、dev-accept、dev-release、dev-ship、sdlc 路由全部以相对路径
  调用 `.sdlc/check.sh`，隐含"当前仓库根下有 `.sdlc/`"。
- "根目录不是仓库"是现状而非硬约束，允许把根目录 git init（用户拍板）。
- 跨仓库需求经常发生：典型如前后端分离（前端界面 + 后端接口）并串联调用上游微服务。
  因此"各子仓库完全独立接入"形态因跨仓库需求无处归置而出局。

不做的代价：该形态的工作区无法接入 SDLC 流程；若强行按现行逻辑在某个子仓库内初始化，
流程产物与门禁只覆盖单个子仓库，高频跨仓库需求没有归置。

## 干系人与用户

| Actor | 角色 | 成功标准（dev-accept 逐条核销） |
|---|---|---|
| 开发者（主） | 在多仓工作区工作，发起初始化与日常流程 | S1、S2、S3、S4、S5 |
| 智能体（主） | 执行 setup-workspace 与技能家族流程 | S1、S6 |
| 新加入的开发者（副） | clone 全部仓库后复原接入 | S7 |
| 成员子仓库（副，受波及） | 其 git 提交行为被门禁覆盖 | S3、S5 |

成功标准（可核销后置条件，B4 原话"sdlc 流程正常执行，规划需求时能联动下面子仓库"
的具体化）：

- S1 根会话可用：在工作区根目录开会话，/sdlc 能正常输出 phase/frontier，
  行为与今天的单仓接入一致。
- S2 跨仓库需求归置：立"前端界面 + 后端接口"类需求时，need/spec/工单全部落在
  根 docs/，工单能点名受影响的子仓库清单。
- S3 子仓提交被校验：在任一成员子仓库提交：不带工单号 → 被拒；带有效工单号
  （存在于根 docs/tickets/）→ 放行；Merge/Revert 头 → 机械放行。
- S4 初始化产出：在根目录跑 /setup-workspace 后：根变成 git 仓库并带全套基础设施；
  成员清单落盘；每个成员子仓库装上门禁 hook 和 AGENTS.md 哨兵。
- S5 幂等重跑：重跑 /setup-workspace 按成员清单 diff 报告增补/移除（缺失经确认才移出），
  已接入物按所有权表报告覆盖/保留（现行升级语义沿用）。
- S6 回根引导：在成员子仓库内开会话，AGENTS.md 哨兵能告知智能体
  "本仓库是工作区成员，流程操作去根目录"。
- S7 新环境复原：新同事 clone 根仓库与全部成员子仓库后，重跑 /setup-workspace
  能按清单恢复全部接入物。

## 系统能力需求

（每条溯源到用户原话或拍板记录，见「开放问题」拍板行。）

- FR-1（UC1/B2）：setup-workspace 能在"根目录非 git 仓库、且根下第一层存在
  git 仓库"的目录完成初始化；"根非仓库且无任何子仓库"仍维持拒绝。
- FR-2（C1）：能将根目录 git init 为工作区仓库，按现行资产生成逻辑落全套基础设施
  （`.sdlc/`、`docs/`、AGENTS.md、GLOSSARY、CODING_STANDARDS、根 hooks）。
- FR-3（C4）：能扫描根下第一层 git 仓库形成成员候选清单，经用户确认后落盘；
  非成员目录不受门禁、不被扫描。
- FR-4（C3）：成员子仓库的提交能被门禁校验：提交信息须含存在于根 `docs/tickets/`
  的工单引用，否则拒绝提交。
- FR-5（E1）：门禁能机械放行 Merge/Revert 头的提交（git 自动生成信息可识别）。
- FR-6（C2）：能为每个成员子仓库落 AGENTS.md 哨兵，内容含成员身份与回根指引
  （流程操作去根目录）；技能家族的 check.sh 调用方式不变。
- FR-7（UC2/E2）：重跑能按成员清单 diff 报告增补；发现成员目录缺失或不再是
  git 仓库时报告并经确认才移出清单。
- FR-8（S7）：在新环境（clone 根仓库与成员子仓库后）重跑能按清单恢复全部接入物。
- FR-9（UC6/B3）：工单能点名受影响子仓库清单，作为跨仓库需求的归置载体。
- FR-10（UC4）：接入后新 clone 进根目录的仓库，重跑时进入候选确认，确认后入册
  并补装门禁与哨兵。

## 场景

主流程一：初始化多仓工作区（UC1；对应 S4）

- Given 根目录不是 git 仓库，其下第一层有 3 个 git 仓库（frontend、backend、gateway）
  和 1 个普通文档目录。
- When 用户在根目录运行 /setup-workspace。
- Then 识别为多仓工作区形态；扫描第一层列出成员候选；用户确认 3 个仓库入册、
  文档目录不入册；根目录 git init 并落全套基础设施；成员清单落盘；
  3 个成员子仓库各装上门禁 hook 与 AGENTS.md 哨兵。

主流程二：跨仓库需求的全流程（UC6+UC5；对应 S1、S2、S3）

- Given 工作区已按主流程一接入，成员含 frontend 与 backend。
- When 用户在根目录开会话立一个"前端界面 + 后端接口"需求，走完 need → spec → 工单。
- Then 全部流程产物落在根 docs/，工单点名受影响子仓库 frontend、backend；
  实现在 frontend 与 backend 内分别提交带该工单号的 commit，两边 hook 均放行；
  根目录 `.sdlc/check.sh all` 对全仓流程产物与检查兜底。

异常流：

- 成员子仓库提交不带工单号（非 Merge/Revert）→ hook 拒绝，报出缺工单引用；
  Merge/Revert 头 → 机械放行（E1 → FR-4/FR-5/S3）。
- 重跑时某成员目录消失或不再是 git 仓库 → 报告异常条目，用户确认后才移出清单；
  未确认前清单保持不动（E2 → FR-7/S5）。
- 会话开在成员子仓库内 → 哨兵告知"本仓库是工作区成员，流程操作去根目录"；
  不做流程操作则正常改代码（C2 → FR-6/S6）。

## 假设与风险

（已过过滤闸：以下各项均属"5 分钟查证不了的用户意图/外部行为"，故留为显式假设。
验证结果折回自验收报告 0001，round 1，2026-10-29。）

- A1 扫描边界（E3 转假设）：只扫根下第一层 git 仓库；成员内部的嵌套 git 仓库
  （含 submodule）属于成员代码，不收编为成员。代价低：真出现嵌套收编需求时另立项。
  （验证：通过——点目录上游不入候选，rev-parse 解析回目录自身才算候选。）
- A2 非成员目录：根下非 git 目录（文档/脚本/无关 clone）不是工作区成员，
  初始化不写入、不门禁、不扫描（UC3 的前提）。（验证：通过——夹具实测不入候选、
  零写入。）
- A3 外来 hooks：成员子仓库已有非本体系 hooks 时沿用现行规则——不覆盖，
  报告并给手动合并方案。（验证：本轮未触发——处置成文有契约断言，行为实测待
  真实外来 hook 出现。）
- R1 大工作区确认成本：8+ 成员逐个确认交互轮次多。缓解方向归 spec
  （如批量确认后个别调整）；不影响 FR。（验证：通过——缓解落地，决策 4 一轮
  交互、默认全入册、只点名排除。）
- R2 哨兵可达性：子仓内会话能否加载哨兵取决于各智能体对 AGENTS.md 的加载行为
  （cwd 及祖先链）。哨兵落在子仓库内（而非仅依赖根）即为此缓解；个别不读
  AGENTS.md 的智能体仍可能看不到指引——届时回退为用户手动回根，不阻塞主流程。
  （验证：通过——哨兵落成员仓内三态实测；不可自动化残余见残余风险。）

残余风险（折回自验收报告 0001，均不阻塞）：个别不读 AGENTS.md 的智能体在成员仓
看不到回根指引（回退：用户手动回根）；外来 hooks 处置未经行为实测（成文与契约
断言在册）；tracker 投影依赖平台认证（gh 未认证时警告跳过，盘上真相源不受影响）。
