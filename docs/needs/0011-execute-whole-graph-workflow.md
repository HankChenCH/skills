# dev-execute 档 1 整图单运行

## 背景与业务目标

need 0010 / spec 0012（票 0020–0023）落地后实测：ZCode 命中档 1（声明式工作流）时，派发形态为**每张就绪票一个工作流运行**（`skills/dev-execute/references/run-mechanics.md` §4）。4 票 spec（票 1–3 同层可并行、票 4 blocked-by 前三票）实测观测（用户 2026-10-31 原话）：「1-3 分别开工作流，4 在开工作流」——运行依赖顺序图只活在主会话编排逻辑里，用户看到的只是 N 个散落运行；且按 CreateWorkflow 工具契约每次运行都需用户确认，N 票 = N 次确认。

已查证事实（本机一手来源，2026-10-31）：

- 档 1 现形态是设计决策，非缺陷（run-mechanics §4「形态：每张就绪票一个工作流运行承载其实现子代理……运行结算通知 = 该票完成通知」）。两个理由：每票完成通知事件驱动先行评审、不轮询；与档 2–4 同构，回退链只换原语不换编排模型。
- 现形态下每个工作流脚本仅含一个 `agent()` 调用、零控制流——原语的执行图能力全部闲置。
- ZCode 捆绑 dynamic-workflows 技能明确支持（`/Applications/ZCode.app/Contents/Resources/glm/packages/bundled-skills/skills/dynamic-workflows/SKILL.md`）：`Promise.all` fan-out/join 表达并行与依赖，含「逐票阶段链在 fan-out 内串、最后 join 一次」的流水线写法（与流水线合回同构）；`world.run` 确定性门可承载预演 `.sdlc/check.sh all`；`git.*` 门面可承载合回；升级提问与类型化洞穴承载运行内停下问人；journal 重放 + AmendWorkflow 承载续接与修脚本复用已完成步；`max_concurrency` 把并行度上限下沉给引擎。
- CreateWorkflow 工具契约：每次运行需用户确认（受宿主权限模式影响）。
- 工作流子代理工具面无障碍："Every subagent has the same tools"（dynamic-workflows SKILL.md），承载 dev-implement 纪律全文无工具面缺口。

业务目标（2026-10-31 拍板 D2）：档 1 命中时，一次 dev-execute 运行呈现为一张工作流执行图——下称**整图单运行**（一张运行依赖顺序图声明为一个工作流运行，同层并行与跨层依赖由脚本控制流表达）。以 4 票 spec 计：用户确认次数 N → 1；执行图可见性无 → 有（一次运行内可看到全部票的推进）。

## 干系人与用户

- 编排用户：发起 dev-execute 运行的人。现每票确认一次、看不到整图；目标一次确认、看图推进。成功标准可核销：一次运行的 CreateWorkflow 调用数 = 1。
- 实现子代理：每票一个，在票 worktree 执行 dev-implement 纪律全文，由工作流脚本派发。
- 评审承载：先行评审在图内进行，承载形态归 spec（A2）。
- 编排主会话：从逐票派发者变为整图声明者 + 运行外守护者（响应升级提问、异常流决策）。
- 其他宿主会话：档 2/3/4 形态与行为零变化（拍板 D2 只涉档 1）。

## 系统能力需求

- **FR-1 整图单运行**：档 1 命中时，dev-execute 能把整张运行依赖顺序图声明为一个工作流运行（开工确认中单次确认），同层票并行、blocked-by 边由脚本控制流表达。〔源：用户原话「一个工作流排好执行图」「1-3 开启并行，4 在他们后面执行」；拍板 D2〕
- **FR-2 逐票先行评审不回退**：图内每票实现完成即在图内先行编排评审，不等同层其余票；依赖满足即推进合回，流水线合回语义在档 1 内保持。〔源：need 0010 FR-3/FR-4 延续；用户场景「4 在他们后面执行」〕
- **FR-3 预演确定性门**：图内每次合回后预演（`.sdlc/check.sh all`）由脚本门承载，绿灯才放行后续票合回与派发。〔源：need 0010 FR-4 延续〕
- **FR-4 人工门与异常流零回退**：合并确认单向门仍必须问人，§8 异常流仍停下问人——承载方式迁移到升级提问/洞穴，语义不变（沉默不算确认、绝不自动解冲突、绝不自动重试）。〔源：dev-execute §6.3/§8 既有门禁〕
- **FR-5 档间差异声明**：开工确认声明与 run-mechanics §4 明示档 1（整图单运行）与档 2–4（逐票派发）的编排模型差异及原因。〔源：拍板 D2 连带后果，我补写 → A4〕

## 场景

主流程：

- **场景 1（整图推进）**：Given 一张 4 票 spec（票 1–3 同层、票 4 blocked-by 前三票），When 档 1 命中且用户开工确认，Then 全程恰好一次 CreateWorkflow 运行：票 1–3 并行实现、各自完成即图内先行评审，票 4 在依赖满足后由图推进，用户看一张图到运行全绿。
- **场景 2（决策点叫人）**：Given 运行中到达合并确认或触发 §8 异常流，Then 工作流以升级提问/洞穴停下问人，用户答完运行续走；等待期间主会话可响应用户其他输入。
- **场景 3（中断续接）**：Given 运行中断（用户喊停/进程退出），Then 按 §7 盘上状态机（票 frontmatter + worktree）推导断点，结合工作流 journal 重放/AmendWorkflow 续接，已合回票不重做。

异常流：

- **异常 1（整图承载不成立）**：开工探测发现整图形态不可用（脚本能力缺失或运行即错）→ 按既有回退链降档运行，不硬失败；兜底形态归 spec。〔假设 A1〕

## 假设与风险

- **A1（我补写）**：整图承载失败时的兜底形态（退回档 1 逐票形态，或直接降档 2）未拍板——归 spec/design。
- **A2（设计风险）**：dev-review 编排评审在图内的承载形态未定（子代理执行评审纪律，或通知主会话介入）——工具面已确认无障碍（一手来源），形态归 spec/design。
- **A3（设计风险）**：§8 异常流「fix 票入图重算」在运行内的承载未定（可能需 AmendWorkflow 修脚本）——归 spec/design。
- **A4（代价，D2 已接受）**：四档同构打破——run-mechanics §4 重写、开工确认声明增差异说明、演练记录补整图形态；一次性文档成本。
