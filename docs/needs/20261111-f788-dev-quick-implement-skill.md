# dev-quick-implement：小改动快速实现通道

## 背景与业务目标

现有管线（dev-clarify → dev-spec → dev-plan → dev-implement → dev-review → dev-ship → dev-accept）对「表格字段 A 改 B」这类小而真实的代码改动过重：每个环节各停一次等人确认，交互成本与改动体量不成比例。而 [trivial] 豁免只限 typo 与纯文档改动，改代码走不了——两者之间存在一条真空地带：改动是真的（需要工单号过 commit-msg 门禁），但流程成本远超改动本身。

业务目标（可核销）：一次准入通过的小改动，从用户发起到合并完成，**全程恰 2 次人工交互**——1 次开工确认 + 1 次合并确认；其余环节（产物自产、实现、检查、评审、收尾）全部自动完成。不做的代价：这类改动要么硬走完整链（流程税），要么被塞进 [trivial] 滥用（绕过追溯），要么在对话里改掉不留产物（破坏「状态在盘上」）。

## 干系人与用户

- **开发者（唯一 Actor，即用户本人）**：有一句话能说清的小改动想法（改名、改文案字段、调参数、小修样式），要完成「改完、验过、合入主干」，成功标准 = 全程只被打断 2 次、产物齐全可追溯。
- **dev-retro（间接干系人）**：审计 quick 通道是否被滥用（准入门是模型自判，无机械判据，审计是唯一兜底）。
- **完整链技能（间接干系人）**：准入门拒绝的请求必须指路到 dev-spec / dev-clarify，不悬置。

## 系统能力需求

- **FR-1 入口**：用户显式调用 `/dev-quick-implement` 并附一句话改动描述即触发；不进 sdlc 自动串联链（next-mode 路由表不加行），完整链技能不自动路由进它。
- **FR-2 准入门**：三道门依次判定——①简单（改动面小、单一概念、无新依赖、无 API/数据契约破坏）②低风险（现有测试可覆盖、可快速回滚）③不违反已有 ADR（读 docs/adr/ 全量与改动面对照）。判定方式 = 模型结合需求描述与代码实际情况综合评估；技能文本内置 rubric 作判断辅助，不作机械门禁。**每次判定必须留痕**（判定理由 + 三道门逐门结论，写进产物备注）。
- **FR-3 拒绝路径**：任一道门不满足 → 当场拒绝，明说卡在哪道门（简单？低风险？ADR N？），指路完整链入口——需求清楚的指 dev-spec，需求本身模糊的指 dev-clarify。
- **FR-4 产物自产**：准入通过后自动产出**真实产物三件套**——真实 need、真实 spec（round 1 单轮）、单张工单，全走固定模板落盘 docs/ 对应目录，validate/publish 照跑；每次 quick 运行立自己的三件套，不设伞形 need。
- **FR-5 确认打包**：开工确认一次覆盖——准入判定结果展示 + need 确认 + spec 批准 + 票概览；用户一次批准即完成 need → confirmed、spec → approved 的状态推进，不再各停一次。沉默不算确认。
- **FR-6 实现**：单工单按 dev-implement 纪律实现（垂直切片、红绿测试），出口 check.sh all 全绿。
- **FR-7 独立子代理快评**：实现全绿后 spawn 独立子代理，按 dev-review 标准轴做精简评审，产出 approved 评审报告；非 approved → 按评审意见返工再评（不新增人工交互，返工在 2 次交互预算内消化）。
- **FR-8 交付停点**：PR 准备就绪（Summary / Evidence / Merge Danger 三节）后停下等合并确认；Evidence 打包验收证据——check.sh all 全绿输出 + spec 验收标准逐条勾 + 评审报告摘要。合并是单向门，由用户亲手点。
- **FR-9 自动收尾**：合并确认通过、执行合并后零交互自动收尾——工单 done、spec 置 done、过程档清扫、原子提交；蒸馏折回仅在确有蒸馏目标时做，无目标跳过并留注。
- **FR-10 兜底审计**：每次 quick 运行的准入判定留痕可被 dev-retro 审计（与 [trivial] 豁免审计同构），发现滥用在 retro 报告中记录并收紧。

## 场景

**主流程**（准入通过）：
- Given 开发者有一个一句话能说清的小改动想法
- When 调用 `/dev-quick-implement` 附改动描述
- Then 模型读代码现状与 docs/adr/，三道门逐门判定并留痕 → 通过则自动产出 need + spec + 工单三件套（validate 通过）→ 开工确认（人工交互 1/2：准入结果 + 三件套一并呈现）→ 批准后按 dev-implement 纪律实现 → check.sh all 全绿 → 独立子代理快评 approved → PR 就绪（Evidence 含验收证据包）→ 合并确认（人工交互 2/2）→ 执行合并 → 自动收尾（票 done、spec done、清扫、原子提交）

**异常流 1（准入拒绝，指回 FR-2/FR-3）**：Given 改动不满足任一道门（如触碰 ADR 0003 裁决、或改动横跨多模块不「简单」）When 准入判定 Then 当场拒绝，逐门说明卡点，指路 dev-spec / dev-clarify，不产任何产物。

**异常流 2（快评不 approved，指回 FR-7）**：Given 子代理评审提出意见 When 返工修正再评 Then 循环至 approved 或判定问题超出「简单/低风险」范畴 → 停止并转完整链（此时已产三件套，从 dev-spec 修订续走）。

**异常流 3（检查不绿，指回 FR-6）**：Given check.sh all 失败 When 修复重跑 Then 修绿继续；反复修不绿 → 停，转 dev-fix 或完整链，不硬闯。

**异常流 4（开工确认被拒）**：Given 用户在开工确认时不批准 When 拒绝 Then 三件套草案落盘不废弃（可修订续走完整链），实现不开始。

## 假设与风险

- **A1 准入自判可能误放行**（判定过松，把不简单的改动放进快车道）：代价中——污染主干风险由合并门人工兜底，但审计成本上升；不确定度中。兜底 = 留痕 + retro 审计。**round 1 靶心之一：准入 rubric 文本质量与拒绝案例积累。**
- **A2 独立子代理快评弱于人工评审**：代价低——合并门仍有人看 Evidence；不确定度低。评审报告摘要进 Evidence 使人可抽检。
- **A3 假设 [trivial] 语义不变**（typo/纯文档继续走豁免通道），quick-implement 只吃「小但真改代码」地带，两通道互补不重叠。
- **A4 假设现有机械门禁零改动即可承载**：commit-msg 要求 [#YYYYMMDD-4hex] 票状态合法——quick 票按正常状态机流转（ready → in-progress → implemented → done）即满足；pre-push 要求 implemented 票有 approved 评审覆盖——子代理快评报告即评审产物，满足。无需改 check.sh。

## 范围与非目标

**非目标**（全部来自显式拍板）：
- 不自动合并——合并单向门永远留人亲手点（D3）。
- 不替代 [trivial]——typo/纯文档继续走豁免通道（D2）。
- 不设伞形 need——每次运行立自己的三件套（D8）。
- dev-accept 不进 quick 链——验收证据折叠进合并确认 Evidence，正式验收手动跑（D6）。
- 不改 check.sh 机械门禁——快评方案保持门禁零改动（D4 推论）。
- 不进 sdlc 自动串联链——仅手动触发（S1）。
