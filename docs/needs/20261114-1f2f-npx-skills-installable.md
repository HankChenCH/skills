# 一条命令把套件技能安装进目标项目的 .agents/skills

## 背景与业务目标

本套件当前唯一的安装方式是人肉拷贝：README《快速上手》第 1 步要求使用者「把 skills/ 下各子目录拷贝或软链到智能体的技能目录（ZCode 为 `~/.zcode/skills/`）」（README.md:50，2026-11-14 检索）。31 个技能逐个拷贝，路径因智能体而异，接入门槛高、易装错版本、无升级路径。

需求发起人（套件维护者）的目标：用户在自己项目的仓库根目录跑一条 npx 命令，技能就被安装进该项目的 `.agents/skills/`。可验证目标：在一个全新 git 项目目录内，一条命令执行完后 `.agents/skills/` 下出现套件技能目录，项目内智能体（ZCode / Claude Code）能发现并调用它们；一条命令可升级。不做的代价：外部用户接入停留在手工拷贝，套件传播受限，装完的版本与上游漂移无从对账。

**内联查证关键结论（2026-11-14，本机实测）**：生态内已有现成安装器 vercel-labs/skills CLI（`npx skills add <owner>/<repo>`，开源），对本仓库**零改动即可跑通**——发现（`--list` 列出全部技能，中文 description 正常展示）与项目级安装（技能落 `./.agents/skills/`，对检测到的 agent 目录建软链，`./skills-lock.json` 记账）均实测通过；可作为行为参照与降级备选。**发起人拍板（2026-11-14）：不走生态 CLI，自建 npm 命令行**——命令名、安装行为、升级机制自可控。另实测：npm registry 本机可达（4 个候选包名查询均正常返回），而 GitHub 直连克隆 300s 超时——npm 发布渠道对国内网络显著更友好。

## 系统能力需求

- **FR-1** 套件提供自建 npm 命令行（套件专属资产安装器），使用者在本仓库之外的目标项目根目录跑 `npx @hankghchen/skills add` 一条命令，套件技能即安装进该项目 `.agents/skills/`；不接来源参数，不装套件之外的任何仓库内容（溯源：发起人原话「我想把技能做成可被安装到项目内的命令行，期望用户通过 npx add xx/skills 的方式安装到项目内的 .agents/skills 里」；D1 拍板 2026-11-14 自建 CLI、D3 拍板套件专属资产安装器、D4 拍板包名 `@hankghchen/skills`——npm 实测可用，scope 无任何占用）。
- **FR-2** 安装完成后，项目内使用的智能体能发现并调用已装的套件技能（溯源：原话「安装到项目内的 .agents/skills 里」——安装的目的即被智能体使用；参照实测：universal 目录 + 对检测到的 agent 目录建软链，目标目录不存在时跳过并提示）。
- **FR-3** README 等面向人的文档把一条命令安装写成官方安装方式，替换现有「拷贝或软链」指引，并写明升级、卸载命令与网络受限时的缓解路径（溯源：原话「把技能做成可被安装到项目内的命令行」——对外的安装故事）。
- **FR-4** 安装器按「套件资产」（GLOSSARY 项目术语章）组织安装内容：本轮资产 = 31 个技能；资产类型可扩展——发起人点名「以后可能还有规范之类」，本轮不实现技能之外的其他资产类型（溯源：D3 拍板原话「套件的专属资产，现在有技能，以后可能还有规范之类」，2026-11-14）。
- **FR-5** 安装内容经 npm registry 分发，使用者可锁定版本安装（`npx @hankghchen/skills@<semver>`）；npm 包 semver 与套件版本对账（溯源：D2′ 拍板「npm 发布」，2026-11-14；npm registry 本机可达实测 vs GitHub 克隆超时实测）。

## 场景

**主流程（安装）**
- Given 使用者在一个全新 git 项目根目录（如 `my-app/`）
- When 运行 `npx @hankghchen/skills add`
- Then 套件技能安装进该项目 `.agents/skills/<技能名>/`（含 SKILL.md 与 references/），使用者可按提示选择装哪些技能；安装器对检测到的 agent 目录建软链、记账锁文件等机制细节归 spec/design（参照 vercel-labs/skills 实测行为：universal 目录 + 软链 + `skills-lock.json`）
- And 项目内智能体新会话能触发已装技能

**升级**：When 使用者重跑安装命令（或升级命令），Then 已装技能对账上游更新（机制归 spec/design，行为参照生态 CLI 的 update/check）。

**异常流 A（网络受限）**：D2′ 拍板 npm 发布后，安装内容随 npm 包分发、不经 GitHub；When 使用者访问 npm registry 受限，Then README 写镜像 / 代理等缓解路径（对应 FR-3、A2 残余风险）。

**异常流 B（装了技能但未接门禁）**：Given 项目只装了技能、未跑 `/setup-workspace`，Then 技能可被智能体触发，但流程门禁（`.sdlc/check.sh`）不存在——技能入口的工作区校验会拒绝流程技能并指路 `/setup-workspace`；安装文档按「先安装、后 `/setup-workspace` 接入门禁」的顺序写明两步关系（Q3 拍板 2026-11-14：CLI 不代做初始化，见非目标）。

## 假设与风险

- **A1（风险）agent 目录约定跟进**：自建 CLI 的安装目标要覆盖各智能体的技能目录约定（`.agents/skills/`、`.claude/skills/` 等），约定随各家演进。代价：新 agent 出现或目录变更时需跟进适配；不确定度：低（`.agents/skills` 已是跨智能体 universal 约定，vercel-labs/skills 支持 20+ agent 可作参照清单）。
- **A2（风险）安装内容的网络可达性**：国内网络 GitHub 直连克隆易超时（2026-11-14 实测 300s 超时一次）。D2′ 拍板 npm 发布后，安装内容随 npm 包分发、不经 GitHub，npm registry 本机实测可达（2026-11-14 候选包名查询正常返回）；残余风险仅剩使用者访问 npm registry 本身受限的场景，README 写镜像/代理缓解路径（对应 FR-3）。
- **A3（风险）自建 CLI 的维护与内容同步成本**：D1 拍板接受的成本——打包、npm 发布纪律、issues 维护，以及 npm 包内容与 `skills/` 目录的一致性（发布流程须保证随包技能与仓库同版本）。代价：每次技能改动多一道发布动作；不确定度：低（机制问题，spec/design 可解）。

## 范围与非目标

非目标（均已显式拍板）：
- 把 vercel-labs/skills 生态 CLI 作为官方安装路径（D1 拍板 2026-11-14；保留为行为参照与降级备选，文档可提及）。
- 发布「技能集 npm 包」供生态 CLI sync 使用（与 D2′ 的「CLI 工具包发布」是两回事；留作后续轮次观察）。
- 安装器代做 `/setup-workspace` 的初始化动作——装技能与接门禁是两步，文档按序指路（Q3 拍板 2026-11-14，原话「Q3确认」）。
- 技能子集打包或安装器层面的分组——技能取舍交安装器交互多选，文档给推荐组合（Q3 拍板 2026-11-14）。
- 通用仓库发现——安装器不接来源参数、不装套件之外的任何仓库内容（D3 拍板 2026-11-14）。
