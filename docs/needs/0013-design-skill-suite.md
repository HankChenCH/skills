# design-* 界面设计技能套件

## 背景与业务目标

用户原话：想新增一套关于设计的技能（前缀 design-*），提高智能体在设计前端布局与功能界面时的能力，使其更贴合使用者的使用场景和操作习惯，同时具备更优的美观程度。

当前痛点（用户亲历）：

1. 布局反直觉。
2. 配色像默认 Bootstrap，缺风格辨识度。
3. 不区分移动端。
4. 忽略空态 / 加载态。
5. 设计未从使用者角度出发——例：操作员希望一屏多看数据，智能体设计大区块表格，一屏看不了几行；管理者更希望总览 + 明细两种视图。
6. 现有系统的风格跟随性差（用户猜测根因：缺乏总的 DESIGN.md 参考）。

业务目标（成功标准）：产出"设计界面 + 对应说明"的述标式交付物（像建筑设计院述标），验收方能知道设计意图 + 看到设计界面供评审。

## 干系人与用户

| 角色 | 要完成什么 | 成功标准 |
|---|---|---|
| 调用方（目标仓库的智能体会话） | 独立按需调用 design-* 技能；脊柱三点（spec 出口 / implement / accept）收到建议 | 想做界面设计时知道调哪个、怎么串 |
| 验收方 | 读设计意图说明、评审设计界面 | 能看懂为什么这么设计、能对着界面提意见 |
| 被设计产品的使用者 | 操作员要一屏高密度看数据；管理者要总览 + 明细 | 设计贴合角色场景与操作习惯，不反直觉 |

## 系统能力需求

- **FR-1 设计约束产出（design-brief）**：给定角色清单与各自任务（如"操作员要一屏多看数据""管理者要总览 + 明细"），产出书面设计约束：每角色的信息优先级、密度要求、关键操作路径；约束进述标说明。（源：痛点 5、业务目标）
- **FR-2 基线建立（design-baseline）**：项目无设计基线时，引导用户产出设计标准分册（docs/standards/ 下按平台分文件）并登记 CODING_STANDARDS.md 索引；不要求先改 setup-workspace。（源：Q9 丙拍板、痛点 6）
- **FR-3 风格跟随（design-baseline / design-ui）**：基线存在时，布局与视觉决策必须先读基线再设计；偏离基线的决策在述标说明中逐条显式声明理由。（源：痛点 2、痛点 6）
- **FR-4 多平台布局（design-ui）**：对 Web / 移动端 / 桌面端 / CLI / 文档视觉五类对象产出布局方案；Web 布局含移动端适配决策（断点或独立布局）。（源：范围拍板、痛点 3）
- **FR-5 四态完备（design-ui / design-deliver）**：界面原型含正常 / 空 / 加载 / 错误四态（样张三态先例 + 用户点名的加载态）。（源：痛点 4）
- **FR-6 硬指标自查（design-ui / design-deliver 出口）**：逐项过硬指标清单——正文对比度 ≥4.5:1、正文字号 ≥14px、触控目标 ≥44px、间距与字号阶梯符合基线；自查结果写进述标说明；不通过项修复或声明豁免理由。（源：Q10 乙拍板）
- **FR-7 述标交付（design-deliver）**：在 design 产物写「界面设计」节（设计意图、角色约束、风格跟随声明、硬指标自查结果）；可点 HTML 原型落 docs/designs/assets/&lt;design-id&gt;/；design 的 approved 门即述标评审门（沉默不算批准）。design-deliver 可直接建含「界面设计」节的 design 产物（简单 spec 不经过 dev-design 的 ADR 三条件门）；与 dev-design 并存时各写各的节、互不覆盖。（源：Q8 甲、Q12 拍板、业务目标）
- **FR-8 脊柱接入三点**：dev-spec 出口识别 spec 含界面交付并建议"先述标再拆票"；dev-implement 装载设计基线与 ui 原则；dev-accept 对照述标说明核销界面 FR。（源：Q11 拍板）
- **FR-9 分平台分册**：brief / ui 的 references 按对象类型分册，按当前对象装载对应分册。（源：范围拍板、Q7 丙拍板）

## 场景

- **场景 1（主流程·新项目首次设计）**：Given spec 含界面交付且项目无设计基线 / When dev-spec 出口建议述标，用户依次跑 brief → baseline → ui → deliver / Then design 产物含「界面设计」节、assets 下原型四态齐、硬指标自查结果在节内；用户批准 design（述标门）后再拆票。
- **场景 2（主流程·有基线跟随）**：Given 设计基线存在 / When ui 设计新界面 / Then 布局与视觉决策跟随基线，无偏离声明；有偏离则述标说明逐条声明理由。
- **场景 3（异常流·用户跳过述标）**：Given dev-spec 出口建议述标 / When 用户拒绝 / Then 正常拆票（建议不强制）；dev-accept 无述标可对照时按工单验收标准核销，并在验收报告注明"无述标"。
- **场景 4（异常流·实现偏离述标）**：Given 述标已 approved / When dev-accept 发现实现界面偏离述标约束（如高密度要求被做成大区块表格）/ Then 开 dev-fix 票回实现链。
