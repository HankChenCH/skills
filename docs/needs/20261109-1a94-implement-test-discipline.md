# implement 测试纪律强制化：异常流表格驱动 + 集成级场景自动化承载

## 背景与业务目标

ref-testing 场景路由表定义了六种测试方法，但跨多轮 implement 实践只有红绿循环被真实触发，
表格驱动测试与集成测试零触发。查证到的因果链是**上游断链 + 承载缺省**，不是方法缺失：

1. **spec 断链（主根因）**：need 模板场景节要求"主流程 + 主要异常流"，但 dev-spec 起草
   验收场景时只查"覆盖全部 FR，缺一条 validate 报孤儿 FR"——不查异常流继承，need 写了
   异常流、spec 不写照样通过；FR 级异常流条目也无强制要求。下游各环节均无缺口：
   dev-plan 将工单级场景逐条机械映射进票的验收标准（忠实传递），dev-implement 按票
   逐条实现——票里没有异常条目，异常流程自然无人测，表格驱动的触发信号（多组输入
   输出）根本不出现。零触发是下游症状。
2. **集成承载缺省**：ref-testing/references/integration.md 写明集成级场景"要能落成测试
   **或**进 dev-accept 运行清单"——这个"或"在既有 spec 中被普遍选成后者（如
   docs/specs/0004:60、0007:64 均标"留验收阶段人工执行"），自动化集成测试从未成为
   默认承载。
3. dev-implement 出口门禁只查 `check.sh all` 全绿与验收标准证据，不查异常流覆盖，
   也不查集成级场景的自动化承载。

后果：异常流程（校验失败、越界输入、错误路径）的期望验证缺失，缺陷只能在人工验收或
生产环境暴露；spec 验收场景与实现测试之间的映射断裂。

可验证的业务目标（下一轮含校验/跨票协作场景的 spec 实践中核销）：

- 异常流测试覆盖：验收标准中的异常流条目全部进入红绿循环；多组输入输出行为以表格
  驱动承载，异常行与正常行同表（信号自判触发，覆盖由 FR-1 上游供料保证）。
- 每条可自动化的集成级场景有自动化集成测试承载，不再默认落人工清单。
- spec 验收场景逐条带承载声明，dev-accept 验收前可机器读出哪些场景必须先跑自动化。

不做的代价：红绿循环 happy-path 倾向持续存在，异常期望悬空；集成级场景继续全部人工核销，
用户原话"对整个 spec 规定的场景有对应的实现测试"无法核销。

## 干系人与用户

- **开发者（流程用户）**：在 implement 与 accept 阶段获得异常流与集成级场景的测试证据；
  成功标准：验收标准勾选时能指出异常行测试与集成测试名。
- **dev-spec**：起草验收场景时强制异常流条目与承载声明；成功标准：新 spec validate 通过
  且逐条场景可数出异常条目与承载方式。
- **dev-plan**：拆票时为可自动化集成级场景指定承载票；成功标准：无"无归属票"的集成级场景。
- **dev-implement**：异常条目入红绿循环，按信号自判表格驱动细则；成功标准：含异常的
  验收标准均有异常测试证据。
- **dev-accept**：先跑全量集成级自动化测试再走人工段；成功标准：验收报告含自动化结果段。
- **check.sh（校验器）**：是否新增承载声明校验规则属 spec/design 决策，本 need 只要求
  声明可被机器读取。

## 系统能力需求

- **FR-1**：dev-spec 起草验收场景时，异常流条目成为强制项：有 need 的必须继承其场景节
  的主要异常流；含错误处理的 FR（校验、解析、边界、外部 IO 失败、状态转换拒绝路径）
  必须补异常流场景条目，与正常流条目并列，各带工单级/集成级标签；validate 对缺失
  异常流继承可报错（校验规则是否机器化归 spec/design 决策）。异常条目按**具体失败
  模式逐条枚举**，每条对应可独立测试的期望行为——禁止以"上传失败时提示用户"一类
  笼统表述概括（如上传需求应拆为：超上限拒绝并报上限值、超时报错且可重试、格式
  不符报支持格式列表）；枚举以主要失败模式为界，不追求穷尽。
  （来源：用户原话"没有关注异常流程是否按正确的期望触发"+"有没有可能是 spec 或 plan
  的时候本身就没有写"+上传失败模式枚举例；拍板 D1-A、D4 因果链修正、D5 枚举粒度）
- **FR-2**：dev-implement 红绿循环纪律显式包含异常行为："每个行为"包括验收标准中的
  异常流条目——异常条目同受先失败测试再实现约束；表格驱动按 ref-testing 场景路由表
  信号自判加载（FR-1 供料后"多组输入输出"信号自然出现），不写死强制路由。
  （来源：拍板 D4 选 B'；用户原话"与测试方法关系不是很大"）
- **FR-3**：spec 验收场景逐条声明承载方式：可自动化的集成级场景默认必须自动化承载，
  标签带承载声明（承载票指向）；声明人工执行的必须写理由。声明格式保证机器可读。
  （来源：用户原话"对整个 spec 规定的场景有对应的实现测试"；拍板 D2-A）
- **FR-4**：dev-plan 拆票时为每条可自动化集成级场景指定承载票；承载票的验收标准含
  集成测试编写（真实协作者 + 受控外部替身，按 integration.md 通则），测试在集成后
  代码上运行。（来源：拍板 D3）
- **FR-5**：dev-accept 验收时先跑全量集成级自动化测试（须全绿），再逐条执行人工段清单；
  每条集成级场景的核销证据注明自动化测试名或人工理由。有红即停下指路 dev-fix。
  （来源：拍板 D2-A 与 D3 的推论）
- **FR-6**：新规则仅约束新立 spec 与其后续 implement/accept；存量已 fulfilled spec
  不回改。（来源：拍板"仅新生效"）

## 场景

主流程：

- `[FR-1 | 工单级]` Given spec 的 FR 为校验/解析类（如"超限时报错并列出行数"），
  When dev-spec 起草验收场景，Then 该 FR 带异常流条目（"空输入报错""恰好越界报错"），
  与正常流条目并列；need 场景节的既有异常流全部被继承。
- `[FR-1 | 工单级]` Given FR 为文件上传，When dev-spec 起草异常流，Then 按"超上限
  拒绝并报上限值""超时报错且可重试""格式不符报支持格式列表"等失败模式逐条枚举，
  不以"上传失败时提示用户"一句概括；每个失败模式可在 implement 阶段独立落成
  一个红绿行为。
- `[FR-2 | 工单级]` Given 票的验收标准含上述异常条目，When dev-implement 实现，Then
  异常条目作为行为进入红绿循环（先失败测试再实现）；该行为构成多组输入输出时按
  路由表加载表格驱动细则，异常行与正常行同表，行名即行为，期望值为独立来源字面量。
- `[FR-3 | 工单级]` Given dev-spec 起草含跨票协作路径的 spec，When 打验收场景标签，
  Then 每条集成级场景形如 `[FR-N | 集成级 | 承载票 NNNN]` 或
  `[FR-N | 集成级 | 人工：理由]`，无承载声明的集成级条目不被接受。
- `[FR-4 | 工单级]` Given dev-plan 拆票，When spec 存在可自动化集成级场景，Then
  每条有指定承载票，该票验收标准含"集成测试编写并可在集成后运行"。
- `[FR-5 | 集成级 | 承载票见 FR-4]` Given spec 名下全部工单 done，When dev-accept
  验收，Then 先跑全量集成级自动化测试且全绿，再逐条人工段；任一红即停止核销并指路
  dev-fix。

异常流：

- `[FR-2]` Given 行为仅异常路径可触发（如全量校验失败分支），When 写测试，Then 异常行
  进表，不在表外塞特例（对应 table-driven.md 通则 5"表外无特判"）。
- `[FR-1]` Given spec 的某 FR 属纯展示无错误分支，When 起草验收场景，Then 该 FR 免于
  异常流条目，豁免理由可在备注注明——防止为凑条目发明异常。
- `[FR-3]` Given 集成级场景依赖真实凭据无法自动化（如真实平台 publish 端到端），
  When 打标，Then 声明人工加理由，进 dev-accept 人工段（对应 D2-A 例外条款，
  同 docs/specs/0004:60 先例）。
- `[FR-1]` Given need 场景节的主要异常流未被 spec 验收场景继承，When spec 起草与
  validate，Then 缺失可被发现（校验是否机器化归 spec/design 决策）——防断链复发。

## 假设与风险

- **假设 A1**（代价低 × 确定度低）："含错误处理的 FR"判据（校验/解析/边界/外部 IO/
  拒绝路径五类）足以让 dev-spec 阶段机械判定，不需外部调研。已查证：既有 spec 存在
  可参照的异常流场景写法。**验证结果（验收报告 20261110-9c81）：本轮未触发**——判据
  已落盘为 dev-spec §3 可机械核验条款，"判据充分性"是起草实践主张，round 1 无校验类
  FR 起草实践，留下一轮实践中核销。
- **假设 A2**（代价中 × 确定度中）：FR-1 上游供料 + 异常条目入红绿后，异常流测试
  覆盖可稳定出现，表格驱动零触发作为下游症状随之消除（"多组输入输出"信号自然出现）。
  若实践仍见异常条目被跳过或表格驱动仍零触发，round 2 可补出口门禁兜底（对应本 need
  否决的 D1-C 方案），改动点已在卡上。**验证结果（验收报告 20261110-9c81）：本轮未
  触发**——运行时行为留待下一轮含校验类 FR 的 spec 实践验证（同 spec 0003 先例）；
  规则落地侧已备齐（dev-implement:53、dev-spec:78-84），round 2 出口门禁兜底备而未用。
- **风险 R1**：一轮同改六个文件（dev-spec、dev-implement、dev-plan、dev-accept、
  ref-testing、GLOSSARY），规则间引用需一致（如 FR-3 的声明格式被 FR-4/FR-5 引用）；
  缓解：spec 阶段先定声明格式与引用关系再动文件。**验证结果（验收报告 20261110-9c81）：
  验证通过**——grep 走查证实承载声明格式四处引用字面/渲染一致、GLOSSARY.md:49 已登记
  "承载票 / 承载声明"、FR-6 生效限定六文件 8 处全命中，引用链无断裂。
- 靶心：FR-1/FR-2 异常流强制是用户最痛点，round 1 全做已拍板，无需再圈范围。
  **验证结果（验收报告 20261110-9c81）：验证通过**——FR-1~FR-6 六条全部有落盘条款与

  grep 走查命令按字面复跑时 ref-testing/SKILL.md 零命中（路由行竖线 GFM 转义为 `\|`），

非目标（全部来自显式拍板）：

- 不回改存量已 fulfilled spec（拍板：仅新生效）。
- 不为表格驱动写死 implement 强制路由（拍板 D4 否决原 D1-B，表格驱动按信号自判）。
