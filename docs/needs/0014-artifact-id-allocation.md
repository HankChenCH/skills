# 产物编号分配机制统一治理（号复用与多会话竞态）

## 背景与业务目标

现行编号规则（METHOD.md §产物约定）：产物文件名 `NNNN-slug.md`，四位零填充、每类产物
独立递增、从 0001 起；各技能按「id = 目录内最大号 +1」取号，规则分布在 9 个技能
（dev-clarify / dev-spec / dev-plan / dev-fix / dev-review / dev-accept / dev-overview /
dev-research / dev-retro）。

该规则有两个结构性缺陷：

**缺陷一：清扫后号复用（已实证，非隐患）。** 过程档（ticket / review / acceptance /
overview）验收后随蒸馏清扫删除，目录最大号回落，新产物把历史号重新分配出去。证据在
`.sdlc/trackers/github.map`：

- 票号 `0024` 两条记录：`docs/tickets/0024-blueprint-whole-graph-run.md`（→ issue #87，
  已清扫）与 `docs/tickets/0024-dev-review-axis-isolated-agents.md`（→ issue #118）。
- acceptance 号 `0001` 被复用 9 次（0001-spec0001-round1 … 0001-review-axis-isolated-agents
  各为不同文档）。

危害链：本体系审计链主承载为 tracker 投影与源码提交 `[#NNNN]` 引用（GLOSSARY「归置分档」），
号一复用——① git 历史里两个 `[#0024]` 无法分辨指向哪张票；② 工票 `blocked-by` 按号引用，
实现技能按号查票查到的是复用后的另一张票（用户 2026-11-04 确认的主要痛点）。

**缺陷二：多会话取号竞态。** 「读目录→写文件」两步无原子性，且过程档被 `.gitignore`
排除、git 拦不住同名冲突；两个会话同时开票会取到同一个号。spec 虽是知识档不清扫、
无号复用问题，但取号是同一条 max+1 规则，竞态相同。

**业务目标（可验证）：**

1. 每类产物新分配的号与该类全部历史号（含已清扫产物）不冲突。
2. 多会话并发取号零冲突、零人工协调。
3. git 历史与 tracker 投影中的 `[#NNNN]` 全历史无歧义。
4. 以一次模拟仓演练实证 1–3 并留痕——用子代理模拟多个并发会话，同时开 spec / 开票。

不做的代价：审计链持续失真；blocked-by 查错票导致实现技能改错目标；多会话只能串行开票。

  + 2026-11-04 纠正）
- FR-3 谱系可读：有父产物的新产物在号中携带父产物号前缀，前缀后接全局时间戳子段

  留痕消解。（用户答 1 + D2 拍板）

## 场景

**场景 1（已发生的号复用，历史实证）**
Given 清扫已删除 `0024-blueprint-whole-graph-run`（issue #87）
When spec 0016 派生新票按 max+1 取号
Then 取到 `0024`，与历史票同号不同票 → map 双 0024、git 历史 `[#0024]` 歧义。

**场景 2（清扫后开票，回归路径）**
Given 某类过程档全部被清扫、目录为空（如当前 docs/acceptance/）
When 新验收报告取号
Then 不得取到 `0001` 等历史已用号。

**场景 3（两会话并发开票）**
Given 会话 A 与会话 B 同时对同一仓库开票
When 双方各自取号并落盘
Then 两张票得到不同号，无人工介入。

**场景 4（多会话并发开 spec 与开票并存）**
Given 多个会话并发取号（演练中由子代理模拟）：会话 A 正在开 spec，会话 B 正在开票
When 双方各自取号落盘
Then 各得不同号，spec 号与票号互不冲突。

**场景 5（谱系前缀，FR-3）**
Given spec 0017 拆票
When 其派生工票取号
Then 票号形如 `spec0017-20261104-a3f2-slug.md`，按号即可读出归属。
