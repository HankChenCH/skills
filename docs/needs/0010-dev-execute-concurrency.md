# dev-execute 并发执行优化

## 背景与业务目标

dev-execute（spec 0006）把一张 approved spec 名下全部工票按运行依赖顺序图编排：
同层票独立票 worktree 经子代理并行实现，逐票编排评审，机械合回运行分支并逐票预演。
实际运行中观测到三类问题（用户 2026-10-31 提出）：

1. **合回冲突频繁停机**：同层并行票合回时后合者撞先合者，触发 §8 异常流，
   停下问人。
2. **主会话同步干等**：子代理派发后主会话阻塞到全部完成才进编排评审与合回，
   未利用异步能力。
3. **并发模型写死子代理**：不适配多宿主——部分宿主无子代理能力，部分宿主
   提供比子代理更优的并发原语。

已查证事实（本仓库内联查证，2026-10-31）：

- dev-plan 拆分纪律只有"垂直切片 + blocked-by 只标真实依赖"
  （`~/.zcode/skills/dev-plan/SKILL.md` §3），无"同层票改动面互斥"约束。
  垂直切片刻意切穿所有层，同层两张票各自动 schema 或共享接口时，实现期
  物理隔离（各自票 worktree）不冲突，合回期后合者必撞。
- 合回顺序"同层任一序"（`~/.zcode/skills/dev-execute/references/run-mechanics.md` §7），
  合回冲突→停机问人是设计意图（dev-execute SKILL.md §8"绝不自动解冲突"），
  处置是 expand–contract 拆票回 /dev-plan。触发频繁才是问题。
- 子代理派发为同步阻塞（dev-execute SKILL.md §5.1 无后台派发表述）；
  ZCode 的 Agent 工具支持后台运行（`run_in_background` 参数）未被使用。
- "当前层全部票合回且预演绿→进入下一层"（SKILL.md §5.5）是层屏障模型，
  天然串行化。
- 多宿主是既成事实：README.md:46"内置 ZCode 与 Claude Code 的接入参考，
  其他智能体走通用流程"；`~/.agents/skills/` 与 `~/.zcode/skills/` 并存；
  `~/.zcode/skills/to-tickets/agents/openai.yaml` 是 Codex 接入点。
  dev-execute 的"子代理并行"（SKILL.md §5.1）写死了单一并发模型。

业务目标（2026-10-31 拍板）：

- **消除合回冲突停机**：3 次 dev-execute 运行中 2 次因合回冲突触发 §8
  异常流停机问人（用户口述）。目标：合回冲突零停机，人工介入收敛到
  开工确认 + 合并确认两次。
- **异步流水线**：同层并行实现期间主会话不被锁死——可响应用户、可先行
  评审已 implemented 的票。
- **并发机制按宿主自适应**：同一技能在 ZCode、Claude Code、Codex、
  DeepSeek harness 上都能以该宿主可用的最优并发原语运行。

拍板记录（2026-10-31，第一批）：

- D1 → 最痛点是合回冲突停机：3 次运行 2 次触发；round 1 靶心 = 冲突消除
  （去向：业务目标第 1 条）。
- D2 → 成功标准 A + B 都要：零冲突停机 + 异步流水线（去向：FR 待编号）。
- D3 → 问题 1 改法两者都要：dev-plan 源头互斥约束 + dev-execute 开工前
  预检（去向：FR 待编号）。
- D4 → 宿主范围：ZCode、Claude Code、Codex、DeepSeek harness 全适配
  （去向：R1 调研范围）。

## 干系人与用户

- 编排用户：在宿主智能体中发起 dev-execute 运行的人。合回冲突停机时被叫来
  解冲突，同步干等时被锁在等待里。
- 实现子代理：每票一个，执行 dev-implement 纪律，在票 worktree 内工作。
- 拆票会话（dev-plan）：产出工票与 blocked-by 边，决定同层并行面。
- 宿主智能体：承载技能运行环境，决定可用并发原语。已确认使用面：ZCode、
  Claude Code、Codex、DeepSeek harness（2026-10-31 拍板 D4）。

## 系统能力需求

- **FR-1 改动面互斥拆票**：dev-plan 拆票时能判定同层票改动面重叠；重叠票
  强制串行化（标 blocked-by）或按 expand–contract 重切——落盘的同层票满足
  改动面互斥（GLOSSARY 已登记）。〔源：D3、S2〕
- **FR-2 开工前冲突预检**：dev-execute 开工确认前能基于票正文与代码现状
  预估同层票改动面重叠，报告风险并给默认建议（串行化或回 /dev-plan 重切）；
  不硬拦，是否开工由用户决定（既有开工门禁不变）。〔源：D3、S3〕
- **FR-3 异步实现与先行评审**：并行实现期间主会话不被阻塞——派发后可随时
  响应用户；票 implemented 后可先行编排评审，不等同层其余票实现完成。
  〔源：D2-B〕
- **FR-4 流水线合回**：已 approved 的票在依赖满足时即合回运行分支并预演，
  层屏障取消；"全部票 implemented 且预演绿"的运行全绿判定保留。〔源：S1〕
- **FR-5 宿主并发能力调研报告**：产出《四宿主并发原语对照》（ZCode、
  Claude Code、Codex、DeepSeek harness）：并发原语清单、后台与状态回收、
  隔离能力、无子代理宿主的退化方案——作为 FR-6 的设计输入。〔源：S4，
  R1 三路归置为 FR〕
- **FR-6 宿主自适应派发**：dev-execute 能探测宿主可用并发原语并按 FR-5
  报告选用最优可用者；无子代理宿主按退化方案运行（形态由 FR-5 定），
  宿主有更优原语（如声明式工作流）时使用之。〔源：D4、用户原话
  "根据当前智能体特色来做"〕

## 场景

主流程：

- **场景 1（拆票互斥）**：Given 一张 approved spec 待拆票，When dev-plan
  发现两张拟同层票预估改动同一 schema，Then 该对票标 blocked-by 串行或按
  expand–contract 重切，落盘后同层票满足改动面互斥。
- **场景 2（开工预检）**：Given dev-execute 建好运行依赖顺序图，When 预检
  报告某同层两票改动面高重叠，Then 报告风险与默认建议并等用户决策；用户
  不确认不建任何 worktree。
- **场景 3（流水线运行）**：Given 第 1 层 3 票并行实现，When 票 A 先
  implemented，Then 主会话先编排评审 A；A approved 后即合回并预演；期间
  票 B/C 仍在实现，用户插话随时可答。
- **场景 4（全绿收口）**：Given 全部票合回且末次预演绿，Then 运行全绿，
  照既有收口链走（一次合并确认 + 票 done + 清理 + 出口报告）。

异常流：

- **异常 1（预演红）**：流水线合回后预演红 → 既有 §8 异常流不变
  （指路 /dev-fix，fix 票入图重算）。
- **异常 2（合回冲突仍发生）**：互斥约束把冲突从常态降为异常；异常流本身
  保留——停下问人，绝不自动解冲突。〔对应业务目标"零停机"的边界：
  目标是消除常态冲突，不是取消人工门〕
- **异常 3（宿主无并发原语）**：探测到宿主无子代理/后台能力 → 按 FR-5
  报告的退化方案运行，开工确认时向用户声明该宿主的并发形态。

## 假设与风险

- **A1（我补写的建议）**：合回前可用 `git merge-tree` 干跑预检实际冲突，
  把同层合回顺序排成无冲突序——低成本，但属实现手段，交 /dev-spec 评估
  取舍，不进 FR。
- **A2（设计风险）**：改动面判定粒度（文件/模块/接口级）未定——判粗则
  并行度损失放大（S2 已接受该类代价），判细则漏检；粒度归 dev-spec/design。
- **A3（外部依赖，待 FR-5 消解）**：Codex 与 DeepSeek harness 的并发能力
  无一手信息——若某宿主完全无并发原语，FR-6 在该宿主退化为串行，
  FR-3/FR-4 的异步目标在该宿主不可达。
