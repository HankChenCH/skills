# V 模型整 spec 编排运行技能（dev-execute）

## 背景与业务目标

现有管线一次只推进一张工单：sdlc next 模式要求用户逐票点名（next-mode 路由规则"总控不得代挑"），每张票各走一次"实现 → 评审 → PR → 合并确认"——跑完一张含 5 张票的 spec 需要至少 10 次人交互（5 次点名 + 5 次合并确认）；工单间 blocked-by 依赖顺序靠人看 frontier 清单自己排；票级红绿测试在 dev-implement 已有，但票间集成问题要等最后 dev-accept 才暴露；"整个 spec 执行到哪了"没有一屏视图。

来源：用户 2026-10-28 指令"添加 v 模型的 implement 技能，旨在实现整个 spec……构建运行依赖顺序图，并追加 v 模型理论的左右臂，实现整个运行流程"；四痛点为用户 2026-10-28 圈定原话：一次一票太碎、依赖顺序靠人记、验证不显式成阶梯、全流程视图缺失。

业务目标：新增编排技能（默认命名 dev-execute）——输入一张 approved spec，构建其名下工票的运行依赖顺序图，在独立 git worktree 中按依赖序并行推进"实现 → 评审"，每票合回后跑集成预演（V 模型右臂上行），全部绿后经一次合并确认收口。左臂分解产物（spec/工票）已在盘上，本技能从 V 底起跑。成功标准（可核销）：

- S1 一张含并行机会的 spec 从确认开工到合并完成，人交互恰 2 次：开工确认 + 合并确认。
- S2 同层无依赖票的实现在时间上重叠执行；运行期间主工作区不被占用。
- S3 运行结束：spec 名下全部工单 status: done，出口报告指路手动 /dev-accept。
- S4 任何异常流停下时，报告含连坐阻塞面（哪些后续票被阻塞）与指路技能名。

## 干系人与用户

- 用户（主 Actor）：发起运行；在开工确认、合并确认两个决策点拍板；异常流停在原地时裁决怎么解。
- agent 会话（执行 Actor）：构建运行依赖顺序图、创建 worktree、并行调度工票实现与评审、产出进度报告。
- 被编排技能：dev-implement（单票红绿纪律原样复用，零改动）、dev-review（逐票评审）、dev-ship 前半（运行末生成一次 PR）。
- 异常回路技能：dev-fix（预演失败开 fix 票）、dev-spec（缺口修订）、dev-accept（运行后手动验收）。
- sdlc 总控（副 Actor）：默认报告增加"运行中 worktree"段，跨会话进度一屏可见。

## 系统能力需求

- FR-1 能输入点名 approved spec，分析名下全部工票的 blocked-by，构建运行依赖顺序图（同层无依赖可并行、层间串行约束的分层视图，标注并行机会与关键路径），展示并请求开工确认。
- FR-2 能在独立 git worktree 与运行分支中执行整个运行（用户指定机制：原话"要用 git worktree 模式运行"），主工作区不被占用。
- FR-3 同层无依赖票并行实现：每票独立 worktree + 分支，blocked-by 边是唯一串行约束（用户原话"能并行就并行，不要严格串行"）。
- FR-4 评审通过的票按依赖序机械合回运行分支（合并不设人工门），每次合回后在运行分支上跑票间集成预演（`.sdlc/check.sh all` + spec 既有集成级测试）。
- FR-5 多会话可同时各跑一张 spec：不同运行各持独立 worktree 与运行分支，互不阻塞（用户原话"可能多会话执行不同 spec"）。
- FR-6 全部票 implemented 且预演绿 → 按 dev-ship 前半模板生成一次 PR → 合并确认（单向门，问人）→ 合并后该 spec 全部工单 status: done → 清理运行 worktree；逐票评审出口的"自动准备 PR"在运行内让渡到运行末执行。
- FR-7 出口输出进度报告（逐票终态 + 运行摘要），指路手动 /dev-accept。
- FR-8 sdlc 总控默认报告增加"运行中 worktree"段：`git worktree list` + 逐运行分支读票状态，跨会话进度一屏可见。
- FR-9 异常流一律停下问人并指路对应技能（场景节 E1–E5），不自动兜底、不自动解冲突。

## 场景

主成功场景（单 spec 运行）：

- Given 一张 approved 的 spec，名下 N 张票（blocked-by 构成有向无环图），主工作区在主分支且干净，该 spec 无进行中的运行。
- When 用户经 /sdlc next 路由（frontier 出现同 spec 多张可开工票）或手动触发 dev-execute <spec NNNN>。
- Then：
  1. 入口校验：spec approved、名下票齐全、无外来 in-progress 票；不满足 → 停下指路（E6 类拒绝路径）。
  2. 创建运行分支与运行 worktree；对名下全部票拓扑排序得运行依赖顺序图，分层展示并行机会与关键路径；用户确认开工（决策点①）。
  3. 逐层调度：同层每票独立 worktree + 分支并行实现（dev-implement 红绿纪律原样）→ 出口自动 dev-review；绿票按依赖序机械合回运行分支；每票合回后跑集成预演。
  4. 全部票 implemented 且预演绿 → 生成一次 PR → 用户合并确认（决策点②，单向门）→ 合并后全部票 → done → 清理运行 worktree。
  5. 出口进度报告，指路手动 /dev-accept。

异常流：

- E1 评审出现设计级阻断（dev-review 既有语义：机械问题自动修自动重审）：运行停在该票，报告连坐阻塞面，问人处置。
- E2 实现中发现 spec 缺口或错误：停下指路 /dev-spec 修订（门禁回路，不是失败）；修订 approved 后重入，从盘上票状态续跑。
- E3 集成预演失败：停下问人，指路 /dev-fix 开 fix 票（决策卡 D3）；fix 票并入运行依赖顺序图重算，修复后重入续跑。
- E4 并行票合回冲突（两票改到同一文件）：停下问人怎么解（决策卡 D5）；指路可含按 expand–contract 拆票回 /dev-plan。
- E5 多会话并行的两个运行分支先后合并、后者冲突：合并确认处停下问人（rebase 后重跑预演再入合并门）。
- E6 用户点名单张票或 spec 未 approved：拒绝，指路 /dev-implement 或 /dev-spec（单票与未批准 spec 不在编排范围）。
- E7 会话中断：票状态与 ## Progress 在各票 worktree 分支上已是盘上真相；重入从 `git worktree list` + 票状态推导续接点。

## 假设与风险

- A1 同层并行票改到同一文件的频率低——依据 dev-plan 垂直切片原则（每票切穿全层、边界不重叠），但无机械保证，兜底是 E4 停下问人。代价：并行收益打折；不确定度：低。（验证：本轮未触发——演练票互不相交，未度量真实冲突频率；停机兜底已实证：合回冲突 CONFLICT 后 `merge --abort` 停门问人，验收 0001 FR-9）
- A2 每票独立 worktree 是完整 checkout，依赖安装（node_modules 等）各一份：磁盘与安装时间随并行度线性增长；并行度上限可在 spec 阶段定默认值。不确定度：低。（验证：本轮未触发——演练为最小仓库未装依赖，未度量代价；默认并行度上限 4 已在 spec 阶段落定）
- A3 编排会话并发调度多子代理，上下文 token 消耗高于单票会话：sdlc 总控水位线机制（绿 <30% / 黄 30–50% / 红 ≥50%）可复用到编排调度。不确定度：低。（验证：本轮未触发——演练单会话驱动，未跑真实多子代理并行；水位线机制已在 sdlc 落地）
- A4 多会话同时 publish 到 tracker：不同 spec 的产物文件不同，.map 幂等设计（重复 publish 更新而非新建）已覆盖，竞态面仅在同产物重复写。不确定度：低。（验证：本轮未触发——演练仓库 TRACKER=local；.map 幂等已由 spec 0004 票级验收覆盖）
- 残余风险：真实会话级并行未验——FR-3/FR-5 演练在单会话内按时间序模拟 git 层行为，两个真实 agent 会话同时各跑一张 spec 的调度面（子代理并行度、上下文水位、tracker 并发 publish）未被覆盖；首次实战可能暴露会话层问题，异常流全部停机问人兜底，无自动放大（来源：验收报告 0001）。技能文本的执行面依赖 AI 遵循：dev-execute / run-mechanics / sdlc 接线均为文本契约，不同会话遵循度有方差，单次偏差经评审与 retro 回路修正（来源：验收报告 0001）。
- 下一轮建议：① `.sdlc/config.sh` 接入检查命令（最小可行：Markdown 结构 lint——技能文件行数上限、frontmatter 字段校验），让 `check.sh all` 从"无命令警告"变为有牙齿的门禁；② 首次真实运行 dev-execute 跑一张小 spec（2–3 票、一层并行），补齐会话级证据，预期产出回流 run-mechanics 修订（先例：合回信息缺票号被 hook 拦的修订）。
- round 1 靶心：FR-3 并行调度与 FR-4 合回 + 预演（新机制，无先例）；FR-2/FR-5 的 worktree 是 git 成熟能力，风险最低。

## 范围与非目标

非目标（全部来自显式拍板）：

- 不改造 dev-implement：单票纪律（红绿、入口门禁、出口自动评审）零改动，编排技能在其外层（拍板：新建编排技能）。
- 不以强化 sdlc next 替代建新技能（拍板：否决该选项）。
- 运行收口不自动调 dev-accept：全部 done 后停，指路手动验收（拍板：用例圈定圈掉"收口自动调 dev-accept"）。
- 运行依赖顺序图不落盘为产物：会话内计算视图，执行进度由既有工单状态机表达，check.sh 零改动（拍板：陈述句确认）。
- 一次运行只处理点名 spec 名下的票：其他 spec 的票不进本次运行，fix 票插入也只重算本 spec 的图（拍板：范围边界确认）。
- 不做票级合并的逐票人工确认：票合回运行分支是机械操作，人工门只在运行末合并确认一次（拍板：D1）。
