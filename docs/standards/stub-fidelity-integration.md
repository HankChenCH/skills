# 替身保真缺口与集成级拦截纪律

注入替身（fake/stub）的测试断言的是**替身的契约**，不是真实协作者的契约；真实协作者的行为漂移只能由真实协作者参与的集成级测试拦截。替身写得越"合理"，这个缺口越隐蔽。

## 判据（何时必须真实协作者集成测试）

满足任一条件的交付物，其与外部真实协作者的契约一致性**不得只靠注入替身测试背书**：

1. 交付物会被真实协作者**校验或解析**（如 npm 包被宿主 loader 校验清单文件）——替身不实现校验语义时，替身测试全绿 ≠ 协作者接受。
2. 协作者写入的工件格式由协作者决定（如官方命令写依赖行的版本形态）——替身写的字面 ≠ 协作者写的字面，钉死替身字面的断言在真实链路上永远不成立。
3. 发布型资产（发布后同版本号不可重发）——发布前必须有真实协作者链路验证过，否则坏资产发出去只能靠升版本修复。

## 实证（spec 20261115-495e round 1）

demo 插件包 `cordis.patch.yml` 为顶层映射形态：单元校验器只核「以包名引用自己」事实（全绿）、注入执行体 e2e 全绿——真实官方 dsh（0.2.2-rc.1）语义性拒绝（`must be a top-level YAML array`）并回滚落盘。由集成承载票（20261115-98b6）的真实 npx 端到端在发布后拦下，升版本 0.1.1 修复。替身保真缺口的三道防线各拦一道：单元校验器核事实（自引用）、集成级核官方可解析性（真实协作者）、发布对账核包内外一致。

## 纪律

- spec 测试决策同时落注入替身 seam 与真实协作者集成级承载时，集成级承载票是**发布门前的义务段**，不是可选项（合并候选验收先跑自动化段全绿）。
- 真实协作者写入的字面（版本形态、路径风格、清单语法）**不得作为替身测试的期望值来源**——替身测试钉替身契约，真实链路断言钉工件级语义（落点齐备 + 实装版本 + 记账一致），两套期望各自独立成立。
