## 一、流程拓扑

### 脊柱（七阶段门禁流水线）〔方法自创〕
- **定位**：单次变更从想法到沉淀的主干流程，七个阶段依次为：问题定义（clarify）→ 调研（research）→ 设计（spec/design/prototype）→ 规划（plan）→ 实现与质量（implement/review）→ 交付（ship/release）→ 反馈沉淀（fix/retro/docs）。每阶段有门禁，不过门不进下一阶段。
- **落点**：蓝图 §4.1；由 15 个 `dev-*` 流程技能承载。

### V 模型〔外部〕
- **定位**：经典软件工程模型，左臂逐级分解（需求→规格→设计→实现），右臂逐级验证（单元→集成→验收）。本方法取其"右臂"补集成验证：单票都绿不代表拼起来对，规格级验证由专门环节负责。
- **来源**：1980 年代系统/软件工程经典模型（V-Model）。
- **落点**：蓝图 §4.2 左右臂对照表；右侧验证由 `dev-accept` 承载。

### 循环模型（MVP 分轮）〔外部·思想 + 方法自创·落法〕
- **定位**：需求模糊或决策者短期视野受限时，用最小实现换信息：实现 → 审查风险 → 改进优化，循环增强系统。本方法的落法是 need 固定含"假设与风险"节、spec 带 `round: N` 字段、验收报告含"残余风险 / 下一轮建议"，退出条件机械化（need 终态 `fulfilled`）。
- **来源**：迭代增量开发与精益创业 MVP（Minimum Viable Product，Eric Ries《精益创业》）；风险驱动思想可上溯至 Boehm 螺旋模型。
- **落点**：蓝图 §4.3；分轮决策在 `dev-spec`，回转点在 `dev-accept`。

### 需求工程三步（挖掘→分析→设计）〔外部〕
- **定位**：经典需求工程的三个活动。本方法对应管线位置：clarify 承担挖掘+分析，spec 承担设计。
- **来源**：需求工程标准教材（如 Sommerville、Wiegers《软件需求》）。
- **落点**：蓝图 §9 末段。

### 需求三层视点（业务需求 / 用户需求 / 系统需求）〔外部〕
- **定位**：把需求按"为什么做（业务）→ 谁用、要完成什么（用户）→ 系统要具备什么能力（系统）"三层下钻的分析方法。多干系人、业务流程复杂时作为主讨论方法。
- **来源**：需求工程分层惯例（Wiegers & Beatty《软件需求》的 business / user / functional 三层）。
- **落点**：蓝图 §6.2 need 模板的前三节（背景与业务目标 / 干系人与用户 / 系统能力需求 FR-N）；选择器在 `dev-clarify`。

### 用例驱动〔外部〕
- **定位**：以"主流程 + 异常流"走查驱动需求澄清的方法，适合交互密集、流程分支多的需求。走查结果落 need 的"场景"节。
- **来源**：Ivar Jacobson 用例（use case），UML 体系。
- **落点**：蓝图 §6.2"场景"节、§9 选择器。

### 风险驱动 MVP 分轮〔外部·思想 + 方法自创·落法〕
- **定位**：需求模糊时，把模糊需求显式化为假设清单，按"错了代价 × 不确定度"排序，round 1 只覆盖风险最大的最小可验证范围。
- **来源**：风险驱动开发（Boehm）；"代价 × 不确定度"排序是对风险暴露（概率×代价）的会话内改造。
- **落点**：蓝图 §4.3、§6.2"假设与风险"节。

### 原型驱动 / 调研驱动〔通用〕
- **定位**：两种需求方法论备选项——UI/体验说不清时先做可点的原型；技术或外部依赖不确定时先联动调研。
- **落点**：蓝图 §9 选择器；分别联动 `prototype`（原 Matt 套件）与 `dev-research`。

### tracer-bullet 垂直切片〔外部〕
- **定位**：拆工单的基本方式——每张票切穿全部技术层（数据、接口、UI、测试），可独立演示，大小适配单个会话上下文。结构性防集成病的第一道保险。
- **来源**：The Pragmatic Programmer（Hunt & Thomas）的"曳光弹"；相关的还有 walking skeleton（Alistair Cockburn）。
- **落点**：蓝图 §4.2 末段、§11.5 `dev-plan` 拆票规则。

### 横向分层 vs 垂直推进〔通用〕
- **定位**：反模式与正例的对照——"先把模型全写完再写接口"是横向分层（禁）；一次只做一个验收标准、端到端打通是垂直推进（行）。
- **落点**：蓝图 §12 实现纪律第 1 条。

### expand–contract〔外部〕
- **定位**：宽泛机械重构（重命名、改共享符号类型）不硬塞进垂直切片，而按"先并存、分批迁移、最后收缩，每批保 CI 绿"的序列拆。
- **来源**：并行修改（parallel change），重构领域通用模式（Martin Fowler 站点收录）。
- **落点**：蓝图 §11.5。

### 工单级 / 集成级（验证层级）〔方法自创〕
- **定位**：spec 验收场景的两种标注：`[FR-N | 工单级]` 可拆进单票验收标准；`[FR-N | 集成级]` 拆不进单票、必须集成后验证，构成 `dev-accept` 的运行清单。集成风险在规划时显式化，而不是合并后才发现。
- **落点**：蓝图 §4.2、§6.3 验收场景节、§11.5。

## 二、门禁与反绕过

### 门禁式规范（gate）〔外部·思想 + 方法自创·实现〕
- **定位**：每阶段有检查清单，不过门不进下一阶段；与"指令式规范"（写了规矩但没检查）相对。是整套方法对"Matt 套件容易被绕过"这一核心痛点的回答：**门禁不可绕**。
- **来源**：思想同源新产品开发的 Stage-Gate（Robert Cooper）；"指令式 vs 门禁式"的对立为会话提炼。
- **落点**：蓝图 §1 三个拍板决策之一、§13.2 自测清单第 2 项（拒绝路径是灵魂）。

### 四层防御（L1–L4）〔方法自创〕
- **定位**：反绕过的完整机制栈：L1 常驻指令（AGENTS.md 哨兵块）、L2 技能入口（调 check.sh 校验上游产物，不满足即拒绝指路）、L3 机械层（git hooks 跑 check.sh，连人在终端手敲也拦）、L4 可选增强（ZCode PreToolUse hook 拦 `--no-verify` 与无工单的 src/ 编辑）。
- **落点**：蓝图 §3。

### 豁免通道（[trivial]）〔方法自创〕
- **定位**：typo、纯文档改动走 `[trivial]` 标记豁免门禁，每次豁免留痕（commit message），由 `dev-retro` 审计是否滥用。防止门禁把小事卡死，也防止豁免成为后门。
- **落点**：蓝图 §3、§5.4 pre-commit、§6.6。

### 门禁分级（轻门禁 / 重门禁）〔方法自创〕
- **定位**：commit 时只查轻量项（message 带 `[#NNNN]` 且工单状态合法，或带 `[trivial]`）；merge/push 前才查重项（implemented 工单都有 approved 评审）。每次提交都全量检查会让人想卸载门禁。
- **落点**：蓝图 §3、§5.4 `pre-commit` / `pre-push`。

### check.sh〔方法自创〕
- **定位**：门禁脚本是全部机械判断的单一落点，8 个子命令：`phase`（全库状态总览）/ `frontier`（可开工工单）/ `ticket`（入口校验）/ `all`（全量 lint/typecheck/test）/ `validate`（模板与追溯校验）/ `pre-commit` / `pre-push` / `publish`（发布到 tracker）。git hook 和技能用同一套判断——校验逻辑下沉到脚本，技能只保留判断性行为。
- **落点**：蓝图 §2 原则 1、§5.4。

### 能机械检查的绝不只写成指令〔方法自创〕
- **定位**：第一设计原则。规则若可机械检查就必须落在 check.sh；技能正文只写"怎么做、拒绝时怎么指路"。
- **落点**：蓝图 §2 原则 1，贯穿全部技能设计。

### 状态在盘上，不在对话里〔方法自创〕
- **定位**：一切流程状态由产物 frontmatter 与 `## Progress` 节表达，不依赖对话记忆；会话可随时中断续接（重入）。任何流程技能中断前必须先把进展写回盘上再停。
- **落点**：蓝图 §2 原则 2、§8 普适规则、§12 中断与交接。

### 以落盘产物为接口〔方法自创〕
- **定位**：技能之间通过文件衔接（spec 文件、工单文件），不通过对话记忆——这是"流程化"的实质：流程状态存在文件系统里，跨会话可续。
- **落点**：蓝图 §2 原则 3。

### 机器物与人文物分家〔方法自创〕
- **定位**：`.sdlc/` 放流程基础设施（脚本、配置），`docs/` 放流程产物（人要读的），互不越界。
- **落点**：蓝图 §5.1 原则 1、§5.2 目录总览。

### 单一真相源〔通用〕
- **定位**：每类信息只存一份。本方法的多处应用：产物 frontmatter 是流程状态的单一真相；蓝图是设计的唯一真相源（先改文档再改技能）；"什么是好"的知识只在 ref-* 存一份；不设 `.scratch/` 草稿区以杜绝第二真相源（草稿就是 `status: draft` 的正式产物）。
- **落点**：蓝图 §5.7、§7.3、§13.3。

### 盘上主本、tracker 投影〔方法自创〕
- **定位**：docs/ 永远是真相源，GitHub/云效 Codeup 只是发布目标；单向发布不回读，双向同步是深坑、单向发布是浅水。门禁读 frontmatter，所以 tracker 上有没有 issue 不影响校验。
- **落点**：蓝图 §2 原则 7、§5.5。

### 哨兵块（sentinel block）〔通用〕
- **定位**：setup-workspace 在 AGENTS.md 中用 `<!-- sdlc:begin / end -->` 标记圈出的自管地盘，块外永远是用户的；重跑只替换标记之间的内容。放指针不放全文，避免上下文膨胀。
- **来源**：配置管理中"托管块"（managed block）惯例。
- **落点**：蓝图 §5.3（L1 防御的载体）。

### 审计链〔通用〕
- **定位**：评审报告与工单等流程产物全部进版本库、不 gitignore——它们本身就是审计链，是门禁体系的一部分；豁免留痕供 retro 审计。
- **落点**：蓝图 §5.1 原则 2、§5.7。

### git hooks（pre-commit / pre-push）与一行转发〔外部〕
- **定位**：L3 机械层的载体。hooks 本身不进版本库，所以只做一行转发（`.sdlc/check.sh pre-commit`），真逻辑全在版本化的 check.sh 里；换机器重跑 `/setup-workspace` 即恢复。
- **来源**：git 官方钩子机制。
- **落点**：蓝图 §5.2、§5.4。

### PreToolUse hook〔外部·平台机制〕
- **定位**：ZCode 平台的工具调用拦截钩子，L4 可选增强：拦含 `--no-verify` 的命令、无在办工单时的源码编辑。已实现（2026-10-28，need 0003 / spec 0005）：判定脚本 `.sdlc/hooks/l4-guard.sh`，工作区 `.zcode/config.json` hooks 块接线，失效安全为放行。
- **落点**：蓝图 §3 L4、§5.2、§14。

### 幂等 / 懒创建〔通用〕
- **定位**：setup-workspace 可反复重跑不破坏已有内容（按所有权表决定覆盖或补缺）；产物目录由第一个产物落盘时创建，不留 `.gitkeep` 占位。
- **落点**：蓝图 §5.1 原则 3、§5.2。

### 所有权表〔方法自创〕
- **定位**：规定每条路径由谁首次创建、谁日常写入、setup 重跑时整体覆盖 / 只补缺失 / 绝不触碰。`src/` 及一切用户文件永不触碰。
- **落点**：蓝图 §5.2。

## 三、产物与追溯

### frontmatter 与产物状态机〔通用·机制 + 方法自创·定义〕
- **定位**：YAML 头部字段（id / status / spec / blocked-by / round…）表达产物身份与状态；八类产物各有固定状态机，箭头上标推进者（如 need：draft →confirmed（dev-clarify）→fulfilled（dev-accept））。check.sh 扫 frontmatter 得全貌，状态和文件不出现两张皮。每个技能只碰自己负责的那段状态。
- **来源**：YAML front matter 惯例（Jekyll 等静态站点工具链）；状态机应用为本会话定义。
- **落点**：蓝图 §6.1 总表。

### 八类产物（need / spec / design / ticket / review / acceptance / adr / research）〔方法自创〕
- **定位**：流程的全部落盘接口，各有固定模板：need 需求纪要、spec 规格、design 技术方案、ticket 工单、review 评审报告、acceptance 验收报告、adr 架构决策记录、research 调研报告。模板内嵌在写产物的技能里（执行者持有模板），METHOD.md 只写规则，避免两处漂移。
- **落点**：蓝图 §5.2、§6。

### NNNN-slug 命名〔方法自创〕
- **定位**：四位零填充、每类产物独立递增、从 0001 起；slug 一律 ASCII 小写短横线（中文标题放正文 H1，无合适英文用拼音）。正文引用必须带类型限定（"spec 0003"），裸编号只允许在 frontmatter 里。commit message 首行带 `[#NNNN]`。
- **落点**：蓝图 §5.6。

### FR-N 需求编号与追溯链〔外部·实践 + 方法自创·机制〕
- **定位**：need 里系统需求编号 FR-1、FR-2…；spec 验收场景标注覆盖哪个 FR；dev-accept 逐条核销。任何 FR 没有验收场景覆盖，`check.sh validate` 报**孤儿 FR**。"局部视野"问题的机械解法——不靠 agent 记得看全局，靠追溯链锁死 need/spec/acceptance。
- **来源**：需求可追溯性（requirements traceability）是需求工程标准实践。
- **落点**：蓝图 §4.2、§6.6 三道机械保证。

### ADR（Architecture Decision Record）〔外部〕
- **定位**：架构决策记录，状态 `accepted → superseded`（被新 ADR 取代时）。建 ADR 的三个条件（会话提炼）：难逆转、无上下文会困惑、真实权衡。dev-implement 装载上下文时读与改动区域相关的 ADR。
- **来源**：Michael Nygard《Documenting Architecture Decisions》（2011），accepted/superseded 是其标准生命周期。
- **落点**：蓝图 §6.1、§10.2 批 2 要点、§12 装载上下文。

### Given/When/Then〔外部〕
- **定位**：验收场景的书写格式（Given 前置 When 动作 Then 结果），need 的"场景"节与 spec 的"验收场景"节都用它。
- **来源**：BDD（Dan North）与 Gherkin（Cucumber）语法。
- **落点**：蓝图 §6.2、§6.3。

### 用户故事三段式〔外部〕
- **定位**："作为\<角色\>，我想要\<功能\>，以便\<收益\>"——spec"用户故事"节的固定格式，编号长列表。
- **来源**：XP 惯例（Connextra 模板）。
- **落点**：蓝图 §6.3。

### GLOSSARY.md 与统一语言〔外部·思想〕
- **定位**：懒创建的术语表；写产物时术语一律来自 GLOSSARY 且首次出现给定义；实现装载上下文时读它。对应 DDD"统一语言"（ubiquitous language）思想——文档一致性靠词汇一致。
- **来源**：Eric Evans《领域驱动设计》。
- **落点**：蓝图 §5.2、§7.1 ref-writing。

### CODING_STANDARDS.md〔通用〕
- **定位**：懒创建的编码标准，评审"标准轴"的依据；setup-workspace 按探测到的框架提供 starter（TS/Python/Go/Java）三选一种入；repo 已文档化的标准优先于 ref-review 的内置基线，工具已强制的跳过。
- **落点**：蓝图 §5.2、§11.1、§11.7。

### METHOD.md〔方法自创〕
- **定位**：方法论全文（规则、状态机、目录规范），由 setup-workspace 从蓝图 §2–§6 生成；不放产物模板（模板内嵌技能）。
- **落点**：蓝图 §5.2、§5.7、§13.3。

### 语义化版本与 CHANGELOG〔外部〕
- **定位**：dev-release 的版本号与变更日志遵循语义化版本（major/minor/patch）；CHANGELOG.md 懒创建，仅需要发布流程的项目。
- **来源**：semver.org；Keep a Changelog 惯例。
- **落点**：蓝图 §5.2、§10.2 批 3、§11.15。

### Progress 节与重入〔方法自创〕
- **定位**：工单模板固定含 `## Progress` 节（做到哪步 / 下一个动作 / 卡在哪，三行以内），是实现中断交接的载体；重入测试（中断后从盘上状态续接）是每个技能建完的必测项。
- **落点**：蓝图 §6.4、§8、§13.2 第 3 项。

## 四、实现与质量

### 红绿循环（Red/Green）〔外部〕
- **定位**：每个行为先写一个失败的测试，再写刚好让它通过的实现。禁止为变绿删测试、改弱断言、加条件跳过。
- **来源**：TDD（Kent Beck），红-绿-重构节奏。
- **落点**：蓝图 §12 实现纪律；ref-testing 展开标准。

### seam（接缝）〔外部〕
- **定位**：可以在不改动该处代码的情况下改变行为的位置。测试只写在 spec 预定的接口边界（seam）上；design 负责定义 seam，implement 遵守，是 V 右臂"模块边界测试"的载体。
- **来源**：Michael Feathers《修改代码的艺术》（Working Effectively with Legacy Code, 2004）。
- **落点**：蓝图 §4.2、§6.3 测试决策、§12。

### 只测外部行为，期望值来自独立来源〔外部·实践〕
- **定位**：好测试的两条核心标准：测外部行为不测实现；断言期望值必须来自独立来源（已知字面量、算例、spec），禁止用与实现相同的逻辑算出（同义反复测试）。禁止 mock 内部协作者、测私有方法。
- **来源**：GOOS（Freeman & Pryce《测试驱动的面向对象软件开发》）等测试质量论述；反模式清单在 ref-testing。
- **落点**：蓝图 §7.1 ref-testing、§12 禁止项。

### 深模块〔外部〕
- **定位**：好实现的标准之一——接口窄、做的事多；配套"命名表意、错误处理显式、边界情况被处理而不是被注释、代码读起来像叙事"。
- **来源**：John Ousterhout《软件设计的哲学》（A Philosophy of Software Design）。
- **落点**：蓝图 §7.1 ref-implementation。

### 投机泛化 / YAGNI〔外部〕
- **定位**：禁止无投机泛化（为 imagined future 加的抽象）——Fowler 坏味道之一；对应 XP 的 YAGNI（You Aren't Gonna Need It）。实现只做工单要求的事。
- **落点**：蓝图 §7.1、§12 禁止项（"实现验收标准之外的功能"）。

### diff 最小化〔通用〕
- **定位**：只改工单要求的；顺手重构无关代码是 review 的必抓项。
- **落点**：蓝图 §7.1、§12 边界纪律。

### 代码坏味道基线（Fowler）〔外部〕
- **定位**：ref-review 内置的坏味道清单（每条：是什么 → 怎么修），作为评审标准轴的兜底基线；repo 已文档化的标准优先于基线，工具已强制的跳过。
- **来源**：Martin Fowler《重构》（Refactoring）坏味道目录。
- **落点**：蓝图 §7.1 ref-review。

### 双轴评审（标准轴 + Spec 轴）〔方法自创〕
- **定位**：dev-review 的两条独立轴——标准轴（CODING_STANDARDS + 坏味道基线：写得对不对）与 Spec 轴（对照 spec/工单：缺失、走样、超范围——做的是不是要的）。两轴独立报告不合并重排，防止互相稀释；均为零阻断才算通过。
- **落点**：蓝图 §6.5、§11.7。

### 阻断 / 建议分级〔通用〕
- **定位**：每条 finding 的严重度分级；区分"违反标准"与"个人品味"，后者不阻断。每条 finding 必须可执行：文件:行 + 怎么改 + 为什么。
- **落点**：蓝图 §7.1 ref-review、§6.5。

### 失败测试先行（缺陷修复纪律）〔外部·实践〕
- **定位**：dev-fix 修复任何缺陷前必须先有复现该缺陷的失败测试，再修，再回归。分诊定级在前。
- **落点**：蓝图 §10.1、§10.2 批 2。

### 单向门 / 双向门〔外部〕
- **定位**：不可逆决策（单向门）与可逆决策（双向门）的分类。合并是单向门，必须问人；PR 正文模板固定含 `## Merge Danger`（单向门/双向门 + 影响半径）节。
- **来源**：亚马逊 Type 1 / Type 2 decisions（Bezos 股东信）。
- **落点**：蓝图 §8 决策点表、§11.8。

### 影响半径〔通用〕
- **定位**：一次改动可能波及的范围，PR 正文 Merge Danger 节要求写明。
- **落点**：蓝图 §11.8。

## 五、AI 协作与技能工程

### 技能（SKILL.md + frontmatter）〔外部·平台机制〕
- **定位**：ZCode 技能的载体：`~/.zcode/skills/<名>/SKILL.md`，frontmatter 只有 name 与 description；需要附件（如 ref-testing 范例库）放同目录 `*.md` 引用。slug 英文、内容中文。
- **落点**：蓝图 §13.1。

### description 第一道网〔方法自创〕
- **定位**：description 故意写得宽（承接"帮我写代码"这类直连请求），保证没走流程的请求也能命中技能，然后在入口被拦下并指路——门禁的价值恰恰在被拒绝的那一刻体现。
- **落点**：蓝图 §12 末段写法要求、§13.1。

### 拒绝路径〔方法自创·强调〕
- **定位**：门禁技能里拒绝路径写得和 happy path 一样认真：停止、转述缺什么、指路该跑哪个技能（如"spec 0003 还是 draft，先 /dev-spec 完成批准"）。"拒绝不是失礼，是本技能的职责。"每个技能建完必须测拒绝路径。
- **落点**：蓝图 §12、§13.2 第 2 项。

### 自动化契约（出口三形态）〔方法自创〕
- **定位**：每个流程技能完成后只允许三种形态之一，禁止做完沉默等指令：①自动调用下一个技能；②抛出决策问题（必须带默认建议，用户只需回"嗯"或纠正）；③被门禁拦停并指路。配套 `/sdlc next` 模式：自动推进到下一个决策点为止——"你只管决策，重复劳动归流水线"。
- **落点**：蓝图 §8。

### 决策点〔通用·词 + 方法自创·全表〕
- **定位**：全流程必须问人的点已穷举成表（spec 批准、分轮范围、拆分粒度、合并确认、定级、复盘采纳等），其余全部自动串联。合并确认是唯一的强制单向门。
- **落点**：蓝图 §8 决策点全表。

### 三层技能架构（L1 基础设施 / L2 参考 ref-* / L3 流程 dev-*）〔方法自创〕
- **定位**：技能体系分层：L3 流程技能驱动生命周期、持门禁、自动串联；L2 参考技能定义"什么是好"，由流程技能在指定时机加载；L1 基础设施是 check.sh + trackers/ + config.sh + METHOD.md + AGENTS.md 块。对应的三层分工：**技能=行为，参考=标准，脚本=判断逻辑**。
- **落点**：蓝图 §2 原则 6、§7。

### ref-* 参考技能（writing / implementation / testing / review）〔方法自创〕
- **定位**：四个内部参考——ref-writing（平实具体、例子优先、禁空洞抽象词、给数字/命令/文件名）；ref-implementation（深模块、显式错误处理、无投机泛化、diff 最小化）；ref-testing（只测外部行为、期望值独立、反模式清单）；ref-review（可执行 finding、阻断/建议分级、坏味道基线）。"什么是好"只存一份、按需进上下文，不污染每个会话。用户直呼 ref-* 时引导到对应流程技能。
- **落点**：蓝图 §7.1、§7.3、§11.3。

### 引用矩阵（越靠近实现层 reference 越密）〔方法自创〕
- **定位**：规定每个流程技能在什么时机加载哪个参考：文档类技能落盘前加载 ref-writing；dev-implement 开工装 ref-implementation + ref-testing（写测试前重读）；dev-review 评审前装 ref-review + ref-implementation；dev-fix 在失败测试之前装 ref-testing。
- **落点**：蓝图 §7.2。

### 上下文税〔方法自创·表述〕
- **定位**：技能全文每次进上下文，长篇教科书式技能是每个会话都在交的税——技能控制在 70 行左右，校验逻辑下沉脚本、标准下沉 ref-*、范例内嵌而非铺陈。
- **来源**：对 LLM 上下文窗口经济性的会话内表述。
- **落点**：蓝图 §12 写法要求。

### 触发测试 / 五项自测清单〔方法自创〕
- **定位**：每个技能建完必须过五项自测：①触发（3 句典型话术含一句没走流程的直连请求，验证 description 命中）；②门禁拒绝路径；③重入（中断后从盘上状态续接）；④产物过 `check.sh validate`；⑤出口三形态按自动化契约执行。
- **落点**：蓝图 §13.2。

### 先改文档，再改技能〔方法自创·治理规则〕
- **定位**：实现中发现设计缺陷，先改蓝图再改技能，保证文档与实物不漂移；每建完一个技能在蓝图 §10.2 标完成日期（蓝图兼作进度台账）。
- **落点**：蓝图 §13.3。

### 文风基准（dev-implement 范文）〔方法自创〕
- **定位**：dev-implement 全文作为 19 个技能的写法浓度基准：开头一句定性职责并预告拒绝行为；纪律用操作性规则不用口号；每个出口动作明确三选一；70 行左右。其余技能照此批量生产保证风格一致。
- **落点**：蓝图 §12。

### Matt Pocock 套件〔外部·现存技能集〕
- **定位**：本机已装的第三方技能链：对话 → to-spec → to-tickets → implement（内调 tdd）→ code-review → pr → retro，支线 research / domain-modeling / prototype / diagnosing-bugs / triage / handoff。定性：指令式（有规矩无检查、易绕过）——它是本方法的反面教材与共存对象。批 1 试用确认后，其生命周期类技能移入归档目录；写作类（writing-*）保留不冲突。
- **落点**：蓝图 §1、§10.3。

## 六、平台与扩展

### tracker 适配器〔方法自创〕
- **定位**：`.sdlc/trackers/{local,github,codeup}.sh` 适配器 + config.sh 的 `TRACKER` 枚举；新增 Gitee/GitLab/Jira 只需加一个适配器文件，15 个流程技能零改动——技能永远只管落盘。
- **落点**：蓝图 §5.5、§14。

### 出口三选一（本地 / GitHub / 云效 Codeup）〔方法自创·本项目语境〕
- **定位**：setup-workspace 交互式向导的第一问：产物与 issue 发布到哪。选 GitHub 验证 `gh` 已登录、选 Codeup 验证 `CODEUP_TOKEN`；凭据不通过回落本地并明确告知，不静默降级。
- **落点**：蓝图 §11.1。

### ZCode 草稿工作区〔外部·平台机制〕
- **定位**：会话发生在一个一次性草稿工作区（`~/.zcode/workspace/draft-<uuid>`），蓝图最初写在那里；归档入本仓库后才成为可版本化、可治理的真相源。
- **落点**：本档案开头归档说明、会话纪要。
