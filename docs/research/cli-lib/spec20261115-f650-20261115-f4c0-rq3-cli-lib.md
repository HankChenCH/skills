# RQ3 CLI 库选型调研：五维度对比 + 否决线 + 选型推荐 + 迁移方案（spec 20261115-f650）

## 1. 执行摘要（结论速览）

**推荐 commander 15**（15.1.0，2026-11-07 发布）。推荐依据全部来自本机实测：零运行时依赖、闭包下载增量约 0.64 MB（现行包下载量 2.4 MB 的 27%）、安装树 236 KiB、npx 冷启动中位 2.30 s 低于现行包 3.60 s（现行冷启动大头来自 @clack/prompts 而非解析层）、warm 启动与无依赖基线同为约 1.2 s 地板、`import` 成本 ≤ 30 ms、自带 typings、纯 ESM 对齐本包 `"type": "module"`、help 生成可被逐字整替（探针实证）、五候选中维护面最健康（7 open / 1165 closed）。

**否决（异常流 D，实测数据支撑）**：yargs 18（闭包下载 ~2.9 MB > 否决线 1.2 MB 的 2.4 倍、安装树 924 KiB、冷启动中位 4.23 s 为全场最高，比现行包还慢）。**警示（接近否决线，是否加严由 design 复核）**：clipanion 4.0.0-rc.4（下载 ~1.0 MB = 否决线的 82%、安装树 592 KiB 超警示线、2024-09-06 后无任何发布且 4.0 停留 rc 已 14 个月+）。

**迁移核心结论（FR-8/FR-5）**：任何候选库都无法"开箱"保持现行错误口径——现行 cli-args.js 是顺序敏感的单遍解析器（互斥/值必需/配对错误按 argv 顺序首个命中即抛），而五个候选的语义校验层（conflicts/required 等）都不产生我们的中文逐字文案。等价迁移的最小风险路径 = **库只负责 token 消耗与 help 旗标拦截，顺序敏感状态机原样保留为我们的校验层**，报错文案零改动。探针实证：五个库各按此模式接入后，16 个验收案例矩阵（--help/-h/互斥/值缺失/配对缺失/未知旗标/位置参数/组合取值等）输出与现行 CLI **字节级一致**（stdout/stderr/退出码三通道），commander 探针额外通过多错误先后序 2 案例。全部探针代码与原始输出在 §10。

## 2. 范围与方法

### 2.1 候选集

commander / yargs / cac / citty / clipanion（工票指定五候选）；另设两条参照线：**零依赖基线**（无解析库 fixture，测 npx 地板）与**现行包 fixture**（真实 @hankchen/infra 包形态，仅 @clack/prompts 依赖，测现行冷启动基线）。Node 内建 `util.parseArgs` 不作为候选（无 help 生成、无子命令模型，不满足 RQ3 动机=为子命令扩展引入库），仅作为"不引入"选项记录在 §8。

### 2.2 实测环境（本机一手）

- macOS 26.6（25G72）、Apple M5（arm64）、node v24.22.1、npm/npx 11.19.1、zsh
- 实验全部在 `/tmp/r3-exp/` 下空目录进行（fixtures、caches、runs 分目录），仓库目录内零安装/打包操作；现行包形态以 `package.json + bin/ + src/ + skills/ + plugins/` 拷贝至 /tmp 后 `npm pack` 取得
- 冷启动口径：`env npm_config_cache=<全新空目录> npx --yes file:<包tgz>`，即 **npm 缓存 + npx 安装缓存双冷**（首装下载 + 解压 + 运行）；热启动 = 同缓存重复运行；计时 `/usr/bin/time -p`（取 real）；每候选 3 个独立冷样本（中位数为准，离群值如实标注）
- 下载量口径：冷启动后 `du -sk` 该全新缓存目录（压缩态字节的稳定口径，3 样本一致）；安装树口径：`du -sk node_modules`（解压态）
- 探针口径：以真实 `parseArgs`/`renderHelp`（src/cli-args.js 的 /tmp 副本）为参照驱动，复刻 bin/infra.js 旗标路径出口（`✗ ${err.message}` + 提示行 + 退出码），16 案例 × 5 库逐字节 diff

### 2.3 版本与来源纪律

候选版本 = npm dist-tag latest（检索 2026-11-15）；特性结论带官方仓库/文档链接（§11），检索日期 2026-11-15；体积/冷启动全部为本机实测（§10 附命令与原始输出）。npm registry 元数据（版本/发布时间/engines）与本机 `npm view`/`npm pack`/`gh api` 查询均为检索当日一手查询。

### 5.3 测量注意（如实记录）

- 冷启动单样本受网络波动影响大（commander 首样本 4.23 s vs 后两样本 2.25/2.30 s），故取中位数并把全部样本列出（§10.2）。
- 排查记录：两轮批量补样脚本因 zsh 不对未引用变量做分词，`npx` 收到目录路径静默空转（0.12–0.15 s / 缓存 4 KB），已定位为脚本缺陷并重跑修正；有效数据以上表为准。zsh 分词坑同时命中过探针矩阵首轮运行（已用 `${=var}` 修正后重跑），留痕备查。

## 6. 维度三 + 四：模型扩展性与 help 等价复刻（探针实证）

### 6.1 子命令/旗标模型扩展性（维度三）

现行 CLI 是单命令五旗标；RQ3 的动机是给"两层菜单 → 子命令化"预留扩展面。五候选的模型：

- **commander**：`.command(name)` / `.addCommand()`、嵌套子命令、`isDefault` 默认命令、别名、独立可执行子命令、`preAction/postAction/preSubcommand` 生命周期钩子、help 分组。五候选中最成熟、文档最全的子命令模型（官方 README「Subcommands」节，检索 2026-11-15）。
- **yargs**：`.command()` + 位置参数 DSL（`<required>` `[optional]` `[variadic...]`）、middleware、`.commandDir()`。表达力强；18.x ESM 迁移后周边（plugins/coercion 生态）成熟度需要 round 2 引入时逐项复核。
- **cac**：git 风格 `cli.command('lint [...files]', 'desc')`、点嵌套选项（`--namespace.option`）、命令别名、默认命令、命令级未知选项校验（README：「Any unknown options will be reported as an error」——注意该特性是**命令级**的；本包现行形态是全局选项，探针确认 cac 在全局选项形态下不报未知旗标，若迁移把旗标挂进 default command 则 cac 也能拥有未知检测）。
- **citty**：`defineCommand({ subCommands })` 递归嵌套 + 懒加载子命令 + meta.alias/hidden。API 面小、心智负担低；0.2.x 未到 1.0。
- **clipanion**：class 命令 + `static paths` 路由 + 嵌套 + 选项代理/取反/连写（batches）+ Typanion 运行时校验。能力面广但 4.0 停留 rc、维护停滞（§9）。

### 6.2 help 生成能力：现行 --help 逐字复刻可行性（维度四）

现行 `--help` 是**一段固定文本**（src/cli-args.js `renderHelp()`，含中文用法/旗标/行为三段）。等价复刻的定义 = `-h`/`--help` 触发时**逐字节输出该文本**、退出码 0、不掺库自带格式。可行性判定（官方文档 + 探针双证）：

| 候选 | 库自带 help | 逐字整替路径 | 探针结果 |
|---|---|---|---|
| commander | 内置 help 渲染（configureHelp/addHelpText/分组） | 覆盖实例 `helpInformation()` 返回 `renderHelp()` 文本；`-h` 交库拦截（`commander.helpDisplayed` → exit 0） | **16/16 字节一致** |
| yargs | usage + 选项表自动排版（无法整替） | `.help(false)` 关闭内置 help；`h/help` 声明为普通布尔；状态机派发自印文本 | **16/16 字节一致** |
| cac | 自动 help（`cli.help(callback)` 只能后处理 section，官方 README 无整替口） | 不调用 `cli.help()`；解析后检查 `options.h/help` 自派发 | **16/16 字节一致** |
| citty | meta 自动生成（`--help/-h` 自动处理，官方 README；无整替文档） | 不用 `runCommand`（其内建 help 不可覆盖），改用导出的 `parseArgs` + 自派发（实际绕开库的 help/解析层） | **16/16 字节一致**（但库贡献趋零，见 §6.3） |
| clipanion | 自动 help 页 + 内建 help 命令；**4-rc 下 `-h` 短旗标在 schema 上触发 AmbiguousSyntaxError**（探针一手复现） | help 由状态机自派发；`cli.process()` 仅作未知旗标/位置参数检测（UnknownSyntaxError 可捕获、按消息模式重映射） | **16/16 字节一致** |

结论：**五库都能做到逐字复刻**，但 cac/citty/clipanion 的"整替"实为绕开库的 help 层自派发；只有 commander 与 yargs 在保留库 help 拦截的同时完成整替（commander 的 `helpInformation` 覆盖是官方文档支持的定制面，最稳）。

### 6.3 迁移等价探针（FR-5 防线的实证基础）

方法：参照驱动复刻 bin/infra.js 旗标路径出口（parse → catch 打 `✗ ${err.message}` + 提示行 exit 1；help 打 `renderHelp()` exit 0），16 案例矩阵覆盖：`--help`、`-h`、互斥两向（`--all --skills x`、`--plugins x --all`）、未知旗标（`--foo`）、位置参数（`positional`）、值缺失三态（`--skills`/`--plugins`/`--profile`）、配对缺失（`--profile dev`）、可重复取并集（`--skills a --skills b`）、逗号分隔（`--skills a,b`）、`--all`、合法插件对（`--plugins p --profile dev`）、无 profile 插件（`--plugins p`，parse 层返回 profile:null）、零旗标（interactive）。每案例比 stdout + stderr + 退出码三通道。

**结果：五库探针全部 16/16 与现行 CLI 字节一致**；commander 探针另通过 2 个多错误先后序案例（`--all --skills dev-spec --foo` 互斥先于未知旗标、`--foo --all --skills dev-spec` 未知旗标先行）。

各库达成等价所需的接入模式（round 2 的工程蓝图，按"语义状态机保留"分层）：

- **commander**：`helpInformation()` 覆盖 + `exitOverride()` + `configureOutput({ writeErr: () => {} })`（抑制库自带 `error: ...` 行）+ `showSuggestionAfterError(false)`（关 "did you mean"）+ `allowUnknownOption()`/`allowExcessArguments()`（把未知旗标与位置参数的检测顺序让给状态机）+ 错误码通道（`commander.helpDisplayed` → exit 0）。库保留职责：token 消耗、`-h/--help` 拦截、值类型化。
- **yargs**：`.help(false)` + `.strict()` + fail 处理器消息重映射 + `.help`/`h` 声明为普通布尔；逗号分隔由我们的 coercion 完成（yargs 类型化消耗 `--skills a,b` 得 `['a,b']` 单元素，需自行 split）。
- **cac**：无全局未知旗标校验、无 strict → 未知/位置参数全部由状态机预扫描承担；库只做类型化值消耗与（可选的）help 后处理。
- **citty**：导出 `parseArgs` 无 schema 值消耗、无 strict，`runCommand` 内建 help 不可逐字覆盖 → 库近乎只剩 token 化底座。
- **clipanion**：`cli.process()` 抛 `UnknownSyntaxError`（可捕获、消息含未知旗标/多余位置参数原文）做检测通道；`-h` 短旗标 4-rc schema 歧义（AmbiguousSyntaxError）→ help 自派发。

诚实结论：**等价的关键不是"选哪个库"，而是"语义状态机必须保留在我们这侧"**。五库在此模式下等价；差异在于库还能替我们承担多少（未知检测：commander/yargs/clipanion 有、cac/citty 没有；值消耗：commander/yargs/cac/clipanion 有、citty 无 schema 时没有；help 拦截：仅 commander/yargs 可保留库拦截）。

## 7. 异常流 D 承接：体积否决线（FR-6 继承 need 异常流 D）

### 7.1 阈值建议（归 design 拍板，本报告给数据支撑）

否决线的锚点选择：冷启动 wall-time 单样本受网络波动影响（§5.3），**不适合作为阈值载体**；warm/import 成本全库趋零（§5.2 读法 3）也不需要卡。真正确定性、可复核的量是**首装字节与解压树**。据此建议（建议值，design 可按带宽分布加严/放宽）：

- **R1 否决线（下载量）**：候选依赖闭包压缩下载量（全新缓存口径）> **1.2 MB** → 否决。依据：现行包全量下载 2.37 MB（其中技能资产 tarball 仅 309 KB，交互层 clack 占 2.3 MB）；一个"参数解析"用途的依赖超过现行包下载量的一半（>1.2 MB）即构成 need 异常流 D 所指的"明显增重"。
- **R2 警示线 / 否决线（安装树）**：候选闭包安装树（解压）> **500 KiB** 警示、> **1 MB** 否决。依据：解压树影响 npx 落盘与磁盘占用，1 MB ≈ 现行包 tarball 的 3 倍，对解析用途明显失配。
- **R3 辅助口径（冷启动）**：候选冷启动中位显著高于现行包（本机数据：现行 3.60 s）→ 一票警示，交 design 结合 R1/R2 复核；不单独作为否决依据（波动性理由如上）。

### 7.2 逐候选判定（显式标注）

| 候选 | R1 下载量（线 1.2 MB） | R2 安装树（警示 500 KiB / 否决 1 MB） | R3 冷启动中位（现行 3.60 s） | 判定 |
|---|---|---|---|---|
| commander | 676 KB ✓（56% 线） | 236 KiB ✓ | 2.30 s ✓ | 通过 |
| cac | 484 KB ✓（40% 线） | 56 KiB ✓ | 2.32 s ✓ | 通过 |
| citty | 148 KB ✓（12% 线） | 56 KiB ✓ | 2.26 s ✓ | 通过 |

| clipanion | 996 KB ⚠（83% 线） | 592 KiB ⚠（超警示线，未达否决线） | 2.90 s ✓ | **警示**：逼近 R1 否决线 + R2 超警示线；叠加维护停滞（2024-09 后零发布、4.0 停留 rc），接近否决线，由 design 复核决定是否加严 |

异常流 D 验收要求的"超阈值候选显式标否决及实测数据"由 yargs 行满足（§10 附实测原始输出）。

## 8. 结论：选型推荐（FR-8）

**推荐 commander 15**。理由（逐条对应实测数据）：

1. **体积/冷启动全绿**（§5）：零运行时依赖、闭包下载 676 KB（否决线 56%）、安装树 236 KiB；冷启动中位 2.30 s 低于现行包 3.60 s；warm 与地板同值、import ≤ 30 ms——引入后的使用者可感知成本只增加首次 npx 约 +1 s（相对现行包），其后无差异。
2. **ESM/TS 原生度最高档**（§4）：纯 ESM 对齐本包形态；自带 typings + 官方 extra-typings 侧包可选强化，匹配全仓 TS 直跑方向。
3. **子命令扩展性最成熟**（§6.1）：`.command()` 模型 + 生命周期钩子，为两层菜单子命令化预留的面最大；文档与社区规模（28.5k stars）使 round 2 引入风险最低。
4. **help 逐字整替是官方定制面**（§6.2）：`helpInformation()` 覆盖 + help 拦截保留在库侧，是五库中唯一"整替走官方口子"的方案（yargs 走 `.help(false)` 关闭口，次之）；16 案例矩阵 + 多错误先后序案例探针全绿。
5. **维护面五库最健康**（§9）：2026-11-07 刚发 15.1.0，open issue 仅 7、closed 1165。需如实记入的成本：major 年更节奏（14.0.0 2025-05-18 → 15.0.0 2026-05-29），round 2 引入即锁定年度升版预算。

**备选**：cac 7（最轻量线：56 KiB / 484 KB / 2.32 s，同为纯 ESM + TS；代价 = help 无法整替需自派发、全局形态下无未知旗标检测、issue 关闭率约 58% (45/77)、社区面小）。citty（模型干净但 0.2.x 未到 1.0，0.x 阶段 breaking 风险由其版本号如实承载；open 84 > closed 48）。

**不推荐**：yargs（否决，§7.2 三重数据）；clipanion（警示：近否决线 + rc 停滞，除非 design 接受其体量与维护风险）。

**"不引入"选项记录在案**：Node 内建 `util.parseArgs`（零字节零冷启动增量）无 help 生成与子命令模型——若 round 2 判断两层菜单子命令化不再需要，则维持手写 cli-args.js（spec 已锁定本轮不替换）与引库相比是合法保守解；引库的前提正是子命令扩展诉求，这也是 commander 相对 util.parseArgs 的存在意义。

## 9. 迁移方案（FR-8；FR-5 防线 = 报错文案逐字不变）

以推荐库 commander 15 为蓝本。目标形态：`src/cli-args.js` 对外接口（`parseArgs(argv)` / `renderHelp()`）不变，内部由"手写循环"换为"commander 解析 + 语义状态机校验层"，bin/infra.js 零改动。

### 9.1 现行旗标语义映射表

| 现行（cli-args.js） | 语义 | commander 15 表达 | 等价要点 |
|---|---|---|---|
| `--all` | mode='all'，出现即生效，与 --skills/--plugins 互斥 | `program.option('--all', '安装技能类型全部条目（免交互）')` | 布尔旗标；互斥判定**不**用 `.conflicts()`（库的错误文案不可控），保留在我们的状态机层 |
| `--skills <名[,名...]>`（可重复，逗号分隔，取并集保序） | 逐次合并去重（首现顺序） | `program.option('--skills [names]', '按条目指定安装；逗号分隔，可重复出现，取并集', collectFn)`，collectFn 内做 `split(',')+trim+filter+Set 去重` | 值消耗交给库（`--skills a b` 的值关联与位置参数区分由库保证）；并集语义在 collectFn 复刻 |
| `--plugins <名[,名...]>`（同上；与 --profile 配对） | 同上 | `program.option('--plugins [names]', …, collectFn)` | 同上；registry 包名不做形态校验（与现行一致） |
| `--profile <名>`（只与 --plugins 配对，先后顺序无关） | 配对检查延后到解析结束 | `program.option('--profile [name]', …)`；配对校验保留在我们层（解析后 `mode!=='plugins' && profile!==undefined` → 逐字报错） | 库侧 required=false，不产生库文案 |
| `-h` / `--help` | 即时派发 help，优先于其后错误 | `program.helpOption('-h, --help', '显示本帮助')`（默认启用）+ `program.helpInformation = () => renderHelp()` 覆盖 | 逐字输出 + `commander.helpDisplayed` → exit 0；库继续负责拦截时机 |
| 未知 `--xxx` | `未知旗标 ${arg}；可用旗标：…（--help 查看示例）` | `allowUnknownOption()` 关闭库检测；状态机 default 分支检测后抛我们的文案 | 未知检测顺序让给状态机 = 与 cli-args 错误触发顺序完全一致（探针实证含多错误先后序 2 案例） |
| 位置参数 | `不接受位置参数「${arg}」…` | `allowExcessArguments()` 关闭库检测；状态机 default 分支检测 | 同上 |
| 旗标清单文案 | `FLAGS.join('、')` | 常量照搬 | 文案零改动 |

### 9.2 互斥校验等价方案

不使用库的 `.conflicts()`/`.check()`（其错误文案与触发时机都不可控，FR-5 会破）。方案 = **保留 cli-args.js 的顺序敏感状态机为后置校验层**：commander 解析成功后，按 argv 顺序走一遍状态机（--all/--skills/--plugins/--profile/未知/位置参数/值缺失），在**与现行完全相同的触发点**抛**逐字相同**的 `Error`；bin/infra.js 的 catch 出口（`✗ ${err.message}` + 提示行 + exit 1）不动。探针已证明该层能复刻 cli-args 的全部错误触发顺序（16 案例矩阵 + 2 多错误先后序案例）。保留状态机还天然保住两条现行边角语义：值缺失判定"旗标后无 token 或空串"（不看是否以 `-` 开头，`--skills -h` 取 `-h` 为值）、配对检查延后到解析结束（`--profile` 与 `--plugins` 顺序无关）。

### 9.3 错误口径等价方案（FR-5 防线：文案逐字清单 + 出口通道映射）

**逐字文案清单（迁移后必须一字不差，含全角标点与空格）**：

1. `--all 与 --skills 互斥：全装与按条目指定只能选一`
2. `--plugins/--profile 与 --all/--skills 互斥：插件安装与技能安装只能选一`
3. `--skills 需要至少一个技能名（如 --skills dev-spec,dev-plan）`
4. `--plugins 需要至少一个名字（如 --plugins a,b）`
5. `--profile 需要一个 profile 名（如 --profile dev）`
6. `--profile 需与 --plugins 配对使用（插件安装指定目标 dsh profile）`
7. `未知旗标 ${arg}；可用旗标：${FLAGS.join('、')}（--help 查看示例）`
8. `不接受位置参数「${arg}」：本命令只认旗标，条目请用 --skills/--plugins 指定（--help 查看示例）`

外加 bin 层两行（不在本票改动面，列出仅为完整性）：`✗ ${err.message}` 前缀行、`  运行 npx @hankchen/infra --help 查看全部旗标与示例。` 提示行；以及 `--help` 正常路径的 `renderHelp()` 全文（§9.1 整替保证）。

**commander 出口通道映射表**（库产生的每条通道 → 我们的处置）：

| commander 通道 | 处置 |
|---|---|
| `CommanderError code=commander.helpDisplayed`（-h/--help 拦截完成） | 直接 `exit 0`（helpInformation 覆盖已输出我们的文本） |
| 库自带 stderr `error: unknown option '--x'` 行 | `configureOutput({ writeErr: () => {} })` 静音（库检测已让位给状态机，不应有残留；静音为保险） |
| "did you mean" 建议行 | `showSuggestionAfterError(false)` 关闭 |
| `commander.excessArguments` | 已由 `allowExcessArguments()` 关闭，位置参数交状态机（保触发顺序） |
| 未知选项 | 已由 `allowUnknownOption()` 关闭，交状态机 |
| 选项值消耗（含逗号串） | collectFn 内 split+trim+filter+按首现去重（等价 cli-args mergeValues + Set） |
| CommanderError 其他码 | 兜底 `fail(未预期的解析错误：…)`（探针中仅作哨兵，矩阵未触发） |

**等价性验收方法（round 2 直接复用）**：把 §6.3 探针矩阵 + 2 多错误案例 + 既有 e2e（install.test.js 旗标用例）作为迁移回归集，断言三通道字节一致；既有全量测试（spec FR-5：--help 文本、互斥报错、版本拦截文案逐字不变）为最终防线。

### 9.4 残余边界与风险（如实列出，交 round 2/design 消化）

1. **`--skills -h` 类"值以 `-` 开头"**：cli-args 取 `-h` 为 --skills 的值（mergeValues 收 `['-h']`）；commander 类型化消耗可能把 `-h` 认作旗标。探针矩阵未含此案例；迁移时应在状态机层保持"值缺失判空"语义并实测该案例（建议 round 2 回归集纳入）。yargs/cac/clipanion 同类案例在探针中未触发分歧（值消耗口径与我们一致），commander 需复测。
2. **裸 `--` 分隔符**：cli-args 将 `--` 报"未知旗标 --"；commander 将其作为选项结束符吞掉（不进 argv）。若要保逐字行为需在 parse 前预扫描 `--`。该输入无既有 e2e 覆盖，属"是否值得保真"的决策点。
3. **未知旗标与语义错误共存时的先后序**：探针已覆盖 2 例（互斥在前/未知旗标在前），状态机方案下顺序由我们保证；更多组合（值缺失+未知旗标等）建议 round 2 回归集全排。
4. **commander major 年更**：14→15 相隔 12 个月，15 系内 API 已有破坏性改动先例（`exitProcess` 移除 → `exitOverride`，本票探针一手踩到）；round 2 引入时在 lockfile 钉 minor 并把年度升版写进依赖维护清单。
5. **库的 help 拦截时机**：`-h` 的"即时派发优先于其后错误"语义由 commander 的 helpDisplayed 通道保证（探针矩阵 `--help`/`-h` 两例验证）；若 round 2 调整 helpOption 配置需重跑矩阵。

## 12. spec 缺口与提示（不改 spec，仅报告）

- spec RQ3 契约要求"错误口径等价方案"，未约定等价性的**验证口径**（逐字节 vs 语义等价）。本报告按最严口径（三通道逐字节 + 触发顺序一致）给出探针证据；若 design 认为"语义等价"即可，round 2 可放松 `--` 分隔符等边角保真（§9.4.2），该取舍留 design。
- 异常流 D 的阈值 spec 明示"归 design"，本报告给的建议线（R1 1.2 MB / R2 500 KiB 警示·1 MB 否决 / R3 冷启动辅助）待 design 拍板后回填为正式阈值。
