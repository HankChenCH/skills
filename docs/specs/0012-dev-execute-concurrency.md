# dev-execute 并发执行优化：改动面互斥 + 异步流水线 + 宿主自适应派发

## 问题陈述

dev-execute 的并发运行有三个用户可感问题（源：need 0010，用户 2026-10-31）：

1. **合回冲突常态停机**：3 次 dev-execute 运行中 2 次因同层票合回冲突触发异常流，
   停下问人。根因是拆票无"同层票改动面互斥"约束——垂直切片刻意切穿所有层，
   同层两票各自动 schema 或共享接口，实现期物理隔离不冲突，合回期后合者必撞。
2. **主会话同步干等**：子代理派发后主会话阻塞到全部完成才进评审与合回，
   期间用户输入得不到响应，先完成的票也不能先行评审——层屏障模型把一切
   卡到"同层全部完成"。
3. **并发模型写死子代理**：同一技能要跑在 ZCode、Claude Code、Codex、
   DeepSeek harness 四个宿主上（用户确认使用面），部分宿主无子代理能力，
   部分宿主提供比子代理更优的并发原语（如 ZCode 的声明式工作流），
   写死一种意味着至少一类宿主不可用或次优。

## 方案

把"并发"从一个写死的派发动作，改造为**拆票端消除冲突面、编排端流水线推进、
派发端按宿主自适应**的三段式：

1. **拆票端（dev-plan）**：拆票时逐票落"改动面"行（预估触碰的文件/模块），
   同层票改动面相交 → 并票、标 blocked-by 串行、expand–contract 重切三选一；
   落盘后同层票改动面互斥，并行实现后合回不再常态冲突。
2. **编排端（dev-execute）**：
   - 开工预检：建图后基于票改动面行与代码现状预估同层重叠，报告风险与
     默认建议，并入开工确认（不硬拦、不新增人工门）。
   - 异步流水线：实现子代理后台派发，主会话不被锁死、可随时响应用户；
     票 implemented 即先行编排评审，approved 且依赖满足即合回+预演——
     层屏障取消，"全部票 implemented 且预演绿"的全绿判定保留。
   - 合回预检序：每次合回前 merge-tree 干跑，同层按无冲突序合回；
     全序冲突才停机问人（异常流语义不变）。
   - 宿主自适应派发：能力探测 + 回退链（声明式工作流 > 后台子代理 >
     同步子代理 > 串行逐票），开工确认时声明本次并发形态。
3. **前置调研**：《四宿主并发原语对照》调研报告（need 0010 FR-5）经
   /dev-research 先行产出，作为派发回退链的设计输入；FR-6 实现票开工前
   报告须在盘（spec 0010 superpower 先例）。
4. **顺带成文**：run-mechanics 修订时一并落 ADR 0003 的物化条文
   （用户 2026-10-31 拍板）——同批节原子落地，避免同节两轮改。

## 用户故事

- 作为仓库主人，我想让同层拆出的票互不触碰同一处代码，以便并行实现后
  合回不再常态冲突停机。
- 作为仓库主人，我想在开工前看到同层票的冲突风险报告与默认建议，以便
  带着信息决定开不开工。
- 作为仓库主人，我想在并行实现期间继续跟智能体对话、先评审已完成的票，
  以便不干等最慢的那张票。
- 作为仓库主人，我想让已评审通过的票立即合回并预演，以便缩短整张 spec
  的交付时间。
- 作为仓库主人，我想让 dev-execute 在我的四个宿主上都能用该宿主最优的
  并发方式跑，以便一套技能四处可用。
- 作为仓库主人，我想在开工确认时就知道本次运行用哪种并发形态，以便对
  运行节奏有预期。

## 实现决策

- **改动面承载**：dev-plan 拆票时在票正文增"**改动面：**"行（预估触碰的
  文件/模块清单，口径 = 目录或模块名，不写行级路径——need 0010 假设 A2
  在此收口）；互斥判定读该行 + 代码粗扫交叉；不改票 frontmatter schema，
  check.sh 零改动（validate 不受理正文行）。
- **互斥处置三选一**：同层两票改动面相交 → 并票 / 标 blocked-by 串行 /
  expand–contract 重切；判定属 dev-plan 会话内判断，在既有"拆分粒度确认"
  决策点一并向用户确认，不新增人工门。
- **开工预检**：dev-execute 建图后、开工确认前逐层比对同层改动面行并与
  代码现状粗扫交叉；高重叠对（票号 + 重叠面）+ 默认建议（串行化或回
  /dev-plan）并入开工确认呈现；改动面行缺失的票标"改动面未知"，不猜测。
  不硬拦，仍是开工确认一次问。
- **异步派发与先行评审**：实现子代理改后台派发（宿主支持时），完成通知
  驱动后续编排、不轮询；主会话派发后可响应输入；票 implemented 通知到达
  即编排评审——评审在票 worktree 内进行、不触碰运行分支，与在办票互不
  干扰（既有安全基础，need 0010 已查证）。
- **流水线合回**：层屏障取消——票 approved 且 blocked-by 满足即合回+预演；
  同层票在各自派发时基线上实现、合回后不重放基线（互斥保证合回干净）；
  运行依赖顺序图的"层"保留为展示与依赖满足判定视图；"全部票 implemented
  且预演绿"的全绿判定保留。
- **合回预检序**：每次合回前 merge-tree 干跑；"同层任一序"（run-mechanics
  §7 既有表述）赋予机械选择语义 = 无冲突序优先；候选序全冲突 → 停机问人。
  采纳 need 0010 假设 A1。预检只排序，不做冲突内容的自动解决。
- **宿主自适应派发**：派发环节收敛为能力探测 + 回退链——声明式工作流
  （若宿主提供）> 后台子代理 > 同步子代理 > 串行逐票；探测对象与优先序
  以 FR-5 报告为准；回退链末端串行保证任何宿主可运行；开工确认时声明
  本次并发形态与命中原因。
- **前置调研**：FR-5 报告经 /dev-research 产出，落 docs/research/ 顺位
  （现最大 0002 → 0003），先于 dev-plan 拆票（FR-6 票的改动面与 blocked-by
  依赖其结论）；格式沿 docs/research/0001 先例：一手来源引用 + 检索日期，
  覆盖四宿主 × 四维（并发原语清单 / 后台与状态回收 / 隔离能力 /
  无子代理退化方案）。
- **物化成文吸收**（ADR 0003，用户拍板）：run-mechanics §4 增"建 worktree
  后物化过程档"、§7 增"合回前同步翻转副本"、§8.4 改"done 落盘不提交"——
  与本 spec 并发修订同批落，运行语义一次成文，ADR 0003 修订面随之核销。
- **治理顺序**：先改蓝图再写技能——蓝图 §11.17（dev-execute 规格修订：
  流水线合回 / 异步派发 / 预检 / 自适应回退链）、§11.5（dev-plan 规格修订：
  改动面互斥纪律与改动面行）、§8 决策点表 dev-execute / dev-plan 行同步、
  修订记录新条目；§7.2 引用矩阵与 §10.1 技能清单零改动（无新技能）。

## 验收场景

- [FR-1 | 工单级] Given approved spec 待拆票，When dev-plan 发现两张拟同层
  票改动面相交，Then 并票 / 标 blocked-by 串行 / expand–contract 重切三选一
  处置并经拆分粒度确认；落盘后同层票改动面互斥且每票正文带"改动面"行。
- [FR-1 | 工单级] Given 某票正文无"改动面"行，When dev-execute 开工预检，
  Then 该票按"改动面未知"处理并在报告中标注，不猜测改动面。
- [FR-2 | 工单级] Given 运行依赖顺序图已建，When 开工预检发现同层高重叠对，
  Then 开工确认中呈现重叠对（票号 + 重叠面）与默认建议（串行化或回
  /dev-plan）；用户拒绝开工则零写入退出。
- [FR-3 | 工单级] Given 宿主支持后台派发且第 1 层 3 票并行实现，When 票 A
  先 implemented，Then 主会话立即编排评审 A 而不等 B/C；期间用户输入可被
  随时响应。
- [FR-4 | 工单级] Given 票 A 评审 approved 且 blocked-by 满足，When 同层
  B/C 仍在实现，Then A 即合回运行分支并预演；B/C 完成后按无冲突序合回，
  互斥成立时合回全部干净。
- [FR-4 | 工单级] Given 同层 A/B 均已 approved 且 merge-tree 预检显示 A 先
  合回会冲突、B 先不会，When 机械合回，Then 选 B 先合回；两序皆冲突才
  停下问人（异常流，不自动解冲突内容）。
- [FR-4 | 工单级] Given 全部票合回且末次预演绿，When 运行收口，Then 收口链
  与既有一致：一次 PR → pre-push → 合并确认（单向门）→ 票 done → 清理 →
  出口报告指路 /dev-accept。
- [FR-5 | 工单级] Given spec 0012 approved 且 FR-6 实现票开工，When 检查
  前置交付，Then docs/research/ 顺位调研报告已在盘：四宿主 × 四维覆盖、
  关键结论带一手来源引用与检索日期、事实与判断分离。
- [FR-6 | 工单级] Given 宿主提供声明式工作流原语，When dev-execute 开工，
  Then 按回退链选工作流并行派发；宿主仅有同步子代理时退回同步并行；
  两者皆无时串行逐票。
- [FR-6 | 工单级] Given 回退链命中非最优档，When 开工确认，Then 已向用户
  声明本次并发形态与命中原因。
- [FR-4 | 集成级] Given 三层依赖链 spec 在演练仓库整链运行，When 层 1 两票
  并行且先后完成，Then 流水线全程零合回冲突停机、人工介入仅开工确认与
  合并确认两次、主会话不被阻塞（后台完成通知驱动）。
- [FR-6 | 集成级] Given 演练环境模拟仅具串行能力的宿主，When dev-execute
  从开工到收口整 spec 运行，Then 全链以串行逐票完成，派发 / 评审 / 合回 /
  预演 / 收口各门禁语义不变，开工确认声明了串行形态。

## 非目标

- 不改 dev-implement 单票纪律、dev-review 单票评审路径与 `.sdlc/check.sh`
  （need 0010 非目标 ①；物化成文同款零门禁改动，ADR 0003 后果条款）。
- 不追求全部宿主最优并发形态——无子代理宿主允许串行退化
  （need 0010 非目标 ②）。
- 不改运行依赖顺序图"会话内计算、不落盘"边界（need 0010 非目标 ③）。
- 互斥判定不进门禁：改动面互斥是 dev-plan 会话内纪律，validate 不校验
  票正文"改动面"行（check.sh 零改动的推论）。
- 不做冲突内容的自动解决：merge-tree 预检只排合回序，冲突内容仍停下问人
  （need 0010 场景异常 2）。
- dev-review 编排模式契约不动：异步化只改派发与调度节奏，评审仍显式工单
  范围 + diff 基线 = 运行分支，出口止于 approved。
