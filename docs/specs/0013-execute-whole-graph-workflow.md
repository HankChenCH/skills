# dev-execute 档 1 整图单运行：工作流承载全链编排

## 问题陈述

档 1（声明式工作流档）命中时，一次 dev-execute 运行被拆成 N 个工作流运行——每张就绪票各开一个，票 4 等前置票合回后再开一个。编排用户看到的是散落运行而非排好的执行图；每次运行按 CreateWorkflow 契约各需一次确认（4 票 = 4 次）；每个脚本只含一个 `agent()` 调用、零控制流，原语的执行图、确定性门、运行内人工门、断点恢复全部闲置。运行依赖顺序图只活在主会话编排逻辑里，用户无法从运行视图看进度。（源：need 0011，用户 2026-10-31「1-3 分别开工作流，4 在开工作流……我期望一个工作流排好执行图」。）

## 方案

把档 1 的「每票一个工作流运行」改为**整图单运行**（GLOSSARY 已登记）：开工确认后主会话生成一个工作流脚本，把整张运行依赖顺序图声明进去——同层票 fan-out 并行、blocked-by 边用控制流表达；每票阶段链（建票 worktree 并物化 → 实现子代理 → 先行评审子代理 → merge-tree 预检序合回 → 预演确定性门）逐票在链内串行、跨票按依赖并行；§8 异常流与合并确认经升级提问/洞穴在图内停下问人；fix 票经脚本修订补图；收口链（PR 准备 → pre-push → 合并确认 → 合并 → 票 done → 清理 → 出口报告）全部入图。人工交互仍恰两次：开工确认（图外）+ 合并确认（图内）。档 2–4 零变化。

## 用户故事

- 作为编排用户，我想一次确认后看到一张工作流执行图从开工推进到出口报告，以便不在 N 个散落运行里拼进度。
- 作为编排用户，我想让同层票自动并行、依赖票自动接续，以便主会话不再逐票派发。
- 作为编排用户，我想在实现期间随时插话、先完成的票先评审，以便不干等最慢的票（流水线语义保持）。
- 作为编排用户，我想让预演红、合回冲突这些异常在图内停下来问我，以便决策点不散落。
- 作为仓库主人，我想在开工确认时就知道本次运行是整图单运行还是逐票派发，以便对运行形态有预期。

## 实现决策

- **档 1 重定义（need 0011 假设 A1 裁决）**：档 1 = 整图单运行，唯一形态；旧「每票一个工作流运行」形态废除，不留档内中间形态。探测判据升级为四能力齐备：脚本控制流（fan-out/join 表达依赖）、确定性门（命令门承载预演）、运行内人工门（升级提问/洞穴）、运行记录与恢复（journal 重放 + 脚本修订缓存复用）。缺任一 → 顺位落档 2。DeepSeek harness 预览期工作流无恢复机制，维持调研 0003 结论落档 3 起步；Claude Code dynamic workflows 的运行内人工门能力由实现票按调研 0003 时效条款核验后定档。
- **图的生成与参数**：开工确认后主会话生成一次工作流脚本；票清单、blocked-by 边、并行度上限以类型化参数传入，图仍会话内计算、不落盘（need 0010 非目标 ③ 延续）；并行度默认上限 4 经工作流并发度参数承载，SKILL 调用参数透传覆盖。
- **票阶段链（need 0011 假设 A2 裁决）**：每票在图内为一条阶段链——依赖满足时建票 worktree 并物化过程档（ADR 0003 裁决 1，由脚本 git/文件门面承载）→ 实现子代理执行 dev-implement 纪律全文（随派发传参考技能，既有约定）→ 评审子代理执行 dev-review 编排模式（报告契约 branch/tickets 不变）→ merge-tree 干跑预检序 → 合回 + 翻转副本同步（ADR 0003 裁决 2）→ 预演确定性门（全量检查 + spec 验收场景已有自动化承载的集成级测试）。评审由图内子代理承载而非通知主会话介入：运行中间态无逐票完成通知，主会话介入须轮询，违背「通知驱动不轮询」约束（need 0010 拍板）。评审机械问题修后图内重跑该票评审阶段；设计级阻断走异常流提问。
- **人工门承载（FR-4）**：§8 五类异常流（设计级阻断 / spec 缺口 / 预演失败 / 合回冲突 / 收口 pre-push 不过）与合并确认经升级提问/洞穴在图内停下问人——提问带连坐阻塞面与指路，语义零回退：沉默不算确认、不自动解冲突、不自动重试、不自动改 spec、合并未执行不清理。
- **fix 票补图（need 0011 假设 A3 裁决）**：异常流用户决策需开 fix 票时，主会话按 /dev-fix 开 fix 票，随后以脚本修订把 fix 票并入运行图重算后续，已完成步经缓存复用不重做；修订不成 → 停机问人。
- **收口链入图（2026-10-31 拍板）**：全绿后图内继续收口——收口门禁 fresh 全量检查（确定性门）→ PR 准备（子代理按 dev-ship 前半三节模板起草；平台建 PR 或本地清单完整呈现，跟 TRACKER）→ pre-push 门 → 合并确认升级提问（合并方式与是否打 tag 一并问清，显式确认才执行）→ 执行合并（平台 PR 平台合并 / 本地主工作区合并）→ 票 done 落盘不提交（ADR 0003 裁决 3）→ 清理票/运行 worktree 与分支（先 worktree 后分支）→ 运行结算报告即出口报告（逐票终态 + 运行摘要 + 指路手动验收）。
- **盘上状态机不动**：票 frontmatter + worktree 仍是唯一运行真源；中断续接按既有推导（运行/票 worktree + 票状态）结合运行记录恢复续跑，已合回票不重做；不新增产物类型。
- **档间差异声明（FR-5）**：开工确认声明含本次形态（整图单运行 / 逐票派发 / 串行）与命中原因；命中档 1 时说明整图单运行与逐票档的编排模型差异（图承载全链 vs 主会话逐票编排）。
- **治理顺序**：先改蓝图再写技能——蓝图 dev-execute 规格节修订（档 1 整图单运行 + 探测判据 + 图内人工门 + 收口入图）、§8 决策点表核对（人工门仍恰两次，预计零改动）、修订记录新条目（v1.22 顺位）；引用矩阵与技能清单零改动（无新技能）。

## 验收场景

- [FR-1 | 工单级] Given 会话四能力齐备（控制流 / 确定性门 / 运行内人工门 / 记录恢复），When 开工探测，Then 命中档 1 并声明整图单运行形态；缺任一能力 Then 顺位落档 2 并声明原因，不落已废除的逐票工作流形态。
- [FR-1 | 集成级] Given 4 票 spec（票 1–3 同层、票 4 blocked-by 前三票）命中档 1，When 用户开工确认，Then 全程恰好一次工作流运行承载全图：确认一次、票 1–3 并行实现、票 4 依赖满足后由图接续，直到出口报告。
- [FR-2 | 工单级] Given 图内票 1 先实现完成，When 其评审阶段启动，Then 评审子代理不等票 2/3 即先行评审；报告契约（branch/tickets）与既有编排模式一致。
- [FR-3 | 工单级] Given 图内某票合回后预演红，When 确定性门失败，Then 后续票合回与派发被门拦截，异常流升级提问触发。
- [FR-4 | 工单级] Given 运行中候选序全冲突（或评审设计级阻断 / spec 缺口 / pre-push 不过），When 图内升级提问，Then 呈现连坐阻塞面与指路；用户决策前不自动解冲突、不自动重试。
- [FR-4 | 集成级] Given 预演红且用户确认开 fix 票，When 主会话开 fix 票并修订脚本补图，Then 运行续走且已完成步经缓存复用不重做。
- [FR-4 | 工单级] Given 运行全绿到达合并确认，When 图内升级提问，Then 合并方式与 tag 一并问清、显式确认才执行合并；拒绝则停在该门、盘上状态即运行状态、不强推。
- [FR-5 | 工单级] Given 档 1 命中开工确认，When 呈现声明，Then 含整图单运行形态、与逐票档的编排模型差异及命中原因；技能与蓝图条文一致（grep 可核验）。
- [FR-4 | 集成级] Given 演练仓库 4 票整链运行到出口报告，When 核对人工交互与出口，Then 恰两次（开工确认图外 + 合并确认图内），出口报告含逐票终态与预演记录并指路手动验收。
