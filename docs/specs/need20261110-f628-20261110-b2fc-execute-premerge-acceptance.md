# dev-execute 收口链验收前置：合并候选先验收、passed 才卡合并门

## 问题陈述

dev-execute 收口链（蓝图 v1.29 交付）在合并后才启动验收：验收 rejected 时缺陷已进主分支，需回滚或开修复票才能恢复主线干净，协作者拉到缺陷代码、历史产生回滚噪音。负责人在合并门做单向门决策时手头只有逐票评审与预演证据，没有使用方视角的验收结论——最重要的那份证据恰好在门后才产生。用户原话："先合并，验收不过，分支被污染了……我期望的是先验收，通过了没打问题，才卡合并门告知负责人。"

结构性原因有二：①dev-accept 入口门禁机械要求"当前分支 = BASE_REF"，把验收锚死在合并后的主分支上；②收口链把验收排在清理之后作为收尾，而非合并前的放行门。

## 方案

收口链整体重排——验收从"合并后的收尾"改为"合并前的放行门"：

**新顺序**：运行全绿 → 收口门禁（fresh 全量检查）→ **在运行 worktree 上对合并候选（运行分支）执行验收** → passed → 准备 PR（Evidence 含验收报告编号与终态）→ pre-push 门 → 合并确认（单向门，全模式人工，语义不变）→ 执行合并 → 票 done → 清理 → fulfilled 门（运行后停点）→ 出口报告。

配套三处适配：

1. **dev-accept 承载声明契约**：编排串联调用时随派发声明验收承载（合并候选 = 运行分支）；单独手动调用不声明，保持现状 BASE_REF 门禁。dev-accept 入口门禁按声明分流：编排形态按"工票全 implemented + 逐票评审 approved + 预演绿 + 当前分支 = 声明承载分支"校验；声明写入验收报告首行。
2. **rejected 重验环（限一轮）**：第一轮 rejected → 按 dev-fix 纪律自动开 fix 票入运行图（复用既有脚本修订补图机制）→ 修复 → 评审 → 合回 → 预演绿 → 自动重新验收（新报告，标注重验轮次）；第二轮仍 rejected → 运行停在待判断点等人（全模式保留人工，无人值守不豁免，语义同合并门），分支与 worktree 保留。
3. **清理与人工停点定位修订**："合并未执行不清理"扩展为"验收未 passed 且合并未执行不清理"；运行内人工交互从"恰两次"改为按值守模式分档表述——开工确认与合并确认不变，有人值守验收段交互前置，rejected 待判断点为条件性人工停点（触发才出现）。

本 spec 显式反转蓝图 v1.29"验收在合并后自动启动"对编排路径的排布（v1.29 反转 spec 0006 的先例同款手法：旧修订记录不回改，收口行为以新版为准）；手动 /dev-accept 路径零改动。

## 用户故事

- 作为负责人，我想在合并门前看到验收报告编号、passed 终态与硬伤/瑕疵结论，以便凭完整证据做单向门决策，而不是合并后才知好坏。
- 作为仓库主人，我想让验收 rejected 的改动停在运行分支上，以便主分支历史不被缺陷污染、协作者不拉到坏代码。
- 作为编排用户，我想让第一轮验收 rejected 后自动开 fix 票修完重验，以便小缺陷不停在等人、运行自己走到合并门。
- 作为无人值守用户，我想让重验环跑完一轮后仍失败就停下等人，以便运行不会无限自我循环烧资源，第二轮失败由人判断走向。
- 作为手动验收用户，我想让单独运行 /dev-accept 的门禁与行为保持现状，以便已合并 spec 的验收流程不受编排改造影响。

## 实现决策

1. **治理顺序：先蓝图后技能**（v1.33 先例）。蓝图修订先行：§11.17 dev-execute 收口链段重写（v1.34 条目，显式反转 v1.29 的合并后验收排布）、§11.9 dev-accept 补承载声明与重验入口、§8 决策点表人工门表述按新停点修订；随后技能正文落盘——dev-execute SKILL.md（收口链节、续接节、异常流节、入口门禁在途态枚举、description）与 run-mechanics（收口链全节、中断续接判读次序、验收段细则）及 dev-accept SKILL.md（入口门禁、承载声明、重验分支）。
2. **承载声明契约**：dev-execute 调 dev-accept 时随派发声明验收承载，两值——`合并候选`（编排串联，指向运行分支）与缺省（不声明 = BASE_REF 现状）；声明机械可校验（当前分支 = 声明分支），写进验收报告首行形态行。dev-accept 不新增探测，门禁判据按声明分流。
3. **dev-accept 重验入口**：编排重验声明 + 上一份报告 `rejected` 终态 + fix 票已 approved 合回且预演绿 → 允许开新验收报告（标注重验轮次、引用前轮报告编号）；旧报告不回改、不删除。既有"rejected 即终态不重开"门禁对无重验声明的调用保持原样。
4. **出口序列时序**：dev-accept 的 passed 后序列（蒸馏 → 清扫过程档 → spec 置 done）内容不变、时点在编排形态下延后到合并后执行——由 dev-execute 收口链承载调用时点，dev-accept 纪律文本只改承载与门禁，不改序列本身；fulfilled 门仍为运行后停点（全模式等人）。
5. **收口链机械顺序**：§8.1 收口起点核对不动（fresh 门禁证据仍引出口报告）→ 新增验收阶段（先自动化段后人工段，dev-accept 纪律全文在运行 worktree 执行）→ §8.2 PR 与 pre-push（Evidence 增验收报告编号与终态项）→ §8.3 合并确认与执行（零改动）→ §8.4 票 done（零改动）→ §8.5 清理（前置同步增验收报告——验收报告随每轮完成即同步回主工作区 docs/acceptance/，先于 PR 准备；评审报告同步仍按 v1.32 清理前置不变）→ §8.6 出口报告（构成不变，验收报告项载最终轮次结论；rejected 待判断停点时报告载两轮结论）→ §8.7 改写为合并前验收段细则（原"清理后自动启动"段废止）。
6. **重验环机制**：复用 §8 异常流既有 fix 票入图机制（dev-fix 纪律 + 脚本修订补图 + 门红期间只放行 fix 票合回）——差异仅在触发源从"预演失败"扩到"验收 rejected"，且重验上限一轮；第二轮 rejected 的停点经升级提问承载（档 1）/主会话停点（档 2–4），呈现两轮验收报告结论，处置归人（再修 / 放弃 / 接管，不预设菜单）。无人值守下第一轮重验为纪律化自主处置（留痕随票 Progress 与出口报告自主决策清单）。
7. **续接判读次序重排**（§5.6 第 6 条）：在途态枚举按新链序重写——验收报告 draft（重验环在办）→ 待判断停点（两轮 rejected）→ passed 且未合并（停合并门）→ 合并后（done/清理/fulfilled 既有分支）；"验收未 passed 且合并未执行不清理"使续接时 worktree 与分支必在，推导前提成立。
8. **人工停点定位分档表述**：有人值守 = 开工确认 + 验收段交互（复述确认、人工段实操走查）+ 合并确认 + rejected 待判断点（如触发）；无人值守 = 开工确认 + 合并确认 + rejected 待判断点（如触发），验收段全自动。GLOSSARY「无人值守」词条"除合并到主分支外"句修订为"除合并到主分支与验收二轮 rejected 待判断停点外"；「合并候选验收」新词条登记（双份资产同步）。
9. **验收段异常流并入 §8 决策点表述**：验收 rejected 一轮 / 二轮 / 合并门拒绝三类在 §8 决策点表与异常流节按值守模式分档呈现，与既有五类异常流并列；档 1 经升级提问/洞穴在图内承载（含验收代理停回主会话的混合形态细则照旧）。
10. **零改动声明**：dev-accept 判定分级判据（硬伤/瑕疵）、介质选择三态规则、使用方走查轴装载纪律、逐票评审与预演机制、开工确认双点选、ADR 0003 物化语义（done 落盘不提交）、check.sh 全部子命令——本 spec 一律不动。

## 测试决策

本仓库交付物为技能纪律文本，无运行时测试框架；验证 seam 清单：

- **dev-accept 入口门禁**：承载声明分流的判据完备性（编排形态四条件、缺省形态两条件、重验三条件互斥完备）——条文自查 + validate。
- **收口链顺序一致性**：SKILL.md 收口链节与 run-mechanics §8 的散文重述点按 dual-copy-assets #5 同批登记（v1.32 先例）——两处顺序条款逐段比对。
- **续接判读**：§5.6 在途态枚举与入口门禁在途态例外四态枚举互洽（无漏态、无冲突态）——枚举自查。
- **整链演练**：演练仓库（tmp/devx-drill 先例）跑一张多票 spec，核销集成级场景（验收承载切换、rejected 重验环、二轮停点、清理保留、合并门证据呈现）。
- 既有同类先例：spec 0013（收口链入图演练）、spec 20261108-2fe1（收口自动串联）、票 20261108-a202（清理前置同步）。

## 验收场景

- [FR-1 | 工单级] Given dev-execute 编排串联调用 dev-accept 且声明承载 = 合并候选，When 入口校验，Then 按"spec approved + 工票全 implemented + 逐票评审 approved + 预演绿 + 当前分支 = 运行分支"放行，不要求工票 done 与 BASE_REF。
- [FR-1 | 工单级] Given 单独手动调用 /dev-accept（无承载声明、无重验声明），When 入口校验，Then 现行门禁语义逐条不变（工票全 done + 当前分支 = BASE_REF）。
- [FR-2 | 工单级] Given 验收 passed，When 生成 PR 正文，Then Evidence 节含验收报告编号、终态 passed 与硬伤/瑕疵结论摘要；Given 验收 rejected 或重验在办，When 收口推进判定，Then 不放行进入合并确认门。
- [FR-3 | 工单级] Given 第一轮验收 rejected，When 重验环条款被读，Then 自动开 fix 票入运行图（dev-fix 纪律 + 既有补图机制）、顺序"修复 → 评审 → 合回 → 预演 → 重新验收"明确、重验上限一轮写明。
- [FR-4 | 工单级] Given 第二轮验收仍 rejected，When 停点条款被读，Then 全模式停点等人、无人值守不豁免、语义同合并门（沉默不算放行）、分支与 worktree 保留写明。
- [FR-5 | 工单级] Given 重排后的收口链条款，When 通读顺序，Then 票 done、蒸馏、清扫、spec 置 done、fulfilled 门全部位于执行合并之后，合并前无 fulfilled 确认停点。
- [FR-6 | 工单级] Given 清理条款，When 读核对句，Then "验收未 passed 且合并未执行不清理"成立，且验收报告同步回主工作区的时点（每轮完成即同步、先于 PR 准备）写明。
- [FR-2 | 工单级] Given 负责人在合并门拒绝合并，When 处置，Then 运行停在合并门、盘上状态即运行状态、不强推不清理、已 passed 的验收判定不回滚（现状语义保持）。
- [FR-1 | 集成级 | 人工：整链演练由真实编排会话驱动，验收承载切换与报告声明无脚本化承载票] Given 演练 spec 运行全绿，When 收口启动验收，Then 验收在运行 worktree 的运行分支上执行，验收报告首行声明承载 = 合并候选，非 BASE_REF。
- [FR-3 | 集成级 | 人工：整链演练由真实编排会话驱动] Given 第一轮验收 rejected，When fix 票修复合回且预演绿，Then 自动开具新验收报告（标注重验轮次、引用前轮编号），passed 后进入 PR 准备与合并门。
- [FR-4 | 集成级 | 人工：停点交互语义需人在环观察] Given 第二轮仍 rejected，When 运行到达待判断点，Then 全模式停点等人，`git log BASE_REF` 无运行分支提交，运行分支与 worktree 完整保留，出口报告载两轮验收结论。
- [FR-6 | 集成级 | 人工：整链演练由真实编排会话驱动] Given 验收未 passed 时会话中断，When 重入续接，Then 运行分支与运行 worktree 完整保留，续接从验收段在途态推导恢复（报告 draft / 待判断停点 / passed 停合并门各分支可达）。
- [FR-2 | 集成级 | 人工：整链演练由真实编排会话驱动] Given 全流程验收 passed 且负责人确认合并，When 合并完成，Then BASE_REF 含运行内容，票 done 与清理在合并后发生，fulfilled 门为合并后的运行后停点，出口报告含最终验收报告编号与终态。

## 非目标

- 不限轮数的全自动重验闭环（need D1 拍板：限一轮，第二轮待人判断）。
- fulfilled 确认门前置到合并前（need D2 拍板：保持合并后）。
- 验收承载迁移到部署环境/集成环境（验收仍在运行 worktree 本地承载）。
- dev-accept 判定分级判据、介质选择三态、走查轴装载纪律的任何改动（实现决策 10）。
- 手动 /dev-accept 路径的行为改动（承载声明缺省语义 = 现状）。
