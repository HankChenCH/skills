# dev-review 评审轴清单制：每轴恰一个独立子代理

## 问题陈述

dev-review 双轴评审的独立性承诺（「双轴独立不互相稀释」）在实际执行中落空：纪律文本写的是"两轴**可派**两个并行子代理分头评审"——许可而非强制。执行体据此普遍选择派 1 个子代理串着做两条轴（用户 2026-11-04 观测：dev-execute 各档运行中评审"大多数是开 1 个子 agent 来执行双轴审核"）。后果有二：

1. **上下文污染**：同一个子代理先做标准轴再做 Spec 轴，第二轴的判断建立在第一轴已装载的材料与已形成的结论之上——Spec 轴的"缺失/走样/超范围"三查被标准轴视角带偏，独立评审退化为先后评审。
2. **轴不可扩展**：轴写死在条文中，日后加架构审核、安全审计等新轴时，没有"按轴派发、按轴聚合"的机制可挂靠，无法靠增加子代理并发提效。

证据锚点：`skills/dev-review/SKILL.md:50`（"可派两个并行子代理"）；蓝图 dev-review 条目（"两轴可并行子代理执行"）；蓝图 review 产物行（"双轴独立报告，不合并重排"——独立性有契约、执行形态无强制，二者脱节）。双轴纪律由批 1 交付（2026-10-26，早于编号 spec 体系），本次为其执行形态的契约强化。

## 方案

把双轴评审从"许可并行子代理"改为**评审轴清单制 + 每轴恰一个独立子代理的强制纪律**：轴是可枚举的纪律单元（名称 + 判断依据材料清单 + 产出节）；有子代理能力的宿主上，一个子代理只执行一条轴、只装载本轴材料，并行派发优先、串行逐轴派发次之——隔离靠独立上下文保证，不靠并行；无子代理能力才降级为单上下文逐轴先后亲做，且必须如实声明降级。聚合方（主会话 / 编排方 / 图内评审子代理）只做分轴聚合，不重审不改写。dev-execute 各档与图内评审链执行的是 dev-review 纪律全文，本改动自动继承，编排层与 spec 0013 已交付链零改动。

## 用户故事

- 作为请求评审的用户，我想让每条评审轴由一个只装载本轴材料的独立子代理评审，以便两轴结论互不污染、不因共享上下文而偏颇。
- 作为仓库主人，我想让评审轴成为可枚举清单，以便日后加架构轴、安全轴时按轴并发派发，评审吞吐随轴数扩展。
- 作为编排用户，我想让 dev-execute 各档与图内评审自动继承每轴独立纪律，以便编排层与已完成链零改动。
- 作为无子代理宿主的用户，我想在评审降级为单上下文时得到如实声明，以便知道该份报告的隔离弱点。

## 实现决策

- **评审轴清单制**：评审轴 = 一条独立评审纪律单元，由三要素构成——轴名、判断依据（该轴允许装载的材料清单）、产出节（报告中的对应节）。当前清单恰两条：标准轴（判断依据：已文档化编码标准 + ref-implementation 标准 + ref-review 坏味道基线 + 评审 diff；产出节：标准轴 findings）、Spec 轴（判断依据：工单全文 + spec 对应章节 + 评审 diff；产出节：Spec 轴 findings）。派发、聚合、报告节结构均从清单推导，条文不写死轴数。
- **每轴恰一个独立子代理（强制）**：有子代理能力的宿主上，评审执行体不得在单一子代理内串做两条轴，也不得亲做其中任何一轴；每轴派发恰一个子代理，子代理只装载该轴判断依据所列材料。并行派发优先；宿主并发受限时串行逐轴派发——每个轴子代理仍是独立上下文，隔离不因串行而破。
- **无子代理退化（显式降级）**：宿主无子代理原语时，评审执行体逐轴先后亲做：一条轴的 findings 全文出具落稿后，才进入下一轴；轴间不复用中间结论、不回改已出具轴。评审报告必须声明降级形态（如"单上下文逐轴评审，无子代理隔离"）。
- **聚合纪律升格为强制**：聚合方只做分轴报告聚合与阻断计数，不重审、不合并重排、不互相稀释——既有条文保留，从描述升格为义务。
- **报告契约不变**：评审报告 frontmatter（id/status/tickets/branch/created）与既有分轴节名保留；新增轴时报告新增对应节，模板节结构随清单扩展。
- **编排层零改动继承**：dev-execute 档 1 图内评审子代理与档 2–4 主会话调用执行的都是 dev-review 纪律全文，每轴派发在纪律全文内生效——dev-execute 技能文件、spec 0013 图内阶段链、票 0023 宿主回退链均不感知轴数、零改动。
- **新术语**：「评审轴」（一条独立评审纪律单元 = 轴名 + 判断依据 + 产出节）登记 GLOSSARY。
- **治理顺序**：先改蓝图再改技能——蓝图 dev-review 条目双轴句改写（许可改强制 + 清单制）、review 产物行同步、§13.2 dev-review 自测行补"轴派发核验"项、修订记录新版本顺位；技能侧改 dev-review 纪律文件评审纪律节。全部随实现工票落，先文档后技能。

## 验收场景

- [FR-1 | 工单级] Given 有子代理能力的宿主，When dev-review（单票或编排模式）进入评审执行，Then 每轴恰派发一个子代理，子代理只装载本轴判断依据所列材料，纪律文本含强制措辞（grep"每轴恰一个"可核验）。
- [FR-1 | 工单级] Given 宿主并发受限但具备子代理原语，When 评审执行，Then 两轴子代理串行派发，各自仍是独立上下文，隔离不被串行破坏。
- [FR-1 | 工单级] Given 演练仓库的评审对象，When 新会话实跑 dev-review 单票模式，Then 观察到子代理派发数 = 轴数、聚合报告分轴出具、聚合方未改写未重审 findings。
- [FR-2 | 工单级] Given 评审轴以清单表达，When 新增一条轴定义（材料清单 + 产出节），Then 派发、聚合、报告节随清单扩展，既有双轴专项条文与编排契约零改动（grep 派发/聚合条文无写死轴数量词可核验）。
- [FR-3 | 工单级] Given 无子代理原语的宿主，When 评审执行，Then 逐轴先后亲做、一条轴 findings 落稿后才进下一轴，报告声明降级形态。
- [FR-1 | 集成级] Given dev-execute 运行中某票进入评审阶段（任一档含档 1 图内），When 评审启动，Then 评审按每轴子代理执行、报告契约（branch/tickets/status）不变，编排层技能文件与本 spec 改动零交集（随下次真实编排运行首次核验）。

## 非目标

- 不实加架构轴、安全轴或任何新评审轴——机制就绪，轴本体待独立需求提出。
- 不改 dev-execute 各档形态、spec 0013 图内阶段链、票 0023 宿主回退链——评审继承靠纪律全文，编排文件零改动。
- 不改评审报告 frontmatter 契约（id/status/tickets/branch/created）与既有分轴节名。
- 不改 dev-implement、ref-review、ref-implementation 纪律本体与 `.sdlc/check.sh`。
- 不改单票模式与编排模式的入口门禁与出口分岔——只改评审执行形态（谁在什么上下文里执行），不改双轴的判断依据本体。
- 不改两轴阻断清零的出口语义与阻断处置流程。
