# dsh MCP 对话内管理插件 `@hankchen/dsh-mcp`（round 1 全 FR）

## 问题陈述

dsh 使用者要给智能体接外部 MCP server，现状只能手写 Cordis patch YAML（官方仅提供 memory 三个 default-off 示例 overlay，启用靠 `--patch` 一次性传参或手改 profile patch）；官方 `@deepseek-ai/dsh-mcp-manager` 备好了配置驱动的 server 舰队引擎（reconcile/状态聚合/restart/probe）但没有任何用户可见管理入口（need 20261117-ea73 背景、调研 20261117-ced7 Q3）。本套件第二款 dsh 插件（首个真实功能插件，承 need 20261115-339e 非目标 1 预留）要把这层「配置体验」补上：装进 profile 即获得对话内增删启停 MCP server 的能力，全程不手写 YAML。

## 方案

round 1 = need 全 FR 最小闭环（分轮拍板 2026-11-17：全 FR 一轮；FR-9 调研交付物已由报告 20261117-ced7 核销）：

1. **插件包 `@hankchen/dsh-mcp`**（need FR-7）：独立 npm 包，照 339e 全套规范（package.json 四要素 + `engines.dsh`、发布面预编译、双包发布顺序）；源码放 `agents/dsh/plugins/dsh-mcp/`（ADR f143 布局随包自动分发）。`cordis.patch.yml` insert 两行：`@deepseek-ai/dsh-mcp-manager` 挂载行（官方仅 Web/Desktop profile 自带，headless/sdk/acp 自定义 profile 不含——ced7 F2.3，故插件自带）+ 本插件模块行（`inject` mcpManager/commands/tools/settings 服务；credentials 不在插件行——凭据模板展开由 mcp-manager 行自带 `inject: [credentials]` 承担，插件只透传模板串不消费凭据服务；票 20261117-dd1f 按 cordis inject 语义与 loader 一手来源裁决，工单 Progress 留痕）；依赖 `@deepseek-ai/dsh-mcp-manager`（版本范围归 design，发布前对官方当前版本核验）。
2. **持久化走官方链路**（need FR-3，ced7 F1.4）：server 清单变更经官方 Settings→ConfigEditor 链路写通道提交——落盘 `$DSH_HOME/profiles/<名>/cordis.patch.yml` + volatile 热提交进运行时；不自管配置文件、不直改 patch 文件、不用 `fiber.update()` 直改（三者在调研中被排除：register 不持久、fiber.update 写回不重启存活）。写时全量校验 + revision 拒旧由官方承担（「the document never stores a server the manager cannot act on」）。
3. **双入口**（need FR-1，拍板 D3）：人类命令经 `ctx.commands` 注册（web slash 面与 sdk `run()` 可达）；模型工具经 `ctx.tools.register` 注册（全形态可达）。两入口同调一套管理服务（列含状态/添加/移除/启停）。
4. **配置字段对齐官方 `McpManagedServerEntry` 平铺结构**（need FR-2）：stdio = `command`/`args`/`env`/`cwd`；远程 = `url`/`headers`；敏感值接受 `${credential:…}` 模板（need FR-5，挂载行 `inject: [credentials]`——ced7 F2.3）。
5. **即时生效语义 = 官方 reconcile 语义**（need FR-4）：新增 enabled 条目挂载、移除卸载、`enabled: false` 卸载但条目保留、其他字段变化仅重建该实例（ced7 F1.4 原文），不要求重启 dsh。
6. **infra 侧编目确认**（need FR-6）：新包进 `agents/dsh/plugins/` 即自动随包分发与编目（339e 机制），desktop 拒装/官方命令转发/两落点对账全部复用既有实现；本轮验收确认该链路对新包成立，无预期代码改动。

## 用户故事

- 作为 dsh 使用者，我想在会话内用 `/mcp …` 人类命令列出（含连接状态）、添加、移除、启停 MCP server，以便不学 Cordis patch 语法就接外部系统。
- 作为 dsh 使用者，我想直接对模型说「帮我加一个 MCP server」，由模型调用管理工具完成配置，以便对话式接入。
- 作为 dsh 使用者，我想让对话内做出的变更跨重启保留，以便配置一次持续有效。
- 作为 dsh 使用者，我想在 server 连不上时查到失败状态与原因线索、修好后无需重启，以便故障自愈面可控。
- 作为 dsh 使用者，我想用 `${credential:…}` 模板引用凭据而非明文入清单，以便密钥不落配置文件。
- 作为 infra 使用者，我想经 `npx @hankchen/infra` 的 `plugin add` 把本插件装进目标 dsh profile，以便与既有插件同一套安装体验。
- 作为套件维护者，我想让第二款插件延续 339e 全套生产规范（四要素/预编译/双包顺序/对账三查），以便插件资产模式可持续复制。

## 实现决策

- **插件包契约（need FR-7）**：包名 `@hankchen/dsh-mcp`，语义化版本独立演进；package.json 四要素照 plugin-assets.md §1.2（`type: module`、`main` 直指模块源码、`files` 含 patch 与模块、`dsh.bundle.patch` 指向随包 cordis.patch.yml）；`engines.dsh` 范围与 mcp-manager 依赖范围归 design（发布前对官方当前版本核验，need A3 缓解：只依赖官方公开 Config schema，不自实现落盘逻辑）。【修订 20261118-2d72】依赖生态现实与如实钉版决策：官方 manager 0.2.2-rc.2+ 的 peer 精确钉同 rc 兄弟套件、官方 latest 主包 0.2.2-rc.1 无兼容 manager（npm view 逐一核验留痕票 Progress）——插件如实钉版（engines.dsh ≥ 0.2.2-rc.2、manager ≥0.2.2-rc.2）使错配组合显式拒绝（fail-loud），端到端真跑延后至兼容星座在 registry 可达（FR-8/FR-4 集成前置门承载）。
- **cordis.patch.yml 挂载契约（ced7 F2.3）**：insert 两行——mcp-manager 行（`name: '@deepseek-ai/dsh-mcp-manager'`，带 `inject: [credentials]` 以支持凭据模板；行 id 归 design）+ 本插件模块行（`name: '@hankchen/dsh-mcp'`；行 id 与两行优先级归 design）。patch 顶层数组形态过 verify-bundle 校验（339e fix f158 先例：官方 loader 要求 PatchOptions[]、insert 元素 id+name 必填）。
- **管理服务契约**：插件 `apply(ctx)` 内组合单一管理服务，双入口共调；操作集 = 列出（含状态）/添加/移除/启停。写通道 = 官方 settings/configEditor 持久化 API（settings `update`/`mutate` 带 revision 校验，ced7 F1.4）；命名空间 = 本插件 patch 中 mcp-manager 行的 entry id（id 值归 design）；`servers` 为 volatile 字段与官方 schema 一致。读通道 = `ctx.mcpManager` 的 `list()`/`watch()`（状态聚合 `McpManagedServerStatus` 含 failed/load.lastError/cleanup）。
- **配置字段契约（need FR-2）**：两 transport 字段集对齐官方 `McpManagedServerEntry`（平铺结构、`enabled` 持久意图字段、超时与重连字段可选透传）；`serverName` 命名规则（`[A-Za-z0-9_-]{1,32}`、唯一性）沿官方 schema，冲突时写被拒并列冲突对象。
- **人类命令契约（need FR-1）**：经 `ctx.commands` 注册单命令多子命令形态（`/mcp <子命令> …`，子命令集与参数语法归 design）；覆盖列出（含状态）、添加 stdio/远程两类、移除、启停。可达面声明：web（slash/命令面板）与 sdk（`run()` 识别原生命令）为一等支持形态；headless/acp 组合含命令但无官方适配器触发面、sdk-minimal 无命令子系统（ced7 F2.1）——不作为本命令的验收形态。
- **模型工具契约（need FR-1）**：经 `ctx.tools.register` 注册管理工具（工具名与参数 schema 归 design；参数面覆盖两类 transport 的必填字段 + 可选 env/headers/凭据模板串）；运行时工具集变化依托官方逐步准入机制（`tools/change`、步骤中途移除的 `UNKNOWN_TOOL` 空窗为官方既定行为，ced7 F2.2）。
- **即时生效契约（need FR-4）**：变更语义 = 官方 reconcile 规则（新增 enabled 挂载/移除卸载/禁用卸载保条目/字段变化重建单实例）；连接失败的降级沿 mcp-client 官方语义（自动重连、预算耗尽注销、`waiting-credentials` 状态），插件只负责状态呈现与可修复操作，不自行重试。
- **凭据契约（need FR-5）**：`env`/`headers`/`command`/`args`/`cwd`/`url` 接受 `${credential:REF}` 模板串透传（展开与脱敏由 mcp-client 官方承担：诊断与工具失败中替换为 `[redacted]`）；入口提示语引导模板优先于明文（引导文案归 design/README）。
- **infra 侧（need FR-6）**：无代码改动预期——新包进 `agents/dsh/plugins/` 后编目、菜单、官方命令转发、两落点对账、desktop 拒装、锁文件记账、`verify-pack` 三查、`verify-bundle` 四要素校验全部复用既有实现；验收确认全链路对新包成立，若暴露既有实现缺陷则以 fix 票处置（339e f158 先例）。
- **发布纪律**：照 plugin-assets.md §1.4——先发插件包（pack → verify-bundle → publish `--access public`），再发初始化器（verify:pack 三查）；prepack/postpack 预编译照抄 demo（ADR f650）。

## 测试决策

- **seam 清单**：①插件包结构与挂载行校验（patch 两行、id/name/inject、顶层数组形态）；②管理服务（写通道调用契约：settings 持久化 API 参数形态、读通道 list/watch 状态投影）；③人类命令注册与子命令分发（替身 ctx 断言注册与执行路径）；④模型工具注册与参数 schema 校验（两 transport 必填/可选、模板串透传）；⑤配置校验失败路径（坏条目/冲突/缺失字段的拒绝呈现）；⑥infra 编目对新包的自动收录与对账（fixture 包目录）。
- 既有先例：339e 的四 seam 单测 + 临时目录端到端纪律（node:test、不 mock 文件系统、替身保真门）；插件包发布态校验沿用 `verify-bundle`。
- 官方组件真实行为（manager reconcile、凭据展开、重连）以集成级为界，单测不替身官方内部——只对公开 API 形状断言。

## 验收场景

- [FR-7 | 工单级] Given `agents/dsh/plugins/dsh-mcp/` 包目录，When 运行 `verify-bundle` 校验器，Then 四要素齐备、patch 引用名 = 包名、模块导出 name+apply、patch 为顶层数组且含 mcp-manager 与本插件两 insert 行。
- [FR-7 | 工单级] When 检视发布对账，Then 包内 `agents/*/plugins/` 清单 = 仓库清单且含本插件，禁含 node_modules 三查通过，技能侧对账不变。
- [FR-1 | 工单级] Given 替身 ctx，When 插件 apply，Then `ctx.commands` 注册出 `/mcp` 命令（含列出/添加/移除/启停子命令分发）且 `ctx.tools.register` 注册出管理工具，两入口同调管理服务。
- [FR-2 | 工单级] Given 管理工具参数 schema，When 校验 stdio 条目（command/args/env/cwd）与远程条目（url/headers），Then 必填缺失或跨 transport 字段混用即拒绝并指明字段；可选超时/重连字段透传不断言内部值。
- [FR-3 | 工单级] Given 管理服务的写操作，When 添加/移除/启停一条 server，Then 调用为官方 settings/configEditor 持久化 API（断言调用形态与命名空间），未出现自管配置文件写入、patch 文件直改或 `fiber.update` 调用。
- [FR-4 | 工单级] Given 官方 reconcile 语义契约，When 启停条目，Then 期望语义为：禁用卸载连接但条目保留在清单、重新启用重建连接、移除即从清单消失；失败状态经 list/watch 投影为可查询状态（含 failed 原因线索），不要求重启 dsh。
- [FR-5 | 工单级] Given 带模板串的 env/headers 值，When 提交添加，Then 原样透传不展开不脱敏（展开归官方运行时）；凭据引用缺失时状态投影含 `waiting-credentials`。
- [FR-2 | 工单级] Given 添加请求与既有条目同名（serverName 冲突）或与官方保留命名冲突，When 提交，Then 写被拒并列出冲突对象，不产生半写入状态。
- [FR-6 | 工单级] Given 新包入 `agents/dsh/plugins/`，When 跑 infra 编目与交互菜单，Then 条目正名 = `@hankchen/dsh-mcp`、提示 = 包 description、可勾选转发安装；`desktop` profile 拒装行为不变。
- [FR-6 | 工单级] Given fixture profile（package.json 含依赖行与 `dsh.profile.bundles` 行），When 安装后对账，Then 两落点齐备记成功；缺任一报错指明缺失落点与 profile 路径（need 异常流 B 的拒装与异常流 C 的 README 缓解路径同 339e 口径，随文档检查覆盖）。
- [FR-8 | 集成级 | 承载票 NNNN] Given node ≥24 环境、registry 可达、`@hankchen/dsh-mcp` 已发布、临时 `DSH_HOME`、经 CLI 真装插件的 profile、官方 dsh 与 `@deepseek-ai/dsh-mcp-manager` 兼容星座在 registry 可达（【修订 20261118-2d72】官方 latest 主包 0.2.2-rc.1 无兼容 manager——星座不可达期间集成场景以前置门 skip 兜底，不判失败），When 真实 boot dsh（形态与任务编排归承载票，如 headless 一次性任务驱动管理入口），Then 插件加载无错、经管理入口添加一条 stdio server 成功、对应 `mcp__<名>__<工具>` 出现并可调用、profile `cordis.patch.yml` 出现持久化条目、重启 dsh 后该 server 仍在并自动连接（need FR-8 端到端验收线）。
- [FR-4 | 集成级 | 承载票 NNNN] Given 集成环境同上（含兼容星座可达前置，【修订 20261118-2d72】），When 添加一个连不上的 server（不存在命令/不可达 url），Then 管理入口可查询到 failed 状态与原因线索、条目保留可移除或修复，全程不要求重启（need 异常流 A）。
- [FR-3 | 集成级 | 人工：npm publish 属单向门，发布动作在验收时点由维护者执行] Given `@hankchen/dsh-mcp` 已发布，When `npm view @hankchen/dsh-mcp` 与仓库包清单对账，Then 版本与 `agents/dsh/plugins/dsh-mcp/package.json` 一致（339e 人工条目同法）。
- [FR-9 | 工单级] Given 调研报告 20261117-ced7，When 检索，Then 覆盖 RQ1（持久化机制与落点，含 Settings→ConfigEditor 链路结论）与 RQ2（双入口各形态可见性）两问、每条结论带一手来源且关键结论经主会话回原文抽验（need FR-9 交付核销确认，报告已于 2026-11-17 落盘）。
